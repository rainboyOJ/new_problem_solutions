# Build a separate Canvas graph for relations2

The existing `/relations` page remains unchanged because its React Flow implementation has long-running usability problems such as node overlap and sluggish zoom. We will add `/relations2` as an independent graph view that reuses the existing relation graph data, uses `d3-force` for force-directed layout, and uses PixiJS for Canvas/WebGL rendering and viewport interaction. Keeping a separate route provides an explicit fallback while the new view is validated.

## Considered Options

- Replace `/relations`: rejected because it removes the known-good fallback and couples rollout to the new renderer.
- Continue with React Flow: rejected for this view because the current DOM/SVG rendering path is the source of the reported responsiveness concerns.
- Hand-roll native Canvas rendering: rejected because hit testing, dragging, viewport transforms, and accessibility would become project-owned infrastructure.

## Consequences

The new page must preserve the existing relation semantics and API contract unless a later decision explicitly changes them. It shows relation-participating problems by default (currently 117 of 2139 valid problems); an explicit control can add isolated problems for global exploration. Nodes are circles at overview zoom, with labels progressively revealed at closer zoom; hover and selection expose the problem identity, click opens details, and double-click opens the explanation. `pre` edges are solid directed arrows, while `common` edges are undirected dashed lines; the legend and interaction feedback must communicate line type as well as color. The existing problem-page relation entry remains pointed at `/relations`, while a separate Canvas relation entry points at `/relations2`; the new page accepts the existing `oj/pid/edges/isolated` deep-link parameters. The MVP uses one force-directed layout and keeps search, relation/isolated filters, fit/reset/re-layout controls, legend, details, and explanation navigation; the old page's alternate layouts and tuning sliders are deferred. The force simulation runs in a Web Worker so the main thread remains available for PixiJS pan, zoom, and hit testing; a main-thread fallback is required when Workers are unavailable. The layout uses a collision radius with padding as a hard constraint: settled node circles may not intersect, while edge crossings are allowed. Canvas visual nodes are paired with keyboard-operable DOM search/results/details controls so the graph remains usable without pointer hit testing. Mobile uses pinch zoom, one-finger pan, tap-to-select, long-press drag, a collapsible toolbar, and a bottom details drawer. Performance acceptance targets 60 FPS for the default relation network and at least 30 FPS with all current nodes visible, with no main-thread interaction block longer than 100 ms; initial positions may appear before the Worker fully settles. Relation data is fetched on first entry or explicit refresh only; automatic polling is intentionally omitted so background content updates do not reset an active exploration. Search preserves graph context by dimming non-matches rather than removing them or re-running layout; matching supports OJ, problem ID, title, difficulty, and tags, and selection centers the view. Edge hover exposes the stored relation reason when present. Relation filters use the currently visible edge types to decide which nodes remain in the compact default set; selected or matched nodes are retained, and the isolated toggle shows all nodes. Viewport zoom is anchored at the pointer or pinch center and is available through explicit zoom-in, zoom-out, fit, and reset controls plus keyboard equivalents. Node positions are persisted in browser local storage under a relation-data fingerprint; re-layout clears the current saved positions and new problems receive fresh positions without modifying content metadata. User-dragged nodes remain fixed in their saved positions until re-layout or reset, while other nodes continue to avoid collisions. Loading and API failure states expose progress, retry, and a link back to `/relations`; an empty compact graph explains that enabling isolated problems will show the full catalog. If WebGL is unavailable, the page falls back to a keyboard-operable DOM relationship view with retry and a link to `/relations`; a second Canvas renderer is not maintained. The graph view is read-only with respect to relation metadata: dragging changes only a local visual position, and adding or editing `pre/common` relations remains a content-authoring workflow outside `/relations2`. Node fill color follows the existing primary tag color and is explained by the tag legend; relation meaning is encoded independently by edge color and line style, while difficulty remains in labels/details rather than node color. The global navigation adds a Canvas relation link to `/relations2` while retaining the existing `/relations` link. Automated coverage currently includes route/static-asset smoke tests, strict TypeScript checking for the graph package, and both relations builds; focused graph/Worker protocol unit tests and a repeatable browser benchmark for frame rate, main-thread blocking, and node collisions remain follow-up work outside hardware-sensitive CI gates. PixiJS adds a frontend dependency and requires deliberate handling of node hit testing, keyboard/accessibility affordances, high-DPI sizing, and performance verification at the repository's real graph size.
