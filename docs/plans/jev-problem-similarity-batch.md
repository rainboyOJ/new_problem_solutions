## Jev 批量补充题目相似关系方案

记录日期：2026-10-02。

状态：方案决策已确认，尚未实现或调用模型。本次仅保存方案，不修改代码、题解或关系元数据，不产生 API 费用。后续执行以用户的新指令为准。

## 目标与范围

使用 AI 批量识别仓库内有教学价值的相似题，减少人工逐题维护关系的工作量。第一阶段只新增 `common`，不生成学习先后关系 `pre`，不添加仓库外推荐 `recommend`。

相似关系应帮助学生迁移解题思路：两题的核心模型、状态设计或关键观察相同，适合放在一起对比训练。仅有相同算法标签、故事背景或相似词汇，不足以建立关系。

允许题目没有关系。宁可漏掉一些相似题，也尽量避免错误连边；关系图覆盖率不是首批验收目标。

## 已确认的决策

以下决策来自本次讨论，后续实施应保持一致。

| 决策 | 已确认方案 |
| --- | --- |
| 关系类型 | 先做相似题关系 `common` |
| 相似标准 | 核心模型、状态设计或关键观察相同，具有学习迁移价值 |
| 写入方式 | AI 自动批量写入，之后人工抽查，不逐条等待事前批准 |
| 错误取舍 | 优先减少错连，允许漏连和孤立题目 |
| 模型选择 | 优先试 Jev，效果不足时允许其他模型辅助或替换 |
| 首批规模 | 先做一个算法专题，抽查后再决定扩展 |
| 已有关系 | 只新增，保留已有关系 |
| 费用上限 | 首批累计 API 费用不超过 5 美元，包含辅助模型费用 |
| 抽查方式 | 写入后随机抽查 30 条，不足 30 条则全查 |
| 扩展条件 | 抽查最多允许 1 条不符合相似标准；由用户作最终教学判断 |
| 可追溯性 | 保存新增题对、判断结果和模型版本，支持撤销本批新增关系 |

抽查标准是本轮确认的操作规则，不代表模型整体准确率已有统计保证。没有新增关系时，不能据此认定试验通过或具有实用效果。

## Jev 的角色与已知边界

根据本次查阅的 [TypeSafe 官方介绍](https://docs.typesafe.ai/introduction)，Jev 接受材料和明确的问题，返回 Choice、Score 或 Noul 等结构化判断。它不生成自然语言解释；需要复杂推理的问题应拆成多个具体判断。

因此，本方案将 Jev 作为题对判断器的候选，而不是假定它能自行搜索仓库、理解所有算法并生成可核查的关系理由。候选检索、材料整理、结果合并和元数据写入由外围流程完成；必要时用其他模型提炼解法和起草理由。

[官方模型说明](https://docs.typesafe.ai/models)指出，英文是主要训练语言，中文等语言的效果需要针对实际内容验证。本方案尚未验证 Jev 对中文算法题、代码和解法模型的判断能力。返回格式正确或概率较高，不等于教学关系正确。

实施时固定并记录实际模型版本；价格、访问资格、上下文限制和速率限制以执行时的官方文档及账户能力为准，不把本次文档快照当作长期保证。

## 拟定流程

### 1. 建立首批清单与基线

记录专题、题目身份、现有关系、内容版本和工作区状态。题目身份使用 frontmatter 中的 `oj` 与 `problem_id`，不能只依赖目录名。

检查题解、引用代码与原题材料是否一致。材料不足或互相矛盾的题目暂不参与自动写入，记录排除原因。

### 2. 整理判断材料

每题材料包括原问题的关键约束、核心模型、状态或判定过程、关键观察，以及支持这些结论的题解段落或代码位置。

优先读取现有题解及引用代码，必要时参考 `problem.md`。其他模型提炼的摘要必须标明来源，不能把摘要当作未经核对的新事实。

### 3. 产生并去重候选题对

专题、标签和关键词用于找候选，不能直接作为写入依据。首批在材料量与预算允许时可比较专题内全部无序题对；未来扩展再评估关键词、模型摘要或向量检索的组合。

排除自身引用、重复题对和已经存在的相似关系。`common` 在语义上不表达方向，统计和去重时按无序题对处理；具体在一个还是两个 frontmatter 中存储，应检查现有读取行为后确定，避免重复制造图边。

### 4. Jev 判断与结果筛选

将判断拆成范围明确的问题，例如：两题是否共享核心模型、状态或判定结构是否相近、关键观察能否迁移、相似性是否仅来自通用算法标签。

保存原始结构化结果，再由明确规则合并为“新增关系”或“暂不写入”。具体提示词、评分组合与阈值需要在实施阶段验证，不预先把某个置信度数字等同于正确率。

对通过筛选的题对生成简短中文 `reason`，说明具体共同点。理由应来自材料与判断依据，不能伪称为 Jev 生成的解释。证据不足的题对保留为候选，不为填满字段强行写入。

### 5. 自动写入并校验

只追加新的 `common` 项，保留已有关系、题解正文及其他元数据；按仓库要求同步题目的 `updated`。引用必须指向真实存在且身份匹配的题目。

对修改过的题目运行 [关系校验器](../../scripts/problem-analysis-tools/check_relations.py)，检查字段、引用和重复关系，并检查差异中没有意外改动。校验通过只能证明元数据满足检查项，不能代替教学判断。

### 6. 写入后抽查

从本批新增的唯一题对中随机抽查 30 条，不足则全查，并记录随机种子。复核材料应列出两题、具体相似依据和原文位置，方便用户确认。

用户作最终教学判断，抽查结论单独保存，不覆盖模型原始输出。最多允许 1 条不符合标准才满足已确认的扩展门槛；发现的错误仍需修正。未达标时调整规则、修正或撤销本批新增关系，不直接扩大规模。

## 预算、记录与撤销

调用前按实际材料量、模型价格和请求数量估算成本。累计预算包含 Jev、其他辅助模型和可能计费的重试；发出下一次请求前为其预留费用，避免等到超支后才停止。无法估算费用或余额不足时停止新增请求。

每批至少保留：批次标识、题目清单、内容版本或哈希、提示词与规则版本、模型版本、原始判断、新增关系及理由、请求用量与费用、校验结果和人工抽查结论。记录中不保存密钥。

撤销应针对本批新增项，不恢复整份旧文件覆盖后续人工编辑。如果新增项已经被后续修改，应报告冲突，避免盲目删除。批次记录的实际目录和文件格式留待实施时确定。
