## 全仓 pre 关系方案审核与优化建议

审核日期：2026-10-02。整理日期：2026-10-03。

审核对象：[全仓 pre 关系配置 · 长期批次方案](./pre-relations-full-coverage-plan.md)。

结论：方案方向可行，但当前版本存在规则冲突和执行闭环缺口，不宜直接启动长期全量批次。建议先修订执行规格，完成 M0 工具与恢复验证，再运行有明确数量上限的 M1 试点。

## 2. 执行前必须修正的问题

### 2.1 严格判据、示例与机械校验不一致

对应原计划：§0、§4②、§4③。

原计划排除仅共享二分答案框架的关系，但 worker 示例将 `P1873 → 4135` 标为 `accept`，理由仍是“先掌握二分答案和 check，再处理划分型二分”。另外：

- 示例的 `OpenJ_Bailiance` 与实际 frontmatter 身份 `OpenJ_Bailian` 不一致。
- [P1873](../../problems/luogu/P1873/index.md) 与 [4135](../../problems/OpenJ_Bailian/4135/index.md) 均为“普及/提高-”，不满足计划要求的严格难度递增。
- `reason` 被要求包含双引文，但示例只把引文放在独立字段，`reason` 本身没有引文。
- “关键词命中至少一个”只能证明存在相关用词，不能证明 A 的具体步骤被 B 复用。

建议修订：

1. 用核对过题解、引用代码和题面来源的强前置正例替换示例；把上述题对作为“不满足本次严格口径”的反例。
2. 明确双引文保存在证据字段，`reason` 表达具体迁移关系；如确实要求 `reason` 内嵌引文，则同步修改示例与校验规则。
3. 为引文增加来源路径、行号及内容哈希。证据优先来自题意、思路、证明和引用代码，不能用已有 `pre/common.reason` 反过来证明关系成立。
4. 允许 worker 读取引用源码及 `problem.md`；出现多解法时，指出 B 的哪一种解法复用了 A 的步骤。摘录不完整时补读原文，不能仅凭材料前 4000 字符作最终结论。
5. 将 `grounding` 定义为证据定位与结构约束检查。语义成立仍由 worker 和独立审核判断，不使用“机械自证”表述。

验收条件：正例、通用框架反例、同难度反例、引用不存在、仅引用关系理由等案例都有明确预期，不能只验证 JSON 格式正确。

### 2.2 候选生成提前消耗名额，难度口径也不统一

对应原计划：§1、§2、§5、§6。

现有 [pre_batch.py](../../scripts/problem-analysis-tools/relation_batch/pre_batch.py) 的 `cmd_candidates()` 会在候选尚未经过判断时执行 `counts[kb] += 1`。达到上限后，后续候选不再入选。即使前几对全部被拒绝，后面的强前置也不会获得判断机会。

该脚本的 `TIERS` 还把“普及”和“普及/提高-”合并为同级，把“普及+/提高”和“提高”合并为同级；[lib/problem.js](../../lib/problem.js) 则分别排序。脚本默认允许难度差为 0，原计划严格口径要求难度差大于 0。

建议修订：

- 候选生成只处理身份、标签、难度窗口和去重，不消耗每题 3 条写入名额。
- 指定唯一难度秩来源，导出共享配置或添加一致性校验，禁止两套映射独立漂移。
- 将候选难度条件明确为 `1 <= rank(B) - rank(A) <= 2`，并把未知难度排除原因落盘。
- 将辅助标签排除表写成完整配置，不能使用“python/模拟/usaco/思维…”作为可执行规则。
- 重新生成候选规模、专题大小和费用估算，给出复现命令与配置哈希；原计划的 100,596 对暂不作为已验证的严格口径规模。
- 同一候选固定唯一所属专题，其余标签只作为元数据。共现标签拆分必须保留“无次级标签”的剩余分片，并验证子分片并集等于父集合、互不重复。

验收条件：构造同一 B 至少 4 个候选、前三个拒绝而第四个接受的案例，第四个仍能进入判断并参与仲裁；所有去重后的候选恰好分配一次。

### 2.3 全局最强 3 条与逐专题提交之间缺少仲裁协议

对应原计划：§6、§9、§12。

当前只规定“按 step 分数 + confidence 排序”，没有定义 `step` 指哪一个字段、排序规则、并列处理，以及后续专题出现更强候选时如何替换已提交关系。历史关系直到 M4 才重审，也会提前占据名额。

建议采用统一候选池、逐专题重新计算的方式：

1. 为每个 B 维护全局候选池，包含已审核通过的历史关系、本批候选、当前生效关系和延后候选。
2. 固定排序字段及版本，例如先按独立审核的复用强度等级，再按 worker confidence、`step_reused` 分数，最后按稳定的题对 key 打破并列。具体强度等级需在校准集上定义，不把模型概率直接等同于教学质量。
3. 每完成一个专题，对受影响 B 重新计算当前已评估集合的前 3 条。后来的强候选可以替换本批较弱关系，替换动作进入台账。
4. 对尚未重审的历史关系保留占位；先完成受影响 B 的历史关系重审，再决定新增和替换。证据不足的历史关系不自动删除。
5. 提交说明同时列出新增、替换、删除和延后数量，不再假定每个专题只新增。

这里保证的是“截至当前已评估集合中最强的 3 条”。只有计划范围内候选全部评估完毕后，才能描述为该范围内的最终结果；预算中止时不能宣称全仓最优。

验收条件：不同专题执行顺序得到相同最终选择；分数并列有稳定结果；替换可追溯、可恢复，且不会删除未经重审的历史关系。

### 2.4 历史重审需要独立模式和撤销格式

对应原计划：§4③、§10、§12。

新增机检要求“该有向边尚不存在”，历史重审对象却必然已经存在，直接共用会误判。原计划的撤销协议仅覆盖本批新增项，不能完整恢复历史项删除和 reason 改写。

建议修订：

- 增加明确的 `add` 与 `recheck` 模式；后者验证原条目仍存在且未被外部修改，不执行新增去重拒绝逻辑。
- 103 条已有关系全部进入 worker 阅读与复核。Jev 可作辅助信号，但不能因为初筛失败就自动删除历史项。
- 区分 `keep`、`update-reason`、`remove`、`unresolved`。不符合本次范围、证据不足与关系本身错误应分别记录。
- reason 修改保存旧值、新值；删除保存完整旧条目及必要的顺序信息；恢复时只操作对应条目，避免覆盖后续人工编辑。
- 对原有关系的删除和实质性改写做独立审核。31 条不符合严格难度递增的关系单独列出新旧口径差异。

验收条件：原项存在不会导致重审自动失败；历史 reason 更新和删除都可定点恢复；关系已被人工改写时报告冲突，不能盲目回滚。

### 2.5 预算硬顶必须在请求前执行

对应原计划：§2、§7、§11、§15。

“费用触及 5 美元后，在当前专题边界暂停”允许超支，不能称为硬顶。原计划也没有说明 20% 余量是否包含在上限内，以及校准、重试和结果未知的请求如何计费。

建议规则：

```text
已结算费用 + 在途预留费用 + 下一请求费用上界 <= 本期预算
```

预算预留必须由统一计费器原子完成，并覆盖 Jev 初筛、校准、重试及其他属于该预算范围的调用。建议将 20% 余量包含在 5 美元内，常规请求先按 4 美元规划；余量释放规则单独记录。

额度不足时立即停止新请求，已发出的请求完成后结算并保存断点，不要求先完成当前专题。网络超时而服务端是否计费未知时保留预留，不直接按零费用释放；无法确定价格或请求费用上界时，不自动发起付费调用。

分别记录 Jev、worker、主 agent 和审核 agent 的用量。历史报告显示某次 worker 为零费用，并不能保证后续长期免费。执行前核实当前账户计费范围；本文不重新确认供应商价格。

验收条件：并发抢占剩余额度、超时、重试、恢复进程等情况下，预算预留都不越界，且同一次预留不会被重复使用。

### 2.6 并发结果与写入恢复缺少事务约定

对应原计划：§4②、§7、§10、§13。

共享追加 `worker-results.jsonl` 没有定义唯一写入者或锁；专题级 `state.json` 不足以处理旧 worker 迟到、重复返回、文件已改而台账未落盘等情况。现有 `cmd_write()` 的顺序也是先写题目文件，再追加台账，需要在新 `apply` 中补齐恢复协议。

建议修订：

- worker 只写自己的 `results/<task-id>/<attempt-id>.json`，不改题目和共享状态。主进程验证后统一汇总。
- 每个结果绑定批次、题对、分配代次、两题证据哈希、材料版本、提示词版本和规则版本。旧代次结果保留作证据，但不能覆盖已生效的新结果。
- 状态至少区分待派发、运行中、待校验、待审核、待写入、已生效、拒绝、延后、冲突、证据过期和错误；专题状态从题对状态汇总。
- `apply` 是唯一题目写入者和 Git 操作者。同一 B 的多项变更合并成一次写入。
- 写入前先持久化操作意图及预期前后哈希，再写临时文件并原子替换，最后记录完成；重启时根据文件实际哈希与操作意图恢复。
- 同时校验 A、B 的判断证据是否过期。B 中由本批增加关系引起的 frontmatter 变化，应与题解证据变化区分，避免正常批次写入使所有旧判断失效。
- 对不遵守批次锁的人工编辑仍做冲突检查；原子替换本身不能证明没有外部并发修改。

验收条件：在意图落盘前后、题目替换前后、完成记录前后分别模拟中断；恢复后不丢台账、不重复写边、不覆盖人工改动。

### 2.7 阶段闸门与抽检返修存在歧义

对应原计划：§5、§8、§15、最终决策 16。

§5 要求首专题自动验收后继续，§15 和最终决策要求暂停等用户确认。按最后的决策，应统一为 M1 报告交付后暂停。

抽检还缺少小样本数量、发生时点和返修范围。发现抽检错误后只重跑 doubtful 与被抽中的失败项，会留下未抽中的同类错误。

建议协议：

1. M1 对拟写入的 `accept` 全查；后续专题建议抽检数为 `min(N, max(30, ceil(0.1 * N)))`，固定种子并记录抽样清单。这是建议值，不冒充原计划已确认要求。
2. 抽检在正式写入前进行；所有 doubtful 独立复核，没有形成最终接受结论的不得写入。
3. 发现任何错误即暂停该专题写入，修正错误并分析是否存在同类规则问题。
4. 抽检错误率超过 10%，重审该专题全部 accept；修正规则后重新验收，不能仅修抽中的几条再放行。
5. 连续两个专题超阈值时停止派发，保存现场和原因。若已经发生部分写入，根据台账处理受影响操作。
6. 为“通过率低于 3%”明确分母，建议同时报告初筛通过率、worker 接受率和最终新增率，不混为一个比例。

验收条件：M1 完成不会自动进入 M2；小专题不会因向下取整而零抽检；失败专题的未抽中 accept 不会绕过返修。

### 2.8 产量和工期估算缺少成立条件

对应原计划：§0、§2、最终决策 15。

每题最多 3 条时，1762 道题即使全部可作接收端，总量也最多 `1762 × 3 = 5286` 条。按严格难度递增规则，459 道最低难度题没有可用的更低难度前置，因此进一步得到宽松上界：

```text
(1762 - 459) × 3 = 3909 条
```

这个上界假设关系限于本次有难度分级的题目集合，是最终全部符合新规则的图的上界，不是实际可达到的产量；若仍保留不符合新规则的历史边，需要单独统计。原计划的 7000 条预期不成立。

[b002 工作记录](../../relation-batches/b002-erfen-pre-2026-10-02/work-record.md) 中的 17/263 是旧版阈值筛选结果，后续还有审核、删除、恢复和宽松口径处置，不能视为本次严格语义的实测通过率。

建议先把 100～130 小时标为待试点验证的估计。工期应包含阅读与判断、进程启动退出、完成发现延迟、结果校验、审核、重试和提交。若仅每 3～5 分钟收回任务并补位，一题一个全新 pi 的吞吐可能明显低于估计。

保留原定 8～10 个 worker 和一对一个任务，区分“完成即补位”与“定期故障巡检”。M1 记录任务耗时中位数和 P95、槽位空闲时间、审核积压及重试率，再按实际吞吐外推。

验收条件：所有成本和产量表都注明分母、范围及数据来源；区分实测值、模型估计和数学上界，不再把推测统一标为“实测数据”。

## 3. 建议的执行顺序

以下调整保留三层判断、单侧存储、严格口径、固定 worker 池及按专题提交的方向，补齐试点与长期运行的边界。

| 阶段 | 建议内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0a：冻结规格 | 统一难度、标签配置、候选归属、schema、仲裁、预算和状态协议 | 每个冲突只有一种明确处理规则 |
| M0b：离线实现 | 用固定样本和模拟模型响应实现候选、校验、仲裁、写入及恢复 | §4 的关键检查全部通过 |
| M1：有界试点 | 建议从最大专题选不超过 200 个候选，兼顾子类与边界案例；拟写入 accept 全查 | 报告质量、费用和吞吐，交付后暂停 |
| M2：扩展大专题 | 获得继续指令后按分片推进，受影响 B 的历史关系先重审 | 每片独立验收、统一仲裁、留档和提交 |
| M3：其余专题 | 延续相同规则；预算不足可在专题中途暂停 | 范围内候选都有状态，不把未执行计为拒绝 |
| M4：历史收尾 | 补齐尚未受影响的历史关系重审与 unresolved 报告 | 103 条均有可追溯处置或待处理原因 |
| M5：全仓交付 | 关系校验、内容索引检查、无环、上限、改动范围和台账一致性 | 报告实际完成范围及残余风险 |

“不超过 200 个候选”是本次审核提出的试点建议，替代整块最大标签直接作为试点的做法。试点不能据单一专题推断全仓召回率。可另设少量人工核对的正负校准题对，并抽查初筛拒绝项，观察截断材料与阈值带来的漏判。

启动环境检查应继承 [批次 skill](../../.agents/skills/rbook-problem-batch-launch/SKILL.md)：要求 `HERDR_ENV=1`，核对本机 Herdr/pi 参数和准确模型标识。主 agent 模型与审核模型需明确映射，不能保留无法执行的占位符。本文没有执行 Herdr 环境检查或启动操作。

原计划的 3～5 分钟巡检、8 分钟无进展规则与 [监督协议](../../.agents/skills/rbook-problem-batch-launch/references/supervision.md) 的 3 分钟、5 分钟不同，任务书应明确采用哪一组及其优先级，避免执行者同时遵循两套计时规则。

## 4. M0 必须交付的验证清单

这些检查用于验证长期自动运行中的实际故障场景，不要求为单纯 Markdown 变更增加测试。

- [ ] 两套难度秩不会漂移，同难度候选不会进入严格新增管线。
- [ ] 候选阶段不占用写入名额；第四个候选不会因前三个被拒绝而漏掉。
- [ ] 全局去重和专题拆分不重复、不丢失；无次级标签有明确归属。
- [ ] worker 输出符合正式 schema，身份以 frontmatter 为准，证据可定位。
- [ ] 关键词命中不会自动将语义未通过的关系升级为 accept。
- [ ] 专题执行顺序变化不改变最终仲裁结果；已有关系占位处理明确。
- [ ] 历史重审区分保留、改理由、删除和未决，操作均可追溯恢复。
- [ ] 并发预算预留、重试和未知计费状态不会绕过硬顶。
- [ ] 重复返回和旧代次结果不会覆盖新结果，重复恢复不会重复写入。
- [ ] 写入各阶段中断后可恢复，文件与台账最终一致。
- [ ] A 或 B 的证据变化会失效重审；人工编辑冲突不会被自动覆盖。
- [ ] 正文、源码和无关 frontmatter 不变，只有约定的关系项与 `updated` 可变。
- [ ] 抽检失败会阻止写入，M1 完成会阻止自动扩量。
- [ ] 状态与台账文件的备份、版本控制范围明确；工具改动、关系提交和运行记录的留存职责明确。

建议保留原有 `check_relations.py --all`，并补充 `npm run check:content` 作为实际内容索引兼容性检查。后者需要先具备项目依赖环境；未运行时应明确记录，不能以关系字段检查代替。

## 5. M1 报告最低内容

`canary-report.md` 至少记录以下信息，供决定是否扩量：

- 代码版本、工作区基线、模型、模板、标签配置和难度配置版本。
- 候选总数、初筛通过与拒绝、worker accept/reject/doubtful、最终接受、新增、替换、延后和错误数量。
- 每项比例的分母；没有新增关系时不能只以零错误宣称试点通过。
- 原始判断与独立审核结论分别留存，列出被纠正的正反例。
- 全部拟写入 accept 的复核结果、doubtful 处置及初筛拒绝项的抽查结果。
- 用量、已结算费用、在途和未知费用预留、剩余预算。
- 任务耗时中位数/P95、槽位空闲、审核吞吐、重试和恢复次数。
- 文件变化、验证命令与结果、台账一致性、撤销演练结果。
- 尚未完成的候选、受影响历史关系的处理状态、不能据此推广的结论。
- 下一阶段范围与预计费用，以及当前已暂停的明确状态。

## 6. 审核建议的落实边界

原方案最值得保留的是：严格前置口径、允许没有关系、低置信度不直接写入、单侧存储、主进程统一提交、完整记录和定点恢复。

应优先修正的则是：判据与例子一致性、候选不提前限额、全局仲裁、预算预留和可恢复写入。仅改文案中的数字与闸门不足以支撑长期运行，这些规则需要成为 M0 的实际行为及验收案例。

本次交付为独立审核文档。原计划、脚本、题目关系和批次运行状态均未因本文而修改。
