## 0. 目标与口径

**目标**：为全仓有难度分级的题目补齐**强前置关系 `pre`**，使其可用于题目关系图的学习路径。

**口径（严格）**：`pre` 边 `A → B` 只在同时满足三条时写入：

1. **台阶性**：A 是相对简洁的模板/基础题，B 在 A 的基础上叠加额外流程。
2. **真实复用**：A 教过的**具体**判定、状态设计或关键观察，确实是 B 解法中**实际使用的一步**。
   —— 仅共享「都用二分答案」「都属 DP」这类通用框架**不算**。
3. **方向正确**：A 更基础，B 更难更综合（难度秩 A < B）。

**明确排除**：同难度孪生题（应写 `common`）、B 的主要难度是 A 未教的新范式且该范式构成 B 的
主要门槛、方向颠倒。

**口径代价（已知并接受）**：严格口径的产出量远低于先前的乐观估计。

**产量上界（数学）**：每题 `pre` 最多 3 条，且本次严格口径要求 `rank(A) < rank(B)`（Δrank ≥ 1），
入门难度题（459 道）没有可用的更低难度前置，因此：

```text
(有难度分级题数 1762 - 入门题 459) × 3 = 3909 条   ← 数学上界，不是实际可达产量
```

**实测 / 估计 / 上界必须区分**：

| 口径 | 数值 | 类型 |
| --- | --- | --- |
| 数学上界 | 3909 条 `pre` 边 | 推导（仅在关系限于本次题集时成立） |
| 修正后候选对 | 50,519 对（Δ∈[1,2]、非辅助标签、全局去重） | 实测 |
| Jev 初筛成本/工时 | $5.1 / 并发 24 下约 1.2 小时 | 实测吞吐 + 估算 |
| worker 通过率 | 未知（b002 的 17/263 是旧口径阈值结果，**不可作为本口径实测通过率**） | 待试点 |
| 预计新增 | 待 M1 试点后外推，不预先承诺 | 未定 |

## 3. 编排形态（rbook-problem-batch-launch）

沿用 skill 的 workspace / 主 agent / worker tab 三层形态，但**派发单元从「一题」改为「一个候选对」**
（pre 是批量判定任务，无题解写作内容）。

一个长期批次 = 一个 workspace：

```
herdr workspace create --cwd <pcs2-problem-relation> --label pre-full-<yyyymm> --no-focus
  ├─ 根 tab：主 agent（常驻、带会话、可恢复监督）
  ├─ worker tab ×N（N = 并发 8~10）：名字 = 当前候选对标识 <a-oj-a-pid>__<b-pid>
  └─ 审核 tab ×1：独立审核 agent（抽检与 doubtful 复核，复用同一 tab）
```

- worker 一律 `pi --no-session --provider small-sheep --model deepseek-v4.1-flash`。
- 主 agent 用当前会话模型（`--model <派发器模型>`）。
- 一个 worker tab 派完一个候选对后：主 agent 收回结果 → 结束旧 pi → 确认 pane 回空闲 →
  **原 tab 改名 + 启动全新 pi** 派下一对（skill 的 tab 复用约定）。
- 子 agent 不得创建下级 agent；主 agent → worker 两层。
- task 派发不使用长 `--wait`；用 `herdr agent read` 轮询巡检。

## 4. 三层判断管线（严格口径的落地机制）

```
候选对 (10 万)
   │  ① Jev 初筛（脚本，并发 4~6，成本 ≈$11）
   ▼
短名单 (2.5~3.5 万)  ── 未通过者记 rejected，不进入下一步
   │  ② worker agent 严格裁定 + 写 reason（并发 8~10）
   ▼
结构化裁定 (JSONL)
   │  ③ 脚本接地机检（零成本，可批量自证）
   ▼
写入候选 → 全局上限仲裁 → frontmatter 写入 → commit
```

### ① Jev 初筛（召回优先，key 池并发）

- **凭据池**：10 个官方 API key（本地 `~/.typesafe/jev-lgp888.keys`，权限 600；额度合计 **$50**）。
  端点仍为 `api.typesafe.ai/v1/systemone`，模型 `jev-1.13.0`；`jev.lgp888.xyz` 只是登录/查余额网页，
  **不是**调用端点（实测 `/v1/systemone` 返回 404）。
- **并发**：默认 **并发 24**（实测 10 key 并发全成功、60 并发全成功，单请求 2s 量级）；
  脚本按 round-robin 分配 key，单 key 连续 429 时退避并切换下一个 key。
- **实测吞吐**：修正后 50,519 对（Δ∈[1,2]）≈ **1.2 小时 / $5.1**（并发 24）；
  旧口径 10.06 万对约 2.3 小时 / $10.1（已废弃，仅作对照）。
- 输入：两题材料摘录（`materials/<oj>__<pid>.md`，各 ≤4000 字符）。
- 模板：`questions-pre-v6.json`（在 v5 之上新增**可机检的复用问题**）：
  - `A_is_step_to_B`（Noul）：A 是否为 B 提供入门台阶。
  - `B_harder_than_A`（Noul）：B 是否更难。
  - `same_core_model`（Noul）：核心模型是否同族。
  - `step_reused`（Noul，**新增**）：B 的解法中是否有一处步骤可以直接用 A 教的判定/观察写出。
- 初筛通过条件（召回优先，阈值由首专题校准，方向为**放宽**）：
  `A_is_step_to_B ≥ 0.5 且 B_harder_than_A ≥ 0.4 且 step_reused ≥ 0.3`
- 记录：原始返回落盘 `raw/`，判定结果写 `prescreen-results.jsonl`，可断点续跑。

### ② worker 严格裁定（真正需要阅读能力的一层）

**单元**：一个候选对。

**正例与反例（已核对原文，代替原先错误的示例）**：

| 类型 | 题对 | 难度秩（前端权威序） | 判定 |
| --- | --- | --- | --- |
| ✅ 强前置正例 | `noi_openjudge/ch0111-02`(入门) → `luogu/P1024`(普及/提高-) | r0 → r3 | A 教「变号区间二分求零点」，B 在扫描根区间后逐区间复用同一二分 |
| ✅ 强前置正例 | `OpenJ_Bailian/4135`(普及/提高-) → `luogu/P1083`(普及+/提高) | r3 → r5 | A 教「二分答案 + 线性 check」，B 把 check 换成差分数组 |
| ✅ 强前置正例 | `luogu/P1873`(普及/提高-) → `luogu/P1419`(普及+/提高) | r3 → r5 | A 教二分单调性与 check，B 扩到实数域 + 前缀和/单调队列 |
| ❌ 通用框架反例 | `luogu/P1873` → `OpenJ_Bailian/4135` | r3 → r3（Δ=0） | 同难度同型题，应写入 `common` **而非** `pre`（仓库历史例外，见 §12） |
| ❌ 跨域反例 | `luogu/P1163` → `luogu/P1948` | r3 → r5 | A 为实数二分+逐月模拟，B 核心为 0-1 BFS，A 未教 B 的主要难点（b002 审核 p13 即此类） |
| ❌ 同族反例 | `POJ/1144` → `OpenJ_Bailian/3091` | r3 → r5 | 同难度邻位但 A 的割点判定确是 B 的步骤 → 属**合格**；用作“同族可例外”的对照（A 与 B 仅相差一级时不由难度单独决定） |

**任务书要点**（写入 `worker-brief-template.md`，派发时填入具体题对）：

- 读 `problems/<a-oj>/<a-pid>/index.md`、`problems/<b-oj>/<b-pid>/index.md` 与两份材料，**必须读原文**；
  需要时读引用源码与 `problem.md`；出现多解法时指出 B 的**哪一种解法**复用了 A 的步骤。
  manifest 中的材料摘录截断在 4000 字符，**不足以作最终结论时必须补读原文全文**。
- 按 §0 三条判定，输出结构化 JSON（见下）。
- **证据字段与 reason 分工**（审核 §2.1 修）：
  - `quote_a` / `quote_b`：两题原文逐字片段（各 ≤20 字），放在**证据字段**，并附来源路径与行号
    （`src_a`/`src_b`，形如 `problems/luogu/P1873/index.md:37`）。
  - `reason`：表达**具体迁移关系**（一句话，必须含 `a_step` 或 `b_use` 的关键词），
    **不要求内嵌引文**（与校验规则一致）。
  - 证据不得引用已有的 `pre`/`common.reason` 反推关系成立。
- 允许的裁定值：`accept` / `reject` / `doubtful`（证据不足或边界）。**不强迫二选一**。

**worker 输出 schema**（一行一条，写入**自己的**结果文件，见 §7.1）：

```json
{
  "key": "luogu/P1873->OpenJ_Bailian/4135",
  "verdict": "reject",
  "reject_reason": "same-difficulty-twin",
  "a_step": "二分答案的单调性判定 check",
  "b_use": "划分型二分中判断能否不超过 M 段装下",
  "quote_a": "寻找最大可行高度",
  "src_a": "problems/luogu/P1873/index.md:44",
  "quote_b": "判断是否能将数组划分成不超过 M 段",
  "src_b": "problems/OpenJ_Bailian/4135/index.md:58",
  "reason": "（reject 时可空）",
  "confidence": "high",
  "task_id": "<batch>-<shard>-<seq>",
  "attempt": 1,
  "model": "small-sheep/deepseek-v4.1-flash"
}
```

`reject_reason` 取枚举：`same-difficulty-twin`（同难度孪生，应写 common）、`b-difficulty-elsewhere`
（B 的主要难度是 A 未教的新范式）、`no-reuse`（无真实复用）、`direction-wrong`（方向颠倒）、
`insufficient-evidence`（材料不足）、`self-or-duplicate`（自引用或已存在）。

### ③ 脚本接地机检（`grounding`）

**定位**：证据定位与结构约束检查（审核 §2.1：不使用“机械自证”表述）。
通过机检只说明引用可定位、结构约束成立；**语义是否成立仍由 worker 与独立审核判断**。

对每条 `accept`/`doubtful` 逐条校验，任一不过即降级为 `doubtful` 或 `reject`：

| 检查 | 规则 |
| --- | --- |
| 引文可定位 | `quote_a` 出现在 A 的 `index.md`/材料中；`quote_b` 出现在 B 中（允许去除空白差异） |
| 来源标注 | `src_a`/`src_b` 的路径存在且行号落在文件范围内 |
| 落点存在 | `a_step`/`b_use` 的关键词在对应题材料中出现（命中 ≥1 个关键词；中文无分词，采用双向子串匹配） |
| 方向 | `rank(A) < rank(B)`（按 `lib/problem.js` 与 `tag-config.json` 单源） |
| 难度窗口 | `1 <= Δrank <= 2`（§2.2 修正：同难度不再进 pre 管线） |
| 非重复 | 该有向边尚不存在（含反向 `B→A` 冲突检测）；`recheck` 模式例外，见 §12.1 |
| 上限 | 写入后 B 的 `pre` 数 ≤ 3（§6.1 仲裁） |
| 无环 | 预演写入后全仓 pre 图无环 |
| reason 形态 | 非纯模板句：必须包含 `a_step` 或 `b_use` 的关键词 |
| 动作保护 | 不改正文与代码；只允许关系字段与 `updated` 变化（写入后 `git diff` 校验） |

## 5. 分片与推进顺序

- **全局去重**：一个候选对只判一次（无论属于几个标签）；候选集合先在全仓范围生成并去重。
- **固定归属**：每个候选对**固定一个主专题**（按共享标签的文档序优先、非辅助标签优先），
  其余共同标签只作元数据，保证「去重后的候选恰好分配一次」。
- **专题**：≥3 题的标签（辅助标签不作专题来源）；规模与拆分阈值取 `tag-config.json`。
- **大标签自动拆分**：题数 > 150 或候选对 > 8000 的标签，按「主标签 + 次高频共现标签」拆子类
  （如 动态规划×背包、字符串×哈希、数学×数论），子类各自独立跑闭环。
  **必须保留「无次级标签」的剩余分片**，并校验子分片并集 = 父集合且互不重叠。
- **顺序**：按候选对数量从大到小推进（大专题先做，早期暴露机制问题）；
  因 §6.1 采用「截至已评估集合最强」的仲裁，**专题顺序不改变最终选边结果**。
- **起点闸门**：M1 有界试点（≤200 个候选，见 §15）跑完**暂停**，交付 `canary-report.md`；
  用户确认后才进入 M2。（原文「自动通过即继续」已按审核 §2.7 更正为暂停。）

## 6. 写入规则

| 规则 | 内容 |
| --- | --- |
| 存储 | **单侧**：只写 B（较难的一题）的 frontmatter `pre` 项（与既有 103 条惯例一致） |
| 字段 | `- oj: "..."` / `problem_id: "..."` / `reason: "..."`（沿用 `oj-problem-relation-writer`） |
| 字段顺序 | `pre` 在 `categories` 后、`common`/`source` 前（`add_relation_item` 已实现） |
| 同步 | 改动的题目 `updated` 刷为批次写入时间 |
| 幂等 | 已存在的有向边不重复写入；反向已存在 `pre` 时报 `conflict`，不自动改方向 |
| 本体保护 | 只改 frontmatter，正文与代码零改动（写入后 `git diff` 校验 body 全等） |
| 单一写入者 | `apply` 是唯一题目写入者与 Git 操作者（§7.1） |

### 6.1 全局候选池与仲裁（审核 §2.3）

**问题**：上限 3 条 × 按专题逐个写入时，先做的专题会占满名额，后发现的强前置无法进入。

**协议**：

1. 为每个 B 维护**全局候选池**，含四类：已审核通过的历史关系、本批已评估通过的候选、
   当前生效关系、延后候选（`deferred`）。
2. 固定排序字段与版本（写入 `state.json` 的 `arbitration_version`）：
   - 第一键：独立审核的**复用强度等级**（`strong` / `template-level`，由 worker 与审核定级，
     不把模型概率直接当质量）；
   - 第二键：worker `confidence`；
   - 第三键：Jev 初筛的 `step_reused` / `A_is_step_to_B` 分数（降序）；
   - 第四键：稳定的题对 key 字符串（升序）打破并列。
3. 每完成一个专题，**对该专题涉及的 B 重新计算前 3 条**（不是只追加）。
   后来的强候选可以**替换本批较弱关系**，替换动作写台账（`action: replace-pre`）。
4. 尚未重审的历史关系**先占位**；重审后判定不合格时，该 B 空出的名额再交给候选池。
   证据不足的历史关系不自动删除。
5. 提交说明分别列出 **新增 / 替换 / 删除 / 延后** 数量。
6. 口径声明：这是「截至当前已评估集合中最强的 3 条」；
   只有计划范围内候选全部评估完后，才能描述为该范围内的最终结果；预算中止时不得宣称全仓最优。

**验收**：不同专题执行顺序得到相同最终选择；并列有稳定结果；替换可追溯可恢复；
不删除未经重审的历史关系。

## 7. 监督与守护（长期运行）

| 项 | 规则 |
| --- | --- |
| 巡检 | 主 agent 每 **3 分钟（180 秒）** `herdr agent read` 全 worker（对齐 `supervision.md`） |
| 无进展 | 单 worker **5 分钟（300 秒）**无有效活动 → 读现场 → 指导或重启；等待验收/等待指令不算卡死；同一候选对最多 **2 次**自动重启（对齐 `supervision.md`） |
| 两套计时冲突 | **`supervision.md` 优先**；本方案不再单独规定 3~5 / 8 分钟（审核 §3） |
| 完成即补位 | 与定期故障巡检分开：收到完成即回收并派下一对，不等下一个巡检周期 |
| 失败分流 | 401/403 → 停止该 worker 并报主 agent；429/限流 → 退避后重试（记 `rate-limited`）；上下文过长 → 换 worker |
| 断点 | 每个候选对结果落盘后立即更新 `state.json`；崩溃后 `resume` 只重跑未完成项 |
| 无人值守 | 允许夜间继续；异常累计时停止派新任务并在晨间汇总，不静默乱跑 |
| 资源边界 | 不关 tab 回收 worker、不操作其他批次、不 `herdr server stop`、不杀 Herdr 主进程 |
| 配额 | 主 agent 每小时汇报一次用量；Jev / worker / 主 agent / 审核 agent 分别计数 |

### 7.1 并发结果与写入恢复（审核 §2.6，降价采纳）

审核要求数据库级事务（意图日志 + 临时文件 + 原子替换）。本方案按 Markdown + Git 的实际风险
**降价采纳**为下列六条，**不做原子替换与意图日志**：

1. **结果文件隔离**：worker 只写 `results/<task-id>/<attempt>.json`，**不写共享 JSONL**，
   不碰题目文件和 `state.json`。
2. **主进程统一汇总**：主 agent（或 `apply`）验证后按 `task-id` 升序合并成 `worker-results.jsonl`；
   同一 `task-id` 只采纳最新有效 `attempt`，旧代次保留作证据但不覆盖。
3. **结果绑定版本**：每条结果带 `task_id`/`attempt`/两题证据 hash/材料版本/提示词版本/规则版本；
   证据 hash 变化时标记 `stale` 需重跑（**本批自己造成的 frontmatter 变化不算证据变化**，
   审核 §2.6 的区分要求）。
4. **单一写入者**：`apply` 是唯一改题目与执行 Git 的人；同一 B 的多项变更**合并为一次写入**。
5. **写入前校验 hash**：比对 `pre-manifest.json` 基线 hash；不一致（人工编辑过）则跳过该题并记
   `stale-external`，不覆盖。
6. **恢复手段 = Git**：流程为「算 hash → 写文件 → 立即追加台账 → 每专题 commit」；
   中断时用 `git status` + 台账对照恢复，保证不重复写边、不丢已写入项。
   （审核 §2.6 要求的原子替换视为过度设计，理由：Markdown 单文件写入 + 按专题 commit 已可恢复。）

**验收**：模拟「写文件前后中断」恢复后不重复写边、不覆盖人工改动；旧 attempt 不覆盖新结果。

## 8. 验收与抽检

1. **机检全量**（零成本）：§4③ 全部规则。
2. **抽检数量**：`min(N, max(30, ceil(0.1 * N)))`，固定随机种子并落盘抽样清单（审核 §2.7）；
   M1 试点**全查**拟写入的 accept。
3. **抽检时机**：在**正式写入前**进行；`doubtful` 全部独立复核，没有形成接受结论的**不得写入**。
4. **错误处理**：发现任何错误即**暂停该专题写入**，修正并分析是否存在同类规则问题；
   抽检错误率 > 10% → **重审该专题全部 accept**（不能只修抽中的几条），修正规则后重新验收。
5. **连续失败**：连续 2 个专题超阈值 → 停止派发并保存现场；已部分写入的按台账处理。
6. **比例分母**（审核 §2.7）：分别报告 **初筛通过率**（通过/候选）、**worker 接受率**（accept/初筛通过）、
   **最终新增率**（新增/候选），不混为一个数字；无新增关系时不得以「零错误」宣称试点通过。
7. **提交前**：`check_relations.py --all` + `npm run check:content`（需项目依赖）
   + body 未改动 + 无环 + 上限合规 + 台账一致。

## 11. 预算

- **额度池**：10 个官方 key，合计 **$50**（`~/.typesafe/jev-lgp888.keys`，权限 600）。
- 全量初筛实测估算：**约 121M tok ≈ $5.1**（修正后候选 50,519 对 × 约 2.4k tok）。
- **逐请求计费与上界估算**（审核 §2.5）：预算器在每次请求前检查
  `已结算 + 在途预留 + 本次请求上界 <= 本期上限`；上界按 `state` 字符数估算 token × 单价。
  这是**降价版**：不做原子预留，但保证不越界——并发下由单一预算器进程串行记账。
- **暂停线**：累计估算费用达 **$45（额度 90%）** 时，在**当前请求边界**立即停止新请求
  （不要求完成当前专题），已发出的请求完成后结算并保存断点。
- 无法确定价格或请求费用上界时**不发起付费调用**。网络超时且服务端是否计费未知时，
  保留该请求的预留额，不按零费用释放（审核 §2.5）。
- 分别记录 Jev / worker / 主 agent / 审核 agent 用量；**worker 历史报告显示零费用不代表长期免费**，
  执行前需核实当前账户计费范围。
- 20% 余量包含在 $50 内：常规规划按 **$40** 使用，其余为重试与返修余量。

### 12.1 `recheck` 模式（审核 §2.4）

新增机检要求「该有向边尚不存在」与历史重审对象必然已存在**冲突**，因此必须区分两种模式：

| 模式 | 行为 |
| --- | --- |
| `add` | 现有逻辑：非重复检查（含反向冲突）生效 |
| `recheck` | **不执行新增去重拒绝**；改为验证「原条目仍存在」且「未被外部修改」（比对基线 hash） |

**四种处置**（不合并）：

- `keep`：关系成立且 reason 合格。
- `update-reason`：关系成立但 reason 为模板句或措辞不准；保存**旧值 + 新值**。
- `remove`：关系本身错误（方向颠倒、无真实复用、同难度孪生）；保存**完整旧条目**及顺序位置。
- `unresolved`：证据不足或材料缺失；保留原条目不动，记入报告等待人工或后续批次。

**约束**：

1. 103 条全部进入 worker 阅读与复核；Jev 只作辅助信号，**不因初筛失败自动删除历史项**。
2. reason 改写与删除**分别**保存旧值，恢复时只操作对应条目，不覆盖后续人工编辑。
3. 关系已被人工改写（hash 不符基线）时报告冲突，不盲目回滚。
4. 按前端权威难度序复核，本次已实测 **31 条不满足 `rank(A) < rank(B)`**
   （27 条 Δ=0、3 条 Δ=-1、1 条 Δ=-2）—— 单独列出新旧口径差异，不直接判错、不直接删除。
5. 历史关系的删除与实质改写**做独立审核**（审核 tab），不只靠 worker 自证。
