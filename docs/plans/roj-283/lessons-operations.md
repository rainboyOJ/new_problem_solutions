## T4. `pcs2_queue.py claim <pid>` **不接受 pid** —— 按 `--count` 批量抓

**现象**（2026-10-08）：父会话想把在飞的 4 道标为 claimed：

```bash
for p in 5020 5021 5022 5023; do
  python3 .../pcs2_queue.py claim $p --queue .tmp/roj283-queue.jsonl --worker batch6
done
```

结果**标了 40 道**（`D:9 C1:24 C2:5 A:2`），而不是 4 道。

**根因**：`cmd_claim` 的实现是

```python
picked = pool[: args.count]      # ← pool 由 cohort/status 筛选得到，与位置参数无关
```

`claim` 的**位置参数 `pid` 被忽略**，真正起作用的是 `--count`（默认 10）。
我循环调 4 次 ⇒ 每次抓 10 道 ⇒ **4 × 10 = 40**。

**修复方式**：直接用脚本改 JSONL（精确、可逆），不要用 `claim` 做单题标记：

```python
KEEP = {'5020','5021','5022','5023'}
for r in rows:
    if r['pid'] in KEEP: r['status']='claimed'; r['worker']='batch6'
    elif r['status']=='claimed': r['status']='pending'; r['worker']=None
```

**教训（可推广）**：**循环调用一个工具之前，先确认它的参数语义**。
「参数名像 pid」不等于「支持指定 pid」。
本次能无损还原，是因为 `claimed` 之前的旧状态恰好都是 `pending` ——
如果我把 `done` 的题目也误改了，就没有旧状态可还原了。

**附带**：`pcs2_queue.py` 的默认队列是 `.tmp/pcs2-queue.jsonl`，
而 `accept.py` 用的是 `.tmp/roj283-queue.jsonl` —— **必须显式传 `--queue`**，
否则 `stats` 会报 `total: 0`（看不见任何待办）。

## T5. 「遵循规范」不得写成「正确性要求」——文档偏差的一个新类别

### 现象（2026-10-08，`5028`《阶乘和》）

题目 $1 \le n \le 10$，$S_{10} = 4{,}037{,}913 \ll 2^{31}-1$ ⇒ **`int` 完全够用**。

但仓库 skill `oj-cpp-competitive-style` 规定「**题目数据默认 `long long`**」，且
「⚠ 题面未指定时仍然按本 skill 写」。本题题面未指定类型 ⇒ 按规范应写 `ll`。

于是出现了这样的链条：

```
专家初稿 index.md： 「…因此不会发生溢出，使用普通的 int 即可」
worker 按 skill 改代码： int → ll
⇒ 文档与代码不一致（index.md 说 int，代码写 ll）
```

### ★ 危险的不是不一致本身，而是「修不一致时的措辞」

最省事的修法是**把文档改成「必须用 `ll`」** —— 但这会制造一个**更严重的错误**：

| 写法 | 问题 |
|---|---|
| 「使用普通的 `int` 即可」（原稿） | 与代码不一致 |
| 「**必须**用 `long long`，否则溢出」（错误的修法） | ❌ **事实错误** —— 数据范围内 `int` 逐点正确 |
| 「本题用 `int` 也确实能过；代码改成 `ll` 是**遵循仓库规范**而非修 bug」（正确） | ✅ |

### 判据：区分三类「改类型」的理由

| 理由 | 该怎么说 | 例 |
|---|---|---|
| **正确性**：不改就会 WA/溢出 | 「必须用 `ll`」 | 5021（$13!$ 起 `int` 溢出，且数据覆盖了 $n=13$） |
| **规范**：不改也对，但仓库约定如此 | 「**能过**，但按仓库规范用 `ll`」 | **5028**（数据范围内 `int`/`ll` 逐字节相同） |
| **风格**：纯个人偏好 | 不写进题解 | — |

**判据**：问一句「**保留原类型，真实数据会失败吗？**」
- 会 ⇒ 正确性问题，写「必须」
- 不会 ⇒ 规范问题，**必须同时写明「原类型也能过」**

### counterfactual 是锁定这个区别的唯一手段

`5028` 的 worker 用反事实把结论钉死了：

```
n = 1..10  →  int 版与 ll 版输出【逐字节完全相同（10/10）】
n = 13     →  ll: 6749977113  vs  int: -1839957479   ← 只有这里才分道扬镳
```

⇒ **数据范围内改类型没有修复任何真实点**。有了这张表，
「本题用 `int` 也确实能过」就不是客套话，而是**实测结论**。

### 推广

这条属于「文档偏差」的一个子类。R2 worker 的任务卡里已加入一项固定要求：

> 若你按 skill 改了实现（类型、写法），**请判断 `index.md` 的对应表述是否需要同步**，
> 并给出**带行号的可粘贴建议**；同时说明这是「正确性」还是「规范」问题。

R3 的专家据此修改 —— 比让专家自己发现偏差更省一轮。

## T6. 专家会**往题面里加词** —— 最隐蔽的文档错误

### 现象（2026-10-08，`5026`《末两位数》）

专家初稿 `index.md` 写：

> 「给定一个**非负**整数 $n$（$n < 2000$），求 $n$ 个 $1992$ 相乘的积的末两位数。」

而题面 `problem.md` 原文只有：

```
【题目描述】求 $n$ 个 $1992$ 的乘积的末两位数是多少？
【输入】    输入 $n$。
【提示】    对于所有数据：$n < 2000$。
```

⇒ **「非负」二字题面里没有，也没有任何下界**。是专家自己加的。

### 为什么这类错误特别危险

| | 一般错误 | 「加词」类错误 |
|---|---|---|
| 表现 | 结论错 | **结论可能对，但前提被篡改** |
| 读者感受 | 能通过验证发现 | **会以为那是题面的规定** |
| 影响 | 本题错 | **读者把虚构的约束带到别的题上** |

而且它**恰好掩盖了一个真实的开放问题**：本题题面**只给上界、未给下界**，
所以 $n=0$ 是否合法**是题目本身没定义的**。专家加「非负」二字，
等于**替题目做了一个它没做的决定**。

### 判据

**题面里没写的限定词，不得出现在题解的事实陈述中。** 具体：

| 想做 | 正确做法 |
|---|---|
| 补充一个看起来显然的约束 | ❌ 直接写进陈述<br>✅ 写「题面未给下界」+ 明确标注「若 $n=0$，按……约定」 |
| 简化题面的措辞 | ❌ 改写成「等价说法」<br>✅ 引用原句 |
| 推断数据的取值范围 | ✅ 写「数据实际取值集合 = …（**这是观测，不是题面**）」 |

### 检测手段

R2 worker 的任务卡里已有固定要求（源起 T5）：

> 若 `index.md` 对**题目本身的陈述**与 `problem.md` 原文有出入，
> 请指出**具体行号与原文**，并标注这是「题面要求」还是「作者推测」。

`5026` 的 worker 正是靠这条抓到了「非负」二字 —— **它不在它被要求检查的清单里，
是它在执行核对时顺手发现的**。这说明该职责应作为一项**常设检查**保留。

### 附：worker 同时交出了一个漂亮的旁证

> $\gcd(1992, 100) = 4$ ⇒ 真实答案**恒为 4 的倍数**；
> $n = 0$（输出 1）是**唯一**可能输出非 4 倍数的输入
> ⇒ 佐证 $n=0$ 不是测试点。

这类「用数学结构排除某个边界是不是测试点」的推理，
比「数据里没有这个点」强得多 —— 后者只说明现状，前者说明**为什么出题人不会选它**。

## T7. 专家的「兼容方案」可能比不兼容更有害 —— 跨语言舍入的实例

### 现象（2026-10-08，`5025`《数据统计》）

**背景**：题目要求输出平均值并「保留 3 位小数」。
专家在初稿里标了 `uncertain`，并**主动给出兼容方案**：

> 「C++ 与 Python 在四舍五入（尤其是恰好等于 $*.xx5$）的情形下是否完全一致」
> ……「若 worker 发现由于舍入差异造成的判题错误，
> 则 Python 需要手动使用 `Decimal` 和 `ROUND_HALF_UP` 来兼容 C++ 的输出结果。」

**这个建议听起来完全合理** —— 「四舍五入」的英文是 round-half-up，
所以用 `ROUND_HALF_UP` 去「对齐 C++」似乎是标准做法。

### 实测结果：该方案会引入 **50%** 的分歧

| 模型 | 与 C++ `printf` / Python f-string 的不符数（共 80,000 个精确平分点） |
|---|---|
| `Decimal(精确值) + ROUND_HALF_UP` | **40,000（50%）** ❌ |
| `Decimal(精确值) + ROUND_HALF_EVEN` | 16,002（20%） ❌ |
| **`double(S/n)` 按 round-half-even 格式化** | **0** ✅ |

### 根因：`printf` 不是「四舍五入」

C 的 `printf("%.3f")` 与 Python 的 f-string **都对二进制值做 `round-half-even`（平局取偶）**：

```c
printf("%.3f", 1.0/16);   // 0.0625  →  0.062   保留位 2 偶 → 舍
printf("%.3f", 3.0/16);   // 0.1875  →  0.188   保留位 7 奇 → 进
```

```python
f"{1/16:.3f}"   # '0.062'
f"{3/16:.3f}"   # '0.188'      ← 与 C++ 完全一致
Decimal('0.0625').quantize(Decimal('0.001'), ROUND_HALF_UP)   # 0.063  ← 与两者都不符
```

⇒ **「四舍五入」是日常语言的近似说法，不是 libc/CPython 的实现**。
基于错误的名字去写「兼容层」，就把本来一致的两种实现**改成了不一致**。

### 判据（可推广）

**当有人（包括专家）建议「加一层适配/兼容/转换」时，先回答这一个问题：**

> **不加这一层，会不会有问题？**

`5025` 的答案是不加就没问题（**5,050,100 组全空间穷举 0 分歧**）。
「加一层」的代价是引入 50% 分歧 —— **适配层的常见失败模式**：
它把「两边本来就一致」的情形**改成不一致**，因为适配层依据的是
**对某一侧行为的猜测**（这里是「printf 是四舍五入」），而不是实测。

### 与 T5/T6 的关系

| 编号 | 类别 | 例子 |
|---|---|---|
| T5 | **过度断言**：把规范说成正确性要求 | `5028` 的 `int` → `ll` |
| T6 | **无据添加**：往题面里加词 | `5026` 的「非负」 |
| **T7** | **错误补救**：为不存在的问题加适配层 | **`5025` 的 `Decimal + ROUND_HALF_UP`** |

三者都是「**事实陈述与依据不匹配**」，但 T7 的危害最大 —— 它**主动破坏本来正确的代码**。

### 附带：初稿里的一个「个案当通则」

专家初稿第 45 行写：

> 「标准舍入规则……且**当小数末尾正好为 5 时（如 0.1875），会被进位**（输出 0.188）」

把「$0.1875 \to 0.188$」当成通则 —— 而 $0.0625 \to 0.062$ 立刻反证。
这正是「只有一个样例就下结论」的典型；数据里**唯一**的平分点恰好是保留位为奇数的那种，
所以**一个反例都看不到**。⇒ **数据只有 1 个 tie 点时，不能据此断定舍入模式**
（worker 正是自己构造了 $1/16$ 才看出来）。

## T8. `subagent` 的 `tasks[]` 是**启动专用**，不能用它做多个 `continue`

**现象**（2026-10-08）：父会话想同时给 `5032` / `5034` 两个专家发 R3 消息：

```python
subagent(action="continue",
         agent="roj-expert-gemini",
         tasks=[{"action":"continue","agent":"roj-expert-gemini",
                 "name":"roj-expert-gemini-50","task":"...R3 for 5034..."},
                {"action":"continue","agent":"roj-expert-gemini",
                 "name":"roj-expert-gemini-48","task":"...R3 for 5032..."}])
```

结果：**新建了两个会话** `roj-expert-gemini-55` / `-56`，
而原本的 `-48` / `-50` **没有收到任何消息**（`轮次消息数 = 1`，`罗R3消息 = False`）。

**根因**：`tasks[]` 条目的 schema 只有 `agent` / `task` / `worktree` / `model` /
`preset` / `cwd` —— **没有 `action` 也没有 `name`**。
`tasks[]` 是**纯启动**路径；外层传 `action="continue"` 在 `tasks` 存在时被忽略。

**正确做法**：多个续跑要**逐个单独调用**：

```python
subagent(action="continue", name="roj-expert-gemini-50", message="...R3 for 5034...")
subagent(action="continue", name="roj-expert-gemini-48", message="...R3 for 5032...")
```

（另注：续跑用的参数名是 `message`，启动用的才是 `task`。）

**后果评估（本次）**：可控。R3 消息本身包含完整 worker 报告、
待修行号、要求清单与目标路径，因此**新会话能读现有 `index.md`
与最终代码后重写**——功能上等价，只是丢掉了 R1 的推演上下文。
⚠ 但这**不是**可以依赖的性质：若 R3 消息本身依赖上文（例如「按你上一轮的推导……」），
新会话就会缺信息。所以仍应把「同名续跑」当作默认路径。

**与 T4 同类**：都是**工具的参数语义与直觉不符**（`claim` 忽略 pid；`tasks[]` 忽略 action）。
⇒ **调用前先确认「参数是否真的表达了我以为的语义」，不要靠参数名推断。**

## T9. 数据没覆盖 ≠ 两侧语义相同 —— 潜伏的跨语言不一致

### 现象（2026-10-08，`5036`《反序输出》）

本题要求「读入若干整数，逆序输出」。两个语言的原始实现：

```cpp
// main.cpp —— 用 int 读入后回显（编译器会做规范化）
while (cin >> x) a.push_back(x);
for (...) cout << a[i] << " ";
```

```python
# main.py —— 【完全不转 int】，直接把 token 当字符串回显
print(" ".join(reversed(input_data)))
```

**在真实数据上两者 10/10 逐字节一致。** 但语义其实**不同**：

| 输入 token | `cin >> int` 后回显 | 原样字符串回显 |
|---|---|---|
| `+5` | `5` | `+5` |
| `007` | `7` | `007` |
| `-0` | `0` | `-0` |

⇒ 真实数据的 **469 个 token 恰好全部规范**（无 `+` 号、无前导零、无 `-0`、无小数），
所以这个不一致**从未显形**。

### 为什么这是「潜伏」而不是「无害」

| | |
|---|---|
| **触发条件** | 任意一个非规范 token（`+5` / `007` / `1.0`） |
| **后果** | C++ 与 Python 给出**不同答案**，而 `check_new_analysis.py` 只对**磁盘上的 10 个点**比对 ⇒ **永远查不出来** |
| **发现方式** | **只有人（agent）主动去比「两个实现在非数据输入上的行为差异」才能发现** |

⇒ 这属于**闸门盲区**：闸门验证的是「实现 vs 磁盘期望」，
而这类 bug 需要验证「**实现 vs 另一实现**」在**数据分布之外**的行为。

### 教训与做法

1. **「两个实现都过数据」不等于「两个实现等价」**
   跨语言双实现（C++ / Python）必须额外问一句：
   **「有没有输入能让两者行为不同，而数据恰好没覆盖？」**
2. **高风险点清单**（本次是第 1 类）：
   - **类型转换**：字符串回显 vs `int()` 规范化（`+5` / `007` / `-0` / `1.0`）
   - **溢出**：`int` vs 任意精度（`5036` 的 `INT_MIN`、`5040` 的 `2³²-1`）
   - **整除与取模**：C++ `%` 对负数向零取整，Python `//` 向下取整（`-7 // 2 = -4` vs `-7 / 2 = -3`）
   - **浮点格式化**：`printf("%.3f")` 与 f-string（已在 `5025` 查实**一致**）
   - **排序稳定性**：`std::sort` vs `sorted()`（同为不稳定，但比较器不同时可能不同）
   - **字典/集合序**：C++ `map` 有序，Python `dict` 保持插入序
3. **本次已修**：`main.py` 改为 `int` 规范化后输出，两侧语义对齐。

### 附：worker 的另一个「不过度断言」范例（同一份报告）

`5036` 的 V1 反事实用了 UBSan / `-ftrapv`：

```
加 x = -x;  → UBSan 报 "negation of -2147483648 cannot be represented"
            → -ftrapv 直接 Abort trap: 6
加 abs(x)   → int 版输出 -2147483648，ll 版输出 2147483648   ← 肉眼可见
纯取负变体   → 因补码回绕【输出恰好相同】（UB 但不显形）
```

worker 对最后一种**如实标注「不夸大」**——
没有把「UB 但不显形」说成「会输出错误答案」。
**这种克制正是判据可靠的前提**：如果把不显形的 UB 也说成「会挂」，
那么下次真的不显形时，报告的可信度就被稀释了。

## T10. 侦察命令的**截断**被误读成事实（父会话第 9 次出错）

### 现象（2026-10-08，`5040`《最大数位置》）

父会话在侦察批次十时，用这条命令看题面：

```bash
sed -n '1,30p' content.md | grep -v '^\s*$' | head -14
```

输出末尾是：

```
### 【输出样例】
```

**看起来【输出样例】是空的**。于是任务卡里写了：

> ### 待验证 4：★ 题面自身的缺漏
> 题面的【输出样例】代码块**可能是空的**（请不要绕过它）。

**实际上题面有内容**：

```
### 【输出样例】

3
```

⇒ `head -14` **恰好截断在【输出样例】这一行**，把「标题存在」渲染成了「内容为空」。

### 为什么这次没造成损失

因为探针写成了**疑问**（「**可能**是空的，请核实」），worker 去读了真实题面并**直接证伪**：

| 任务卡写的 | 实测 |
|---|---|
| 「【输出样例】**可能是空的**」 | ❌ **非空**，含 `3`（`problem.md` 第 23–25 行，`od -c` 确认） |

**如果当时写成断言**（「输出样例是空的，所以答案只能从 data 推」），
worker 极可能接受这个前提，然后**为不存在的问题设计验证**——
这正是 `M8` 描述的失败路径。

### 教训

| 做法 | 问题 |
|---|---|
| 用 `head -N` / `limit` 截断看内容 | 截断点**恰好**落在关键位置时，会制造假象 |
| 把截断后的输出当作「完整内容」 | ⚠ **本次错误** |
| 正确做法 | **用 `wc -l` 先看总行数**；或**搜关键词看上下文**（`grep -n -A5 '【输出样例】'`）；或直接读全节 |

⇒ 归纳为一条纪律：**侦察输出必须能区分「确实没有」和「我没看到」**。
具体手段：
- `wc -l` / `wc -c` 先确认规模
- `grep -n -A` 拿**上下文**而不是靠行号截断
- 若用了 `head`/`limit`，**在结论里标注「已截断，未看全」**

### 同一天 worker 还纠正了父会话另外两处假设（同一道题）

| 父会话写的 | 实测 |
|---|---|
| 「溢出成负数后，最大值变成谁」 | ❌ `cin >> int` **不回绕**：越界值被**钳位到 `INT_MAX` 并置 failbit**，此后所有读入失败、数组剩 0。只有 `(int)` 强转 / `scanf("%d")` 才真回绕成 `-1` |
| （隐含）`long long` 与 `unsigned int` 等价 | ❌ `unsigned int` **有真实陷阱**：`max_val = -1` 初值时 `(unsigned)(-1) == 4294967295 == 2^32-1`，**恰好等于题面上限** ⇒ **10/10 全错** |

⇒ 三道假设全部错，全部被 worker 用实测纠正。
**这不是偶然：父会话的「记忆 + 快速侦察」组合在高频出错，而 worker 的「实测 + 一手资料」是唯一可靠的裁决者。**

## T11. 不要在有未跟踪产物的仓库里用 `git add -A`

**现象**（2026-10-08）：父会话要给 `~/.pi` 下的 worker 定义加一节（**该文件不在本仓库**），
顺手在 `pcs2-roj-py` 里跑了：

```bash
git add -A 2>/dev/null      # ← 危险
```

结果**暂存了 25 个文件**，其中包括：

| 类别 | 文件 | 问题 |
|---|---|---|
| **无关的未跟踪产物** | `problems/luogu/P5336/` 下 8 个文件（含 `in1`/`out1` 临时数据） | 不属于本次任何工作 |
| **在飞但未完成** | `problems/roj/5039,5040,5041/` 的四个文件 | 这些题的 R2/R3 尚未收口，**不能提交** |

**本次能无损还原**：`git reset`（mixed）清空暂存区，未跟踪文件回到 `??`，
在飞文件回到未暂存 —— **没有任何提交被污染**。

### 纪律

| 做法 | 评价 |
|---|---|
| `git add -A` / `git add .` | ❌ **禁止** —— 会吞掉无关产物与未完成的工作 |
| `git add <具体路径>` | ✅ **唯一允许的形式** |
| 跨仓库操作时 | ⚠ **先确认 cwd**；`~/.pi` 与 `~/mycode/...` 是不同仓库 |

### 与 `T4` / `T8` 同类

三次都是**「命令的参数/作用域与我以为的不同」**：

| 编号 | 我以为 | 实际 |
|---|---|---|
| `T4` | `claim <pid>` 标记一个 | 按 `--count` 批量抓 10 个 |
| `T8` | `tasks[]` + `action=continue` 续跑多个 | 新建会话 |
| **`T11`** | **`git add -A` 只加我改的东西** | **把一个仓库里所有未跟踪产物全加了** |

⇒ 统一纪律：**执行「作用域可能超出预期」的命令前，先确认它会碰哪些对象**。
对 git 而言：用**明确路径**，不用 `-A`/`.`。

## T12. 题面指定算法时，闸门**结构性失效**（两个实证实例）

### 现象

当题面显式要求某种算法实现手段时（「（冒泡排序）」「用筛法」），
**把实现换成等价算法，输出完全相同** ⇒ `check_new_analysis.py` 永远查不出来。

| 实例 | 冒牌实现 | 闸门结果 |
|---|---|---|
| **`5041`** 题面「（冒泡排序）」 | `bubble_sort()` → `std::sort(a, a+n, greater<ll>())` | **仍报 PASS=10 / FAIL=0**（10 点输出逐字节相同）|
| **`5042`** 题面「用筛法」 | 埃氏筛 → 逐个试除 | **仍报 ✅ PASS=10, FAIL=0** |
| `5038` 题面描述模拟过程（**非**硬约束） | 数学法 $O(\sqrt n)$ | PASS（此例**合法**，因为只是题目设定）|

⇒ **凡题面指定算法，输出比对类闸门都失效。**
这不是闸门的 bug —— 闸门验证的是「实现 vs 磁盘期望」，
而「用了哪种算法」**在输出里不可观测**。

### 必须改用结构性验证（三类证据互证）

| 证据 | 手段 |
|---|---|
| **① 代码结构** | 贴**行号 + 代码片段**，证明算法形态（双重循环 + 相邻交换；布尔数组 + 倍数标记）|
| **② 反向扫描** | `grep` 库函数/试除特征（`std::sort`/`qsort`/`sorted(`/`.sort(`；`%`/`is_prime(x)`）**应为空** |
| **②' 闸门盲区的自证** | **主动造冒牌版跑一遍**，证明闸门确实查不出来（两题都做了）|
| **③ 操作计数指纹**（见 `V7`） | 比较次数 $=n(n-1)/2$；交换次数 $\equiv$ 逆序对数；扰动后分歧数**精确统计** |

### ★ `5042` 的扰动表是最强形态

对 $n = 2..1000$ **全部穷举**，每组扰动给出**精确分歧数**：

| 扰动 | 分歧数 | 结论 |
|---|---|---|
| 外层 `i*i<=n` → `i<=n/2` / `i<=n` | **0** | 冗余但正确 |
| 内层起点 `i*i` → `i*2` | **0** | 两者等价 |
| 去掉 `is_prime[0]/[1]=false` | **0** | 不在输出区间 |
| 删掉 `if(!is_prime[i]) continue` | **0** | 仅常数优化 |
| 删掉内层标记循环 | **997** | 承重 |
| **`i*i<=n` → `i*i<n`** | **11** | 承重，**临界点可精确刻画** |

**最后一行把「凭感觉的选择」变成了可判定的问题**：

```
分歧【恰好发生在 n 是完全平方数时】
集合 = {4,9,25,49,121,169,289,361,529,841,961}
     = [2,1000] 内的全部完全平方数（11 个）
```

⇒ 这正是「扰动 + 精确计数」相对「扰动 + 看变没变」的优势：
**它告诉你「何时会变」，而不只是「会不会变」**。后者才能支撑文档里的一句断言。

## T13. 闸门的 token 级比较对**一切空白差异免疫**（新增独立字节检查器）

### 现象（2026-10-08，`5044`）

`check_new_analysis.py:334` 的判定是：

```python
if got.split() == want.split() or _spj_ok(...):
```

C++ 侧委托给 `check_sample.py`，其 `normalize_output()` 还会
`while lines and lines[-1] == "": lines.pop()`（**剥掉末尾空行**）。

⇒ **两处都对空白差异免疫**：

| 差异 | token 级比较 | 字节级 |
|---|---|---|
| 空输出 **0 字节** vs **一个空行** | 相同（都 `[]`） | **不同** |
| 行尾多余空格 | 相同 | **不同** |
| token 之间多个空格 | 相同 | **不同** |
| `\r\n` vs `\n` | 相同 | **不同** |

**实测**：给 `5044` 注入「无条件多打一个换行」的 bug 后：

```
check_new_analysis.py --realdata 5044   →  ✅ PASS=10, FAIL=0   ← 【假绿灯】
check_bytes.py 5044                     →  ❌ 字节数不同(97830B vs 97829B)
```

⚠ **影响面**：本批已确认 **4 道题**的正确答案是「**0 字节空输出**」
（`5019` / `5029` / `5032` / `5044`）—— 这些题的「空 vs 空行」区别
**闸门完全查不出**。此前是靠 worker 手动 `od -c` 发现的，不是靠闸门。

### 处置：新增独立字节检查器 `check_bytes.py`

与既有闸门**完全独立**（自建编译 + 自建运行 + 自比字节），符合「判据要能被独立证伪」：

```bash
python3 scripts/problem-analysis-tools/check_bytes.py <pid> [<pid> ...]
# 输出示例
# ✅ 5029  10 点：main.cpp 逐字节 10/10 · main.py 逐字节 10/10
# ❌ 5044  ...  problem9.in: cpp=字节数不同(97830B vs 97829B)  py=ok
```

差异还被分类（`字节数不同` / `空白差异` / `内容不同` / `TLE`），便于定位。

**使用时机**：凡题面或数据对**格式**有要求的题
（**空输出**、行尾空格、分隔符宽度、行尾换行）都应跑一次。

### 教训

> **「通过闸门」不等于「逐字节正确」。**
> 闸门是**必要**判据（能抓内容错），但不是**充分**判据（抓不到空白错）。
> 两者都要跑；而**判据之间必须相互独立** ——
> 一个宽松的判据不能用来证明另一个宽松判据的结论。
