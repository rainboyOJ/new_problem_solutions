## T4. `pcs2_queue.py claim <pid>` **不接受 pid** —— 按 `--count` 批量抓

**现象**（2026-10-08）：父会话想把在飞的 4 道标为 claimed：

```bash
for p in 5020 5021 5022 5023; do
  python3 .../pcs2_queue.py claim $p --queue .tmp/roj283-queue.jsonl --worker batch6
done
```

结果**标了 40 道**（`D:9 C1:24 C2:5 A:2`），而不是 4 道。

**根因**：`cmd_claim` 的实现是

```python
picked = pool[: args.count]      # ← pool 由 cohort/status 筛选得到，与位置参数无关
```

`claim` 的**位置参数 `pid` 被忽略**，真正起作用的是 `--count`（默认 10）。
我循环调 4 次 ⇒ 每次抓 10 道 ⇒ **4 × 10 = 40**。

**修复方式**：直接用脚本改 JSONL（精确、可逆），不要用 `claim` 做单题标记：

```python
KEEP = {'5020','5021','5022','5023'}
for r in rows:
    if r['pid'] in KEEP: r['status']='claimed'; r['worker']='batch6'
    elif r['status']=='claimed': r['status']='pending'; r['worker']=None
```

**教训（可推广）**：**循环调用一个工具之前，先确认它的参数语义**。
「参数名像 pid」不等于「支持指定 pid」。
本次能无损还原，是因为 `claimed` 之前的旧状态恰好都是 `pending` ——
如果我把 `done` 的题目也误改了，就没有旧状态可还原了。

**附带**：`pcs2_queue.py` 的默认队列是 `.tmp/pcs2-queue.jsonl`，
而 `accept.py` 用的是 `.tmp/roj283-queue.jsonl` —— **必须显式传 `--queue`**，
否则 `stats` 会报 `total: 0`（看不见任何待办）。

## T5. 「遵循规范」不得写成「正确性要求」——文档偏差的一个新类别

### 现象（2026-10-08，`5028`《阶乘和》）

题目 $1 \le n \le 10$，$S_{10} = 4{,}037{,}913 \ll 2^{31}-1$ ⇒ **`int` 完全够用**。

但仓库 skill `oj-cpp-competitive-style` 规定「**题目数据默认 `long long`**」，且
「⚠ 题面未指定时仍然按本 skill 写」。本题题面未指定类型 ⇒ 按规范应写 `ll`。

于是出现了这样的链条：

```
专家初稿 index.md： 「…因此不会发生溢出，使用普通的 int 即可」
worker 按 skill 改代码： int → ll
⇒ 文档与代码不一致（index.md 说 int，代码写 ll）
```

### ★ 危险的不是不一致本身，而是「修不一致时的措辞」

最省事的修法是**把文档改成「必须用 `ll`」** —— 但这会制造一个**更严重的错误**：

| 写法 | 问题 |
|---|---|
| 「使用普通的 `int` 即可」（原稿） | 与代码不一致 |
| 「**必须**用 `long long`，否则溢出」（错误的修法） | ❌ **事实错误** —— 数据范围内 `int` 逐点正确 |
| 「本题用 `int` 也确实能过；代码改成 `ll` 是**遵循仓库规范**而非修 bug」（正确） | ✅ |

### 判据：区分三类「改类型」的理由

| 理由 | 该怎么说 | 例 |
|---|---|---|
| **正确性**：不改就会 WA/溢出 | 「必须用 `ll`」 | 5021（$13!$ 起 `int` 溢出，且数据覆盖了 $n=13$） |
| **规范**：不改也对，但仓库约定如此 | 「**能过**，但按仓库规范用 `ll`」 | **5028**（数据范围内 `int`/`ll` 逐字节相同） |
| **风格**：纯个人偏好 | 不写进题解 | — |

**判据**：问一句「**保留原类型，真实数据会失败吗？**」
- 会 ⇒ 正确性问题，写「必须」
- 不会 ⇒ 规范问题，**必须同时写明「原类型也能过」**

### counterfactual 是锁定这个区别的唯一手段

`5028` 的 worker 用反事实把结论钉死了：

```
n = 1..10  →  int 版与 ll 版输出【逐字节完全相同（10/10）】
n = 13     →  ll: 6749977113  vs  int: -1839957479   ← 只有这里才分道扬镳
```

⇒ **数据范围内改类型没有修复任何真实点**。有了这张表，
「本题用 `int` 也确实能过」就不是客套话，而是**实测结论**。

### 推广

这条属于「文档偏差」的一个子类。R2 worker 的任务卡里已加入一项固定要求：

> 若你按 skill 改了实现（类型、写法），**请判断 `index.md` 的对应表述是否需要同步**，
> 并给出**带行号的可粘贴建议**；同时说明这是「正确性」还是「规范」问题。

R3 的专家据此修改 —— 比让专家自己发现偏差更省一轮。

## T6. 专家会**往题面里加词** —— 最隐蔽的文档错误

### 现象（2026-10-08，`5026`《末两位数》）

专家初稿 `index.md` 写：

> 「给定一个**非负**整数 $n$（$n < 2000$），求 $n$ 个 $1992$ 相乘的积的末两位数。」

而题面 `problem.md` 原文只有：

```
【题目描述】求 $n$ 个 $1992$ 的乘积的末两位数是多少？
【输入】    输入 $n$。
【提示】    对于所有数据：$n < 2000$。
```

⇒ **「非负」二字题面里没有，也没有任何下界**。是专家自己加的。

### 为什么这类错误特别危险

| | 一般错误 | 「加词」类错误 |
|---|---|---|
| 表现 | 结论错 | **结论可能对，但前提被篡改** |
| 读者感受 | 能通过验证发现 | **会以为那是题面的规定** |
| 影响 | 本题错 | **读者把虚构的约束带到别的题上** |

而且它**恰好掩盖了一个真实的开放问题**：本题题面**只给上界、未给下界**，
所以 $n=0$ 是否合法**是题目本身没定义的**。专家加「非负」二字，
等于**替题目做了一个它没做的决定**。

### 判据

**题面里没写的限定词，不得出现在题解的事实陈述中。** 具体：

| 想做 | 正确做法 |
|---|---|
| 补充一个看起来显然的约束 | ❌ 直接写进陈述<br>✅ 写「题面未给下界」+ 明确标注「若 $n=0$，按……约定」 |
| 简化题面的措辞 | ❌ 改写成「等价说法」<br>✅ 引用原句 |
| 推断数据的取值范围 | ✅ 写「数据实际取值集合 = …（**这是观测，不是题面**）」 |

### 检测手段

R2 worker 的任务卡里已有固定要求（源起 T5）：

> 若 `index.md` 对**题目本身的陈述**与 `problem.md` 原文有出入，
> 请指出**具体行号与原文**，并标注这是「题面要求」还是「作者推测」。

`5026` 的 worker 正是靠这条抓到了「非负」二字 —— **它不在它被要求检查的清单里，
是它在执行核对时顺手发现的**。这说明该职责应作为一项**常设检查**保留。

### 附：worker 同时交出了一个漂亮的旁证

> $\gcd(1992, 100) = 4$ ⇒ 真实答案**恒为 4 的倍数**；
> $n = 0$（输出 1）是**唯一**可能输出非 4 倍数的输入
> ⇒ 佐证 $n=0$ 不是测试点。

这类「用数学结构排除某个边界是不是测试点」的推理，
比「数据里没有这个点」强得多 —— 后者只说明现状，前者说明**为什么出题人不会选它**。

## T7. 专家的「兼容方案」可能比不兼容更有害 —— 跨语言舍入的实例

### 现象（2026-10-08，`5025`《数据统计》）

**背景**：题目要求输出平均值并「保留 3 位小数」。
专家在初稿里标了 `uncertain`，并**主动给出兼容方案**：

> 「C++ 与 Python 在四舍五入（尤其是恰好等于 $*.xx5$）的情形下是否完全一致」
> ……「若 worker 发现由于舍入差异造成的判题错误，
> 则 Python 需要手动使用 `Decimal` 和 `ROUND_HALF_UP` 来兼容 C++ 的输出结果。」

**这个建议听起来完全合理** —— 「四舍五入」的英文是 round-half-up，
所以用 `ROUND_HALF_UP` 去「对齐 C++」似乎是标准做法。

### 实测结果：该方案会引入 **50%** 的分歧

| 模型 | 与 C++ `printf` / Python f-string 的不符数（共 80,000 个精确平分点） |
|---|---|
| `Decimal(精确值) + ROUND_HALF_UP` | **40,000（50%）** ❌ |
| `Decimal(精确值) + ROUND_HALF_EVEN` | 16,002（20%） ❌ |
| **`double(S/n)` 按 round-half-even 格式化** | **0** ✅ |

### 根因：`printf` 不是「四舍五入」

C 的 `printf("%.3f")` 与 Python 的 f-string **都对二进制值做 `round-half-even`（平局取偶）**：

```c
printf("%.3f", 1.0/16);   // 0.0625  →  0.062   保留位 2 偶 → 舍
printf("%.3f", 3.0/16);   // 0.1875  →  0.188   保留位 7 奇 → 进
```

```python
f"{1/16:.3f}"   # '0.062'
f"{3/16:.3f}"   # '0.188'      ← 与 C++ 完全一致
Decimal('0.0625').quantize(Decimal('0.001'), ROUND_HALF_UP)   # 0.063  ← 与两者都不符
```

⇒ **「四舍五入」是日常语言的近似说法，不是 libc/CPython 的实现**。
基于错误的名字去写「兼容层」，就把本来一致的两种实现**改成了不一致**。

### 判据（可推广）

**当有人（包括专家）建议「加一层适配/兼容/转换」时，先回答这一个问题：**

> **不加这一层，会不会有问题？**

`5025` 的答案是不加就没问题（**5,050,100 组全空间穷举 0 分歧**）。
「加一层」的代价是引入 50% 分歧 —— **适配层的常见失败模式**：
它把「两边本来就一致」的情形**改成不一致**，因为适配层依据的是
**对某一侧行为的猜测**（这里是「printf 是四舍五入」），而不是实测。

### 与 T5/T6 的关系

| 编号 | 类别 | 例子 |
|---|---|---|
| T5 | **过度断言**：把规范说成正确性要求 | `5028` 的 `int` → `ll` |
| T6 | **无据添加**：往题面里加词 | `5026` 的「非负」 |
| **T7** | **错误补救**：为不存在的问题加适配层 | **`5025` 的 `Decimal + ROUND_HALF_UP`** |

三者都是「**事实陈述与依据不匹配**」，但 T7 的危害最大 —— 它**主动破坏本来正确的代码**。

### 附带：初稿里的一个「个案当通则」

专家初稿第 45 行写：

> 「标准舍入规则……且**当小数末尾正好为 5 时（如 0.1875），会被进位**（输出 0.188）」

把「$0.1875 \to 0.188$」当成通则 —— 而 $0.0625 \to 0.062$ 立刻反证。
这正是「只有一个样例就下结论」的典型；数据里**唯一**的平分点恰好是保留位为奇数的那种，
所以**一个反例都看不到**。⇒ **数据只有 1 个 tie 点时，不能据此断定舍入模式**
（worker 正是自己构造了 $1/16$ 才看出来）。

## T8. `subagent` 的 `tasks[]` 是**启动专用**，不能用它做多个 `continue`

**现象**（2026-10-08）：父会话想同时给 `5032` / `5034` 两个专家发 R3 消息：

```python
subagent(action="continue",
         agent="roj-expert-gemini",
         tasks=[{"action":"continue","agent":"roj-expert-gemini",
                 "name":"roj-expert-gemini-50","task":"...R3 for 5034..."},
                {"action":"continue","agent":"roj-expert-gemini",
                 "name":"roj-expert-gemini-48","task":"...R3 for 5032..."}])
```

结果：**新建了两个会话** `roj-expert-gemini-55` / `-56`，
而原本的 `-48` / `-50` **没有收到任何消息**（`轮次消息数 = 1`，`罗R3消息 = False`）。

**根因**：`tasks[]` 条目的 schema 只有 `agent` / `task` / `worktree` / `model` /
`preset` / `cwd` —— **没有 `action` 也没有 `name`**。
`tasks[]` 是**纯启动**路径；外层传 `action="continue"` 在 `tasks` 存在时被忽略。

**正确做法**：多个续跑要**逐个单独调用**：

```python
subagent(action="continue", name="roj-expert-gemini-50", message="...R3 for 5034...")
subagent(action="continue", name="roj-expert-gemini-48", message="...R3 for 5032...")
```

（另注：续跑用的参数名是 `message`，启动用的才是 `task`。）

**后果评估（本次）**：可控。R3 消息本身包含完整 worker 报告、
待修行号、要求清单与目标路径，因此**新会话能读现有 `index.md`
与最终代码后重写**——功能上等价，只是丢掉了 R1 的推演上下文。
⚠ 但这**不是**可以依赖的性质：若 R3 消息本身依赖上文（例如「按你上一轮的推导……」），
新会话就会缺信息。所以仍应把「同名续跑」当作默认路径。

**与 T4 同类**：都是**工具的参数语义与直觉不符**（`claim` 忽略 pid；`tasks[]` 忽略 action）。
⇒ **调用前先确认「参数是否真的表达了我以为的语义」，不要靠参数名推断。**

## T9. 数据没覆盖 ≠ 两侧语义相同 —— 潜伏的跨语言不一致

### 现象（2026-10-08，`5036`《反序输出》）

本题要求「读入若干整数，逆序输出」。两个语言的原始实现：

```cpp
// main.cpp —— 用 int 读入后回显（编译器会做规范化）
while (cin >> x) a.push_back(x);
for (...) cout << a[i] << " ";
```

```python
# main.py —— 【完全不转 int】，直接把 token 当字符串回显
print(" ".join(reversed(input_data)))
```

**在真实数据上两者 10/10 逐字节一致。** 但语义其实**不同**：

| 输入 token | `cin >> int` 后回显 | 原样字符串回显 |
|---|---|---|
| `+5` | `5` | `+5` |
| `007` | `7` | `007` |
| `-0` | `0` | `-0` |

⇒ 真实数据的 **469 个 token 恰好全部规范**（无 `+` 号、无前导零、无 `-0`、无小数），
所以这个不一致**从未显形**。

### 为什么这是「潜伏」而不是「无害」

| | |
|---|---|
| **触发条件** | 任意一个非规范 token（`+5` / `007` / `1.0`） |
| **后果** | C++ 与 Python 给出**不同答案**，而 `check_new_analysis.py` 只对**磁盘上的 10 个点**比对 ⇒ **永远查不出来** |
| **发现方式** | **只有人（agent）主动去比「两个实现在非数据输入上的行为差异」才能发现** |

⇒ 这属于**闸门盲区**：闸门验证的是「实现 vs 磁盘期望」，
而这类 bug 需要验证「**实现 vs 另一实现**」在**数据分布之外**的行为。

### 教训与做法

1. **「两个实现都过数据」不等于「两个实现等价」**
   跨语言双实现（C++ / Python）必须额外问一句：
   **「有没有输入能让两者行为不同，而数据恰好没覆盖？」**
2. **高风险点清单**（本次是第 1 类）：
   - **类型转换**：字符串回显 vs `int()` 规范化（`+5` / `007` / `-0` / `1.0`）
   - **溢出**：`int` vs 任意精度（`5036` 的 `INT_MIN`、`5040` 的 `2³²-1`）
   - **整除与取模**：C++ `%` 对负数向零取整，Python `//` 向下取整（`-7 // 2 = -4` vs `-7 / 2 = -3`）
   - **浮点格式化**：`printf("%.3f")` 与 f-string（已在 `5025` 查实**一致**）
   - **排序稳定性**：`std::sort` vs `sorted()`（同为不稳定，但比较器不同时可能不同）
   - **字典/集合序**：C++ `map` 有序，Python `dict` 保持插入序
3. **本次已修**：`main.py` 改为 `int` 规范化后输出，两侧语义对齐。

### 附：worker 的另一个「不过度断言」范例（同一份报告）

`5036` 的 V1 反事实用了 UBSan / `-ftrapv`：

```
加 x = -x;  → UBSan 报 "negation of -2147483648 cannot be represented"
            → -ftrapv 直接 Abort trap: 6
加 abs(x)   → int 版输出 -2147483648，ll 版输出 2147483648   ← 肉眼可见
纯取负变体   → 因补码回绕【输出恰好相同】（UB 但不显形）
```

worker 对最后一种**如实标注「不夸大」**——
没有把「UB 但不显形」说成「会输出错误答案」。
**这种克制正是判据可靠的前提**：如果把不显形的 UB 也说成「会挂」，
那么下次真的不显形时，报告的可信度就被稀释了。

## T10. 侦察命令的**截断**被误读成事实（父会话第 9 次出错）

### 现象（2026-10-08，`5040`《最大数位置》）

父会话在侦察批次十时，用这条命令看题面：

```bash
sed -n '1,30p' content.md | grep -v '^\s*$' | head -14
```

输出末尾是：

```
### 【输出样例】
```

**看起来【输出样例】是空的**。于是任务卡里写了：

> ### 待验证 4：★ 题面自身的缺漏
> 题面的【输出样例】代码块**可能是空的**（请不要绕过它）。

**实际上题面有内容**：

```
### 【输出样例】

3
```

⇒ `head -14` **恰好截断在【输出样例】这一行**，把「标题存在」渲染成了「内容为空」。

### 为什么这次没造成损失

因为探针写成了**疑问**（「**可能**是空的，请核实」），worker 去读了真实题面并**直接证伪**：

| 任务卡写的 | 实测 |
|---|---|
| 「【输出样例】**可能是空的**」 | ❌ **非空**，含 `3`（`problem.md` 第 23–25 行，`od -c` 确认） |

**如果当时写成断言**（「输出样例是空的，所以答案只能从 data 推」），
worker 极可能接受这个前提，然后**为不存在的问题设计验证**——
这正是 `M8` 描述的失败路径。

### 教训

| 做法 | 问题 |
|---|---|
| 用 `head -N` / `limit` 截断看内容 | 截断点**恰好**落在关键位置时，会制造假象 |
| 把截断后的输出当作「完整内容」 | ⚠ **本次错误** |
| 正确做法 | **用 `wc -l` 先看总行数**；或**搜关键词看上下文**（`grep -n -A5 '【输出样例】'`）；或直接读全节 |

⇒ 归纳为一条纪律：**侦察输出必须能区分「确实没有」和「我没看到」**。
具体手段：
- `wc -l` / `wc -c` 先确认规模
- `grep -n -A` 拿**上下文**而不是靠行号截断
- 若用了 `head`/`limit`，**在结论里标注「已截断，未看全」**

### 同一天 worker 还纠正了父会话另外两处假设（同一道题）

| 父会话写的 | 实测 |

## T12. 题面指定算法时，闸门**结构性失效**（两个实证实例）

### 现象

当题面显式要求某种算法实现手段时（「（冒泡排序）」「用筛法」），
**把实现换成等价算法，输出完全相同** ⇒ `check_new_analysis.py` 永远查不出来。

| 实例 | 冒牌实现 | 闸门结果 |
|---|---|---|
| **`5041`** 题面「（冒泡排序）」 | `bubble_sort()` → `std::sort(a, a+n, greater<ll>())` | **仍报 PASS=10 / FAIL=0**（10 点输出逐字节相同）|
| **`5042`** 题面「用筛法」 | 埃氏筛 → 逐个试除 | **仍报 ✅ PASS=10, FAIL=0** |
| `5038` 题面描述模拟过程（**非**硬约束） | 数学法 $O(\sqrt n)$ | PASS（此例**合法**，因为只是题目设定）|

⇒ **凡题面指定算法，输出比对类闸门都失效。**
这不是闸门的 bug —— 闸门验证的是「实现 vs 磁盘期望」，
而「用了哪种算法」**在输出里不可观测**。

### 必须改用结构性验证（三类证据互证）

| 证据 | 手段 |
|---|---|
| **① 代码结构** | 贴**行号 + 代码片段**，证明算法形态（双重循环 + 相邻交换；布尔数组 + 倍数标记）|
| **② 反向扫描** | `grep` 库函数/试除特征（`std::sort`/`qsort`/`sorted(`/`.sort(`；`%`/`is_prime(x)`）**应为空** |
| **②' 闸门盲区的自证** | **主动造冒牌版跑一遍**，证明闸门确实查不出来（两题都做了）|
| **③ 操作计数指纹**（见 `V7`） | 比较次数 $=n(n-1)/2$；交换次数 $\equiv$ 逆序对数；扰动后分歧数**精确统计** |

### ★ `5042` 的扰动表是最强形态

对 $n = 2..1000$ **全部穷举**，每组扰动给出**精确分歧数**：

| 扰动 | 分歧数 | 结论 |
|---|---|---|
| 外层 `i*i<=n` → `i<=n/2` / `i<=n` | **0** | 冗余但正确 |
| 内层起点 `i*i` → `i*2` | **0** | 两者等价 |
| 去掉 `is_prime[0]/[1]=false` | **0** | 不在输出区间 |
| 删掉 `if(!is_prime[i]) continue` | **0** | 仅常数优化 |
| 删掉内层标记循环 | **997** | 承重 |
| **`i*i<=n` → `i*i<n`** | **11** | 承重，**临界点可精确刻画** |

**最后一行把「凭感觉的选择」变成了可判定的问题**：

```
分歧【恰好发生在 n 是完全平方数时】
集合 = {4,9,25,49,121,169,289,361,529,841,961}
     = [2,1000] 内的全部完全平方数（11 个）
```

⇒ 这正是「扰动 + 精确计数」相对「扰动 + 看变没变」的优势：
**它告诉你「何时会变」，而不只是「会不会变」**。后者才能支撑文档里的一句断言。

## T13. 闸门的 token 级比较对**一切空白差异免疫**（新增独立字节检查器）

| 行尾多余空格 | 相同 | **不同** |

```

check_bytes.py 5044                     →  ❌ 字节数不同(97830B vs 97829B)

（`5019` / `5029` / `5032` / `5044`）—— 这些题的「空 vs 空行」区别
**闸门完全查不出**。此前是靠 worker 手动 `od -c` 发现的，不是靠闸门。

### 处置：新增独立字节检查器 `check_bytes.py`

与既有闸门**完全独立**（自建编译 + 自建运行 + 自比字节），符合「判据要能被独立证伪」：

```bash

# ❌ 5044  ...  problem9.in: cpp=字节数不同(97830B vs 97829B)  py=ok

差异还被分类（`字节数不同` / `空白差异` / `内容不同` / `TLE`），便于定位。

**使用时机**：凡题面或数据对**格式**有要求的题
（**空输出**、行尾空格、分隔符宽度、行尾换行）都应跑一次。

### 教训

> **「通过闸门」不等于「逐字节正确」。**
> 闸门是**必要**判据（能抓内容错），但不是**充分**判据（抓不到空白错）。

> 一个宽松的判据不能用来证明另一个宽松判据的结论。

## T14. 「**数据承重**」vs「**离数据承重**」——反事实的两个层次

### 现象（2026-10-08，`5046`《回文字串》）

worker 跑了 5 条反事实，「在真实数据上是否失败」的结果**分成两类**：

| 反事实 | 真实 10 点 | 定性 |
|---|---|---|
| **CF1** 不剥 `.` | **3 点失败** | **数据承重** |
| **CF3** 比较时转小写 | **2 点失败** | **数据承重** |
| **CF2** 无条件去掉末位 | **0 失败** | **离数据才承重** —— 构造 `aba` 得 `No`（应 `Yes`）|
| **CF4** 改用 `cin >> s` | 0 失败（数据无空格） | **离数据才承重** —— 题面说「一行字符串」|
| **CF5** 不剥 `\r` | 0 失败（数据无 CRLF） | **离数据才承重** —— CRLF 容错 |

**worker 对后三条全部诚实标注了「数据无法证伪」**，并说明了**为什么仍必须保留**。

### 为什么这个区分重要

| 写法 | 问题 |
|---|---|
| 「CF2 在真实数据上 0 失败 ⇒ 这个 guard 没用」 | ❌ **错误结论** —— 会把正确的兜底代码删掉 |
| 「CF2 数据无法证伪，但构造 `aba` 会错 ⇒ 离数据承重，仍需保留」 | ✅ |

**判据**：
- **数据承重**：真实数据能证伪 ⇒ 改了就失败 ⇒ **必须保留**（证据充分）
- **离数据承重**：真实数据**无法**证伪，但**构造**输入能 ⇒ **仍需保留**
  （依据是**题面**或**语言的约定行为**，而不是数据）

### 与 `T5`（规范 vs 正确性）的关系

| 编号 | 问题 | 判据 |
|---|---|---|
| `T5` | 「改类型是正确性问题还是规范问题？」 | 「保留原类型，**真实数据**会失败吗？」|
| **`T14`** | 「这条 guard 是数据承重还是离数据承重？」 | 「**构造**一个数据外的输入，会失败吗？」|

两者是同一族：**「在数据上没用」不等于「不需要」**。
差别只在**反事实的输入来自哪里**（真实数据 vs 构造输入）。

### 报告纪律

**每条反事实都必须标注「真实数据上的失败点数」**，0 失败时还要给出**构造输入上的最小复现**。
不允许只写「改了就错」或只写「数据通过」—— 两者都会掩盖层次。

### 附带：`5046` 另一条值得记的发现

```c
while ((c = getchar()) != '.') { ... }    // 经典写法，无 EOF 保护
```

在**没有 `.` 的输入**（`problem3 = abccb`）上 ⇒ **SEGFAULT（rc=-11，stdout 空）**。
⇒ 不是「卡住」，是**直接崩溃**。题面说「以 `.` 结束」但**数据里有不遵守的点**。

## T15. 父会话给出的**具体例子**必须先自己跑一遍（今天 3 次犯错）

### 现象

父会话（编排者）在任务卡里给出具体例子时，**构造了但没验算**，导致 3 次错误：

|---|---|---|---|
| 1 | `5052` | 「假阳性反例：$s_1=\texttt{aba}, s_2=\texttt{ab}$」 | ❌ **不是假阳性** —— 真值就是 `true`（`ab` 是 `aba` 0 次移位的子串）|
| 2 | `5051` | 「`a\rb\r` 经 `splitlines()` 得 **3 行** `['a','b','']`」 | ❌ **得 2 项** —— `splitlines` **不在结尾补空项**（`split('\n')` 才补）|

```
构造一个反例：  找一个看起来能满足「条件」的输入
验证它是反例：  ① 算它在【错误实现】下的输出
               ② 算它在【正确实现】下的输出
               ③ 确认两者不同
```

`5052` 我只做了 ①（`abab` 含 `aba` → true），**跳过了 ②**（真值也是 true）。
`5051` 我只凭「`splitlines` 按多个字符分行」的**印象**推断了项数，没跑。

### 纪律（硬性）

> **写进任务卡的任何具体例子（输入 / 输出 / 数字 / 项数），
> 必须先在本地跑一遍并把结果贴进去。**

具体做法：
```bash
# 反例类：两边都跑
printf '<example>' | <错误实现>   # 得到 got_wrong
printf '<example>' | <正确实现>   # 得到 got_right
# 只有 got_wrong != got_right 才是反例
```

### 与既有纪律的关系

| 编号 | 纪律 | 针对 |
|---|---|---|
| `M8` | 提示写成**疑问**而非断言 | 我的**判断**可能错 |
| **`T15`** | **具体例子必须实跑** | 我的**算例**可能错 |
| `T14` | 反事实要标注**层次** | 我的**验证**可能不充分 |

三者合起来覆盖了「父会话输出」的三类内容：**判断 / 算例 / 验证设计**。
**每一类都必须能被打回**。

## T17. 「数据无法区分」的三个证明层次：从「测不出」到「构造性根因」

### 背景（2026-10-08，`5058`）

题面「输出最大的数」，输出格式有两个候选：
- **(a) 原样回显**（按字符串读，数值比较后回显赢家的原串）
- **(b) `%g` / `cout << double` 默认**（6 位有效数字，去冗余零）

10 个点上两者**输出全同** ⇒ 用 `V8` 只能得出「**数据无法区分**」。

### worker 把它推到了**三个更深的层次**

| 层次 | 做法 | 结论强度 |
|---|---|---|
| **L1** 测数据 | 10 个点上 (a) 与 (b) 输出全同 | 「**在这 10 个点上**分不出」|
| **L2** 穷举声明域 | 整数档 1,999,999 + 两位小数档 1,999,999，往返 **0 不一致** | 「在**声明域内**是**可证明的恒等**」|
| **L3** 找构造性根因 | `data.py:120` 的 `check_token()` **自己断言** `("%g" % float(tok)) == tok` | 「**生成器强制了**二者一致」⇒ 恒等是**设计保证**，不是巧合 |

**L3 最强**：它解释了**为什么**恒等。而且它给出了一个可传递的性质：
**只要数据由这个生成器产出，(a) ≡ (b) 就成立** —— 不需要逐次穷举。

### 还有一个「第四层次」：**产物的生成方式**

worker 还指出：`.out` 本身就是 `std.cpp` 用 **`printf("%g")`** 生成的
⇒ **(b) 与本题数据包「定义上一致」**。

这比 L2/L3 更直接：**答案文件就是按 (b) 的格式造出来的**，
所以「选 (b)」不是「两个都对」而是「**与答案的生成方式同源**」。

### 判据（可推广）

当两个候选实现**在数据上无法区分**时，按以下顺序找更强的证据：

1. **穷举声明域**（若域小，成本低）⇒ 「域内恒等」
2. **找数据生成器的断言**（`grep` 生成脚本里的 `assert` / `if not ...: raise`）
   ⇒ 「构造性保证」
3. **看 `.out` 是怎么生成的**（`data.py` 是否调用了 `std.cpp`？
   用了什么格式化？）⇒ 「与答案同源」
4. **若三条都拿不到**，才如实写「数据无法裁定，两种写法在数据上等价」
   （如 `5057` 的舍入模式、`5025` 的 half-up vs half-even、`5015` 的中位数定义）

⇒ **「无法确定」是合格的最终结论，但应当是【穷尽上述层次之后】的结论**，
而不是第一层就想收手。

### 附带：`5058` 还量化了「Python 原生 `print` 不可用」

```
Python print(1.0)  →  '1.0'     vs   %g  →  '1'
⇒ 480 组边界测试中【369 组分歧】
```
**量化分歧数**比「不一致」更有说服力 —— 它说明这不是边角情形，
而是**近 77% 的输入都会错**。

## T18. macOS libc 的 `%g` 与 glibc / Python **不同**（本机对拍可能假失败）

### 现象（2026-10-08，`5060` 的 worker 发现 + 父会话复验）

macOS libc 的 `printf("%g", v)` 在**科学计数法**下**不去除尾随零**：

| 值 | **macOS libc** | **glibc / Python `%g`** |
|---|---|---|
| `1000005.0` | `1.00000e+06` | **`1e+06`** |
| `2000205.0` | `2.00020e+06` | **`2.0002e+06`** |
| `1234005.0` | `1.23400e+06` | **`1.234e+06`** |
| `1000000.0` | `1e+06` ✅ | `1e+06` |
| `999999.0*999999.0` | `9.99998e+11` ✅ | `9.99998e+11` |

**父会话复验（本机实测）**：

```bash
$ printf '6 999999 +\n' | ./main_cpp    # → 1.00000e+06   ← macOS
$ printf '6 999999 +\n' | python3 main.py  # → 1e+06        ← Python
```

⇒ **`6 999999 +` = 1000005 这个用例上，本机 C++ 与 Python 输出不同**。
worker 用 **docker(debian/glibc)** 实测：**glibc 与 Python 一致，macOS libc 是异类**
（glibc 测 462 个值 0 分歧；macOS 1 处分歧）。

### 影响

| 情形 | 后果 |
|---|---|
| 题目数据**不含**这类值（如 `5060` 现状） | **无影响**（`1000000*1000000 → 1e+12` 两边都同意）|
| 题目数据**含** `*00005` 类值 | ⚠ **`check_bytes.py` 会报假失败**（本机 C++ vs Python 不一致，但两者都"对"各自的 libc）|
| 换评测机（Linux/glibc）| ✅ 本机 Python 与评测机一致；**本机 C++ 的这个输出才是要担心的** |

### 纪律

> **凡输出用 `%g` / `cout << double` 默认格式的题，
> 本机 C++ 的输出【不能】直接当作参照** ——
> 必须意识到本机 libc 可能是异类。

应对：
1. 优先用 **Python 的 `'%g'`** 作为参照（与 glibc 一致）
2. 若怀疑，用 **docker(debian)** 跑 glibc 版对照
3. 在题解里注明 `%g` 的**尾随零去除**是 glibc 行为（评测机行为），
   而**不是** POSIX 强制行为（macOS 就是一个反例）

### 这是「本机 C++ 参照不可信」的第 4 次实证

| # | 本机与评测机的差异 | 处置 |
|---|---|---|
| 1 | `/usr/bin/g++` 是 **clang**（无 `bits/stdc++.h`） | 必须用 `/opt/homebrew/bin/g++-16` |
| 2 | `/usr/bin/python3` 是 **3.9.6**（无 `type X = ...`） | 闸门自动选 `python3.14` |
| 3 | `printf("%.3f")` 的舍入行为需实测（`5025`） | 已实测与 Python 一致（half-even）|
| **4** | **`%g` 不去科学计数法尾随零** | **本条 —— 用 Python `%g` 作参照** |

⇒ **共同纪律**：**本机工具链只是「一个实现」，不是「标准」。**
凡涉及**格式化输出的细节**，都要问一句「**评测机上会怎样**」。

## T19. 修正：`printf("%.Nf")` 是「对**二进制值**精确舍入」，不是「十进制平局取偶」

### 背景

`5025`（数据统计）的结论曾写作：

> 「C++ `printf("%.3f")` 与 Python f-string 都采用 **IEEE binary64 的 round-half-even（平局取偶）**，
>  即平局（恰好 $x.xxx5$）时向上还是向下取决于保留位的奇偶。」

**方向是对的**（它明确说了 binary64），但**容易被读成「十进制平局 ⇒ 取偶」**。

### `5057` 的 worker 给出了更精确的刻画

在 **1960 个十进制平局点**（$w \times$ 单价恰为 $x.xx5$ 的 $w$）上实测：

| 与哪种规则一致 | 数量 |
|---|---|
| **half-even** | **564** |
| **half-up** | **416** |
| **两者都不同** | **532** ← **大多数** |

**反例（机理）**：

```
w = 20.25，单价 1.98
十进制精确值 = 40.095            ← 十进制的「平局」
double 实际值 = 40.094999999999998863…   ← 略小于 40.095（二进制无法精确表示）
printf("%.2f") 对【二进制值】舍入 ⇒ 40.09
十进制 half-up ⇒ 40.10；十进制 half-even ⇒ 40.10（因为保留位 9 是奇数）
⇒ printf 与两者都不同
```

### 正确的表述

> `printf` / f-string 对**浮点变量的实际二进制值**做**精确舍入**（round-to-nearest, ties-to-even
> **在该二进制值上**）。当该二进制值**恰好**等于十进制平局（如 $1/16 = 0.0625$、$3/16 = 0.1875$
> 这类**二进制可精确表示**的值）时，才表现为「十进制平局取偶」；
> 对**二进制不可精确表示**的值，结果与十进制 half-up **和** half-even **都可能不同**。

### 对写题解的影响

| 写法 | 评价 |
|---|---|
| 「printf 是四舍五入」 | ❌ 错（`5025` 已纠正）|
| 「printf 是十进制平局取偶」 | ⚠ **不准确**（1960 个十进制平局点中 532 个两者都不是）|
| 「**printf 对二进制值精确舍入**；两者（C++/Python）实现一致」 | ✅ **准确** |

**实用结论不变**：C++ `printf` / `cout << fixed` 与 Python f-string
在**大量实测点**上**逐字节一致**（`5025`：5,050,100 组；`5057`：100001 值 + 10 个二进制中点）
⇒ **跨语言无需兼容层**（`T7` 的结论仍然成立）。
变的只是**机理表述**。

## T20. 「通过型」检查都要有**对照组** —— 证明检查本身有效

### 问题（`5064` 的 worker 提出并实践）

跑一个检查得到「通过」时，有两种可能：

1. **被测对象真的没问题**
2. **检查根本没在工作**（探针失效、参数不对、被优化掉）

**只报告 (1) 是不够的** —— 必须排除 (2)。

### 做法：写一个**确定会被抓的对照组**，用同一套检查跑

对照组源码（单独放一个文件，避开嵌套 heredoc）：

```c
/* /tmp/control.cpp —— 强制触发 signed overflow */
#include <limits.h>
#include <stdio.h>
int main() { int x = INT_MIN; printf("%d\n", -x); return 0; }
```

```bash
g++ -fsanitize=undefined -o /tmp/control /tmp/control.cpp && /tmp/control
# 预期输出：runtime error: negation of -2147483648 cannot be represented ...
```

| 对照组 | 被测对象 | 结论 |
|---|---|---|
| **报错** | 通过 | ✅ **确实没问题**（探针有效）|
| 报错 | 报错 | ❌ 有问题 ⇒ 报告 |
| **不报错** | 通过 | ⚠ **探针失效 ⇒ 整条结论不可信** |

### `5064` 的两个互补证据（同一天、同一道题）

| 实验 | 做法 | 结论 |
|---|---|---|
| **`V9` + 对照组** | 对照组（`INT_MIN` 取反）确实报错 | ✅ **UBSan 探针有效** ⇒ 被测的「无 UB」可信 |
| **`V1c` 证伪闸门** | 把输出换成硬编码 `cout << 10` | ❌ **字节比对闸门仍然全过** ⇒ **闸门对此完全无效** |

⇒ 两个实验合起来说清了「**哪些检查可信、哪些不可信**」：
`V9`（UBSan）**有效**；字节比对闸门**对硬编码无效**。

### 推广到所有「通过型」判据

| 判据 | 对照组怎么做 |
|---|---|
| `check_bytes.py` | 故意改错一个字节 ⇒ 应报失败 |
| `V2` 字面量集合 | 故意把答案硬编码进去 ⇒ 集合应变化 |
| `V4` 结构不变量 | 故意破坏一个 token ⇒ 应报异常 |
| `V6` 异源对拍 | 故意改错正解 ⇒ 应出现分歧 |

⇒ **`V1c` 本质上就是「字节比对闸门」的对照组。**

**纪律**：报告「某项检查通过」时，若该检查是**本题结论的唯一支撑**，
**必须附上对照组结果**，否则该结论不可采信。

## T21. 「解数」是有歧义的 —— 必须写明**口径**

### 现象（2026-10-08，`5061`）

父会话在任务卡里给了一张「每种 $x$ 的解数」表（$x = 1..19$）：

```
1:0  2:0  3:0  4:1  5:1  6:1  7:0  8:1  9:1  10:2
11:1 12:2 13:1 14:2 15:2 16:3 17:2 18:3 19:2
```

worker 独立复算后指出：**这张表是「任意解」口径**，而 `index.md` 说的「多解」是
**「笔数最大」的最优解口径**：

| $x$ | 任意解数 | **最优解数** |
|---|---|---|
| 12 | 2 | **1** |
| 16 | 3 | **1** |
| 17 | 2 | **1** |
| 18 | 3 | **1** |

⇒ 两套口径下「$x = 4..200$ 中多解的 $x$ 个数」：**189（任意解）vs 95（最优解）**。
`index.md` 的 **95 ✅ 是对的**；父会话的表**不是错的，而是另一个口径** ——
但**表格上没写口径**，所以会误导。

### 纪律

> **凡出现「解数 / 方案数 / 多解个数」这类计数，
> 必须写明计数的是【哪一类解】。**

对本题至少有三种口径：
1. **任意解**（忽略笔数约束）
2. **最优解**（笔数最大的那些）
3. **可行 $x$ 的个数**（可解性，而非解数）

同理，「多解题」这个判定也依赖口径：
- 「存在多个合法输出」= 多解（与最优性无关）
- 「存在多个**最优**输出」= 更窄的多解

### 附带：`V8` 的新层次 —— 候选可以成**等价类**

`5061` 的 tie-break 有 6 个候选，但 worker 发现它们**分成两个等价类**：

```
类 1: (a) 字典序最大 ≡ (d) 优先多买 4 元 ≡ (e) 5 元最少
类 2: (b) 字典序最小 ≡ (c) 优先多买 5 元 ≡ (f) 4 元最少
```

**类内恒等是数学恒等式**（因为 $c = k-r+a$、$b = r-2a$ 都是 $a$ 的**单调函数**），
不是采样巧合；两类在 $x = 4..20000$ 上逐点不同。

⇒ **`V8` 的结论表述要改**：
不是「$k$ 个候选两两互斥 ⇒ 唯一确定」，
而是「**$k$ 个候选分成 $m$ 个等价类，类间可区分、类内不可区分**」
⇒ **「唯一确定」只能确定到类的粒度**。

**判据**：报告候选排除时，要说明
① 有几个候选 ② **分成几类** ③ 哪一类被确定 ④ **类内为何无法区分**（恒等/巧合）。

## T23. 浮点输出的敏感点可能是**乘法结合律**，而不是舍入模式

### 现象（`5068`，π = 3.14159）

题面要求输出圆的直径/周长/面积，各保留 4 位小数。共识是「要小心舍入模式」。
worker 却发现**真正的敏感点不是舍入模式，而是乘法的结合顺序**：

```
r = 65.0：
  精确十进制的 half-even  ⇒ 面积 13273.2177 8
  double 路径（两侧一致）  ⇒ 面积 13273.2177
  差一个末位！
根因：3.14159 作为 double 略【小于】314159/100000，
      把乘积从平局点上方压到【下方】⇒ 舍入方向反转
```

**全扫 $r = k/10^4$（100,301 个值）**：

| 口径 | 不同的数量 |
|---|---|
| 原始 `double`（`(PI*r)*r` vs `PI*(r*r)`） | **35,056（35%）** |
| 经 `%.4f` 格式化后 | **6（0.006%）** |
| **真实 10 个测试点** | **0** ✅ |

⇒ **风险来自写法**（结合顺序），不是舍入模式。

### 与既有纪律的关系

| 编号 | 教训 |
|---|---|
| `T7` | 为不存在的问题加**适配层**（`Decimal + ROUND_HALF_UP`）会引入 50% 分歧 |
| `T19` | `printf` 是**对二进制值**精确舍入，不是十进制平局取偶 |
| `T18` | macOS libc 的 **`%g`** 与 glibc/Python 不同（`%.4f` 经实测**无此问题**） |
| **`T23`** | **敏感点可能是【运算顺序】** —— 同一公式不同写法在极少数值上差一个末位 |

### 纪律

> 涉及浮点输出时，除了「舍入模式」，还要检查**同一公式的不同写法**：
> `(PI*r)*r` vs `PI*(r*r)` vs `r*r*PI`。
> 三者**不等价**（浮点乘法不满足结合律）。

**检查方法**（成本低、收益高）：
1. **穷举扫描**一个足够密的 $r$ 网格（本题 $r = k/10^4$，10 万级）
2. 对每种写法，统计**格式化后**不同的数量
3. ⇒ 若真实数据命中 0 个，则**结论是「数据不敏感」**，
   但必须**如实说明**「换数据可能敏感」

★ **注意区分两个量**：
- 35% 是「**原始 double 值**不同」
- 0.006% 是「**格式化输出**不同」

## T24. 编译器优化会改变浮点结果：**FMA 收缩**（`-O2` 的 `fmsub`）

### 现象（`5067`，`n - 0.8m`）

worker **看了 `-O2` 的汇编**，发现：

```
n - m * 0.8   被收缩成一条   fmsub d31, d31, d30, d29
⇒ 产生极微小的负误差 ⇒ 输出 -0.00（若无归零逻辑）
```

对照实验：**`-O2` 有、`-O0` / `-ffp-contract=off` 无** ⇒ 确认是**编译器收缩**所致。

### 为什么危险：它会**改变输出**

| 输入 | 现象 |
|---|---|
| **整数域**（本题数据） | 14M+ 组窗口内 **0 分歧** ⇒ 无风险 |
| **小数域** | ⚠ `261.115 366.7` ⇒ **C++ `-32.24` vs Python `-32.25`**（第 2 位小数不同！）|

⇒ **同一份代码在 `-O0` 与 `-O2` 下可能给出不同输出**；
**同一公式在 C++ 与 Python 下也可能不同**（C++ 有 FMA 收缩，Python 没有）。

### 纪律

> 涉及浮点的题，除了「舍入模式」与「运算顺序」（`T23`），
> 还要考虑**编译器是否会做 FMA 收缩**。

**检查方法**：
1. **看汇编**：`g++ -O2 -S` 后 `grep -i fma/fmsub`
2. **对照编译**：`-O0` / `-ffp-contract=off` 下跑同样的数据，比较输出
3. **跨语言对照**：C++（可能收缩）vs Python（无收缩）
4. ⇒ 若真实数据上无分歧，**仍需如实说明「换数据域可能分歧」**

### 与 `T23` 的分工

| 编号 | 敏感点 |
|---|---|
| `T23` | **运算顺序**（`(PI*r)*r` vs `PI*(r*r)`）—— 源码层面 |
| **`T24`** | **编译器收缩**（FMA）—— 编译选项层面，**源码看不出来** |

⇒ `T24` 更隐蔽：**源码相同、语义相同，但 `-O2` 与 `-O0` 结果不同**。

### 附带：`5067` 还给出了「舍入歧义不存在」的**数学证明范式**

```
v = n - 4m/5  ⇒  分母 ∈ {1,5}  ⇒  小数位 ≤ 1
穷举证：到最近平局点的距离【恒 ≥ 0.005】
double 实测最大误差 9.31e-11
⇒ 误差比边界小 5.4 × 10^7 倍
```

**这是「证明不存在」而非「实测没发现」的标准形态**（`T17` 的最高层次）：
① 限定量化（小数位 ≤ 1）② 穷举下界（距离 ≥ 0.005）③ 误差上界（9.31e-11）④ 比较得出裕度。

|---|---|---|---|

| 题型 | 不变量 |
|---|---|
| 守恒类（分糖、搬移） | **总和守恒**（或总和减去已知丢弃量） |
| 计数类 | **总和 ≤ 输入规模**、非负 |
| 排序类 | **多重集相等**（输出与输入的元素计数一致） |
| 图论类 | 边数 ≤ 点数²/2、度为偶（欧拉回路）等 |

### 附带：`od -c` 的读法陷阱

⇒ **更安全的读法**（按可靠性排序）：
1. `python3 -c "print(open('f','rb').read())"` —— **直接看 `repr`**（空格显示为 `b' '`）
2. `sed 's/ /·/g'` —— **把空格换成可见字符**
3. `od -An -c` —— 仅在需要看非打印字符时用，且**要数清字段**

## T27. 数据由 `std` 生成时，**10/10 PASS 只是「回归锁」，不是「独立验证」**

### 现象（批次十七，`5071`）

> 即 10 个 `.out` 全部**由 `std.cpp` 自己产出**；而题面 `content.md` 对前导零**完全沉默**，
> 样例 `123→321` **不含任何前导零信息**。

以前只知道「数据由被测程序生成 ⇒ 有循环论证风险」。
worker 把结论**分层**了：

| 结论 | 强度 | 依据 |
|---|---|---|
| 实现与 `std` **一致** | ✅ **确证** | 10/10 逐字节 |
| 该规则**客观正确**（如 `100` 应输出 `1` 而非 `001`） | ⚠ **未确证** | 题面沉默、样例无信息 |

⇒ **10/10 PASS ≠ 「规则正确」，只等于「与 std 一致」。**

### 纪律

> 当结论是「**题面未明说、只能从数据推断**」的规则时，
> 必须**显式标注证据强度**，并说明：
> ① 数据是怎么生成的（查 `data.py` 的 `output_gen`）
> ② 题面/样例是否提供了独立信息
> ③ 若都没有 ⇒ **结论是「与 std 一致」，而非「规则正确」**

★ 这与 `T17`（三个证明层次）呼应：
**「数据支持」< 「题面支持」< 「外部权威支持」**，

## T29. 判据要**可闭式计数**，而不是「穷举了很大一片」

### 现象（批次十七，`5072`）

我在任务卡里问「4 位小数上是否存在平局点」，并暗示「穷举或构造验证」。
专家的结论是「不存在」（错），而 worker 给出了**闭式刻画**：

设 $g=\gcd(x,y)$，$x=ga$，$y=gb$，$\gcd(a,b)=1$：

$$v \cdot 10^4 = 850000 + \frac{20000a}{a+b}$$

该值为半整数 $\iff \dfrac{40000a}{a+b}$ 是**奇**整数
$\iff (a+b) \mid 40000$（因 $\gcd(a,a+b)=1$）且商为奇

$$\boxed{a+b \in \{64,\;320,\;1600,\;8000,\;40000\} = 64 \cdot 5^j,\; j=0..4}$$

**双重验证**：
1. **闭式计数**：$0 \le x,y \le 10^6$ 内共 **2 901 234** 个平局点（占 ~0.29%）
2. **穷举交叉验证**：$[0,1500]^2$ 网格内**预测 2348 个、穷举 2348 个、不一致 0 个**

### 为什么这比「穷举一大片」强

| 方法 | 结论 | 可外推 |
|---|---|---|
| 穷举 $[0,1500]^2$ 没找到 | 「小范围内没有」 | ❌ 不能外推到 $10^6$ |
| **闭式刻画** | 「**恰好**是 $a+b \in \{64,\dots,40000\}$」 | ✅ 可精确计数、可定位最小点 |

★ 闭式刻画还给出**可操作信息**：最小平局点 $(1,63) \to 85.03125$；
$x,y \ge 100$ 的最小平局点 $(100,156)$ ⇒ **可用于构造测试数据**。

### 纪律

> 问「是否存在 X」时，**不要只满足于「穷举了一片没找到」**，
> 而要**给出 X 的刻画**（充要条件），再用穷举**验证该刻画**。

⇒ 这与 `T17`（三个证明层次）一致，但更进一步：
**闭式刻画 > 穷举声明域 > 抽样测试**。
穷举是**验证刻画**的手段，不是**代替刻画**的结论。

全部 12 点：out值 == out排列的 makespan == Johnson 最优  ✅
全部 12 点：S1 全部在 S2 之前 ✓   S1 内 A 升序 ✓   S2 内 B 降序 ✓
判据：all(A[s1[i]] <= A[s1[i+1]]) 与 all(B[s2[i]] >= B[s2[i+1]])
```

⇒ 专家**误读了列**（把 A 值或编号当成 B 值）。**数据没有坏。**

### 为什么这类论断要特别当心

| 论断 | 后果 |
|---|---|
| 「我不确定」 | 无害 |
| 「这里有个细节」 | 无害 |
| **「数据是坏的 / 出题人写错了 / std 有 UB」** | ★ **会写进文档、误导后续所有读者**，而且**很难被推翻**（读者倾向于相信「发现缺陷」的人） |

★ 这是 `T28`（编造精确数字）的**同类**：都是「**看起来更有信息量的论断**」压制了复核。
**「我发现了一个缺陷」比「我没发现问题」更像有价值的结论** ⇒ 因而更少被质疑。

### 纪律

> 凡要写下「**数据/题面/参考实现有缺陷**」，必须先给出一条**机械判据**，
> 且该判据能**一行跑出来**、**可被任何人复现**。

**本题的正确判据**：
```python
all(B[s2[i]] >= B[s2[i+1]] for i in range(len(s2)-1))   # S2 内 B 非增
makespan(A,B,out_perm) == johnson_optimal(A,B,n)         # 值最优
```

**若给不出这样的判据 ⇒ 只能写「我未能复现/我观察到 X，原因未明」，不能写「数据坏了」。**

### 附带：`1425` 的 spj 真正理由是「**并列次序不可复现**」

父会话试了 **5 种 tie-breaker**，**没有一个匹配 `.out`**（最多 4/12）：

| 候选 | 匹配 |
|---|---|
| `S1:(A,id↑) S2:(B↓,id↑)` | 3/12 |
| `S1:(A,id↓) S2:(B↓,id↓)` | 3/12 |
| `S1:(A,id↑) S2:(B↓,id↓)` | 3/12 |
| `S1:(A,id↓) S2:(B↓,id↑)` | 4/12 |
| 纯 stable（按原下标） | 3/12 |

⇒ **结构对、值对，但并列次序是 `std::sort`（不稳定）的副产物**。
⇒ 这才是 spj 的理由：**同样最优但并列次序不同**的合法解会被逐字节比对判错。

```

⇒ **数据本身是 CRLF**，而实现输出 LF ⇒ `check_bytes.py` **永远报错**。

★ 与 `5043` 的区别：`5043` 是**题面样例**的代码块是 CRLF（数据是 LF）；

> 1. **不要**改实现去输出 CRLF（那会牺牲可移植性）
> 2. **如实记录为数据缺陷**（题号 + 点数 + 字节证据）
> 3. 若该题**同时**是多解题 ⇒ **spj 会自然消化 CRLF**（spj 按文本解析）

### 附带：spj 的建立流程（第 2、3 个 spj 的经验）

```
① 判断是否真的多解 —— 看题面有没有「一种 / 任意 / 某一个 / 不唯一」
   ★ 但「题面说多解」≠「闸门一定错」：若 .out 恰好与常见实现一致，逐字节也能过
   ⇒ 必须【实测】哪些点因多解而失败

② 找差异的【形状】—— 本题：点数相同、差异全是同党伙伴对（2i-1 / 2i）
   ⇒ 形状确认了「双方都合法」

③ 写独立判据 —— 【不拿 got 与 want 比较】，而是独立验证 got 的合法性
   · 1519：用 Kosaraju 独立解 2-SAT 判可满足性
   · 1425：独立算 Johnson 最优 makespan

④ **必须做对照组** —— 有 spj 12/12 vs 无 spj 3/12（`T20`）
   ⇒ 证明 spj 确实在起作用，而不是「闸门本来就过」
```

## T34. 「上界」要区分**题面声明的上界**与**真实可达上界**

### 现象（批次十八，`1565`）

题面写「结果**不超过 $2^{31}$**」= 2,147,483,648，
而 `INT_MAX` = 2,147,483,647 ⇒ **题面上界恰好越界 1**。

⇒ 很自然的结论是「**必须** `long long`」。**专家初稿就是这么写的（第 46/65 行）。**

**worker 证明这是错的**：

```
n = 32767, |a_i| ≤ 10^6  ⇒  max Σf_i ≤ 【9,499,939】
（用 recurrence 上界推导，并用 L ≤ 32 的穷举暴力验证该上界确实 ≥ 暴力最大值）
INT_MAX = 2,147,483,647
⇒ 相差 【226 倍】⇒ 【int 实际上是安全的】
```

⇒ **用 `ll` 是规范/防御性选择，不是正确性要求**（`T5`）。

### 纪律

> 题面声明的上界往往**很松**（作者给的是「肯定不会超」的保守值）。
> 判断「会不会溢出」时，应算**真实可达上界**（从数据范围与算法递推推），
> 而不是只看题面数字。

**判据**：
| 层次 | 结论 |
|---|---|
| 题面上界 > `INT_MAX` | ⚠ 需要进一步分析 |
| **真实可达上界 > `INT_MAX`** | ⇒ **必须**用 `ll`（正确性要求） |
| 真实可达上界 ≪ `INT_MAX` | ⇒ 用 `ll` 是**规范选择**（`T5`） |

★ 与 `5066`（三数和 ≤ 3×10^6，临界值 715827883）是**同一纪律的两次应用**。

## T35. **判据本身要先验证「鉴别力」** —— 我的一次零鉴别力判据（错误 #19）

### 现象（批次十八，`1519`）

父会话（我）在派 R2 前，用一个判据确认「程序与 `.out` 的差异都是合法的同党伙伴对」：

```python
# 我的判据
{ours[i], theirs[i]} == {2*i+1, 2*i}      # 逐行比较
```

它给出「全部通过」⇒ 我据此写下：

> `spo8/9/10/11/13` 上程序与 `.out` 的点数相同，差异全是**同党伙伴对**
> ⇒ **两者都是合法委员会**

**worker 证伪**：

```
spo13: 我们的委员会冲突数 = 0，但 .out 的冲突数 = 【3907 / 16000】
       m/4 = 16000/4 = 4000  ⇒ 3907 ≈ 4000
⇒ 【spo13.out 与「随机委员会」不可区分】
⇒ spj 独立拒绝它：厌恶对 (2087, 3608) 同时入选（spo13.in 第 11 行原文）
```

### 根因：**我的判据鉴别力为 0**

```
{ours[i], theirs[i]} == {2i+1, 2i}
⇒ 对【任意两个】「升序 + 每党恰 1 名」的委员会【必然为 True】
   —— 因为两个都是升序、每党恰 1 名 ⇒ 第 i 行放的就是第 i 党的人
   ⇒ 判据恒真，与内容无关
```

★ **判据恒真 ⇒ 它「通过」不代表任何事。** 这与 `T20`（每个通过型判据都要有对照组）
是**同一个纪律**，但这次的对象是**我自己的判据**，而不是闸门。

### 正确的判据应该是什么

```python
# ① 独立验证【双方】的合法性（而不是比较它们的「形状」）
ours_conflicts  = count_conflicts(inp, ours)
theirs_conflicts = count_conflicts(inp, theirs)
# ② 只要有一方非法 ⇒ 是数据缺陷或程序缺陷，不是「多解」
```

★ 关键区别：
| 我的判据 | 正确判据 |
|---|---|
| 比较**两个解的形状**（同党伙伴对）| **各自独立验证合法性**（厌恶对冲突数）|
| 恒真 | 有分辨力（spo13 得 3907）|

### 纪律

> **写下任何判据之前，先问：这条判据在什么情况下会给出「不通过」？**
> **若答不出来 ⇒ 该判据的鉴别力为 0，它的「通过」不构成证据。**

**自检方法**（机械）：
1. 构造一个**应当被拒绝**的样本，喂给判据 ⇒ 若仍通过 ⇒ 判据无效
2. 或在**明显非法**的输入上跑一遍（如 `spo13.out`）⇒ 应报错

★ 这是 `T20` 的**元层次**：
```
T20  每个「通过型」检查都要有对照组
T30  把闸门自身的分辨力也测出来
T35  【我自己的判据】也要先测分辨力
```

## T36. 数据缺陷第 19 类：**期望输出违反题目约束**（`.out` 本身非法）

### 现象（批次十八，`1519` 的 `spo13`）

```
spo13.in:  n = 8000, m = 16000
spo13.out: 8000 个代表编号（升序、每党恰 1 名）
★ 但【有 3907 个厌恶对同时入选】⇒ 该委员会【非法】

  ⇒ .out 与「随机委员会」不可区分（随机委员会期望约 m/4 个冲突）

> 3. **`.out` 非法**（数据缺陷）

★ 这也说明 **spj 的一个重要副作用**：它会**暴露坏的 `.out`**。

## T37. 题面的**数据范围声明**与**数据的实际值域**是两件独立的事（`T33` 的扩展）

### 现象（批次十八，`1519`）

- 题面说代表编号「从 1 编号到 $2n$」⇒ 值域应为 `1..2n`
- `spo13.in` 的**实际值域只到 7999**，而 $2n = 16000$
  ⇒ 8000 个党里 **4014 个完全不受约束**
- ★ 而 `spo13.out` 却横跨到 **15999** ⇒ **旁证 `.out` 是坏的**

### 纪律

> 拿到数据后，先算一遍**实际值域**，与题面声明的范围对比：
> - 实际值域 **窄于** 声明 ⇒ 可能有意（如 `T16` 的 `5017`），也可能数据退化
> - 实际值域 **宽于** 声明 ⇒ **数据缺陷**（如 `T33` 的 `1565` 负值）
> - 实际值域 **远窄于** 声明 ⇒ 该点的**鉴别力可能不足**（很多约束未被触发）

★ 这与 `T33` 合起来是**同一条纪律的两个方向**，也与 `T34`（上界要区分声明与真实）
构成一组：**题面声明的每一个范围/上界，都要用数据实测校验。**

## T38. **空间**也是承重维度 —— 只测时间会漏掉 MLE

⇒ 静态段 **484,327,424 B ≈ 480 MB**。

worker 实测 `peak RSS`：

4. **补充**：`V1` 反事实 + `V6` 异源暴力 + `V9` UBSan + 对照组（同前）
5. **如实记录**：在 `index.md` 里写明「**本题官方期望输出缺失，

★ 对**有唯一答案**的题（如 `3077` 虫食算，若题面保证唯一），
跨源一致 + `V1` 反事实是**相当强**的证据。
★ 对**多解**的题，还需 spj。

### 纪律

> **拿到一道题，第一件事是确认「期望输出存在且完整」。**

★ 这是 `T1`（闸门静默空转）的**同类**，但更严重：
`T1` 是「数据文件找不到 ⇒ 闸门假装通过」，
`T40` 是「期望输出不存在 ⇒ 闸门无法工作」。

## T42. 数据缺陷第 22 类：**题面明确要求输出顺序，但数据不满足该顺序**

### 现象（批次十九，`3166` 旅行）

题面【输出格式】：

> 按**升序**顺序输出**所有**满足条件的路线列表。

实测 11/11 点 **全部不是字典序**：

```
trip1.in  = abcabcaa / acbacba   （LCS 长度 = 5，共 7 个不同 LCS）
trip1.out = ababa abaca abcba 【acbca】 acaba acaca acbaa
字典序     = ababa abaca abcba 【acaba】 acaca acbaa 【acbca】
⇒ 差别只在 acbca 的位置 ⇒ .out 违反题面的「升序」要求
```

★ **旁证：题面的【输出样例】只给了 6 行**（缺 `acbca`），
而数据的 `trip1.out` 有 **7** 行 ⇒ **样例本身也不完整**。

### 与 `T41` 的区别

| 编号 | 题面与数据的关系 |
|---|---|
| `T41` | **题面与数据是两道不同的题**（`3165`）|
| **`T42`** | **题面与数据是同一道题，但【输出顺序】不一致**（`3166`）|

⇒ `T42` 比 `T41` 轻，但**同样致命**：逐字节比对会把**正确**（按题面升序）的输出判错。

### 处理方式

**建 spj，判据 = 「输出集合 == 全部不同 LCS 的集合」**，
并**只报告**是否字典序、**不据此判错**（因为数据自身不满足，无法作标准）。

★ 关键设计：spj 的第 ④ 条（顺序）**只报告不判错** ——
这是「**判据要区分「硬约束」与「软约束」**」的一个实例：
- **硬约束**：集合完整（少了/多了/重复了都错）
- **软约束**：顺序（题面要求，但数据违反 ⇒ 无法执行）

### 纪律

> 题面里凡出现「按 X 顺序输出」「从小到大」「字典序」等**顺序要求**，
> 都要**用数据实测校验**：
> ```python
> lines == sorted(lines)          # 字典序
> ```
> - 若数据**满足** ⇒ 顺序是**硬约束**，实现必须遵守
> - 若数据**不满足** ⇒ **数据缺陷**，需 spj 且顺序降级为**软约束**

★ 这与 `T29`（闭式刻画 vs 穷举）呼应：
**「题面声明」与「数据事实」不一致时，要明确标注哪一个是硬约束。**

## T45. **操作计数指纹** = 复杂度的机械证据（不是「看起来是 O(N log N)」）

### 现象（批次十九，`3165` 的 `V7`）

worker 用**计数埋点**证明实现真的是 $O(N \log N)$，而不是偷换成 $O(N^2)$：

```
point 10 (N = 200000):
  kth_calls = 200000
  kth_steps = 3,600,000
  add_steps = 1,856,000
★ kth_steps / N = 18 = ⌈log₂ 200000⌉      【精确吻合】
⇒ 库函数 / O(N²) 替换不可能产生这个指纹
```

### 为什么这比「复杂度分析」强

| 手段 | 强度 |
|---|---|
| 读代码说「这是 BIT，所以 $O(N\log N)$」 | ⚠ 可能被库函数/偷懒实现替换而不自知 |
| **计数埋点 + 与理论值精确吻合** | ✅ **机械证据**，无法伪造成立 |

★ 关键：**$\lceil\log_2 N\rceil$ 是精确的整数**（18 对 $N = 200000$），
不是「量级相当」⇒ **可以逐位比对**。

### 纪律

> 当「复杂度」本身是被验证对象时（如题面要求 $O(N\log N)$、或数据规模卡常数），
> **在实现里埋计数器**，跑真实数据，与理论公式**精确比对**。

**可用的指纹**（按题型）：
| 题型 | 指纹 |
|---|---|
| 树状数组/线段树上二分 | `kth_steps / N == ⌈log₂ N⌉` |
| 比较排序 | 比较次数 $\approx n\log n$（且**交换次数 ≡ 逆序对数**） |
| 线性筛 | `composite_calls == n` 次内层循环 |
| 并查集 | `find` 路径总长（带压缩应 $\approx n$，不带则 $\approx n\log n$） |
| BFS/DFS | `edges_visited == |E|`（恰一次） |

★ 这是 `V7`（算法指纹）的**量化版**：
`V7` 说的是「用操作计数证明用的是哪种算法」，
`T45` 补的是「**以理论公式为基准做精确比对**」。

## T46. 「点粒度无分辨力」时，**改用 token 粒度**

### 现象（批次十九，`3165` 的 `V8`）

worker 实现 6 个候选解释，发现：

> 只有「倒序 + 第 $P_i$+1 个**空位**（0-indexed）」能通过；
> **但点粒度的失败集无法区分（全是 10/10）** —— 所有候选都挂全部 10 点。
> **有分辨力的是【token 列】**：各候选的**首个分歧 token 列向量**互不相同：
> ```
> va/vb → fd0,1,0…
> vc    → fd2,0,1…
> vc2   → 全 fd0
> vd/vg → 全 fd-1
> ```

### 为什么重要

`V8`（相邻候选排除法）常用「失败点集合」来区分候选。
但当**所有候选都在同一批点上失败**时，点集合**退化**（全部相同）⇒ **无分辨力**。

⇒ 必须**细化到更细的粒度**：token / 字节 / 首个分歧位置。

### 纪律

> **`V8` 的失败集若在某个粒度上退化（所有候选相同），就换更细的粒度重做。**

| 粒度 | 适用 |
|---|---|
| 点（`.in` 文件） | 常规 —— 候选间失败点数不同时 |
| **token / 行 / 列** | 点粒度退化时 |
| **首个分歧的字节偏移** | 仅空白/格式差异时 |
| **逐字节 diff** | 最后手段（`check_bytes.py`） |

★ 与 `T13`（token 级比较对空白免疫）呼应：
**粒度选择决定了判据的分辨力**，而分辨力是 `T35` 要求的**前提**。

## T47. **验证器本身也要被验证** —— worker 的第一版验证器有 bug

### 现象（批次十九，`3064`）

worker 为了验证「题面保证唯一解」，自写了一个**与 DLX 完全不同的**求解器
（候选位掩码 + 唯一候选传播 + 隐式唯一值 + MRV 分支）。

**第一版有 3 处 bug**：

- `peer` **缓冲溢出**
- **回溯未撤销传播**

⇒ 它**一度报出「0/2 解」** —— 而真实答案是 10/10 组**恰好 1 解**。

worker 的**自检方法**：
> 「对一个**已知满解**跑求解器，应得 **1 解**」

### 为什么这是 `T35` 的延伸

| 编号 | 层次 |
|---|---|
| `T20` | 每个「通过型」**检查**要有对照组 |

| `T35` | **我自己的判据**要先测鉴别力 |

> **任何自写的验证器/暴力/对拍程序，上生产前必须跑一组「已知答案」的输入。**

⇒ **自检把假警报挡在了源头。**

## T48. 行数统计用 `split()` 会**多算 1** —— 我的一次读数错误（#22）

### 现象（批次十九，`3064`）

父会话说「`1.in` 有 **17** 行、`1.out` 有 **18** 行」。worker 实测：

```
1.in  bytes=272  wc -l = 16  len(b.split(b'\n')) = 17
1.out bytes=273  wc -l = 17  len(b.split(b'\n')) = 18
```

⇒ **`b.split(b'\n')` 在「文件以 `\n` 结尾」时会多产生一个尾部的空串。**
⇒ `.in` **物理是 16 行**（父会话报的 17 是假象）；
⇒ `.out` **物理是 17 行**（16 行数独 + 1 个空行）—— 这个「多 1 行」是**真的**。

### 纪律

> **统计行数用 `wc -l` 或 `content.count(b'\n')`，不要用 `len(content.split(b'\n'))`。**

| 方法 | 语义 |
|---|---|
| `content.count(b'\n')` | **换行符个数**（= 物理行数，前提是文件以 `\n` 结尾）|
| `wc -l` | 同上 |
| `len(content.split(b'\n'))` | 换行符个数 **+ 1**（若以 `\n` 结尾）|
| `len([l for l in text.splitlines() if l])` | **非空行数** |

★ 这与 `T26`（定宽字段解析）同类：
**「用哪个函数」决定了读出的数字**，而错误的数字会一路传到文档里。
★ 本仓已积累的「读数」类错误：
```
T10/T16/T22  head 截断 ⇒ 结论错
T26          od -c 字段边界误读 ⇒ 数值错
T44          head -c 截断 ⇒ 「全是 0」错
T48          split() 尾空串 ⇒ 行数多 1
⇒ 全部是「读数」，且全部是我犯的
```

父会话的任务卡问「`W` 用 `int` 是否安全」，worker 发现**问题本身不够细** ——

|---|---|---|
| **算术**（`current_sum + gift[idx] <= W`）| **必须 `ll`（正确性要求）** | 全 `int` 版被 UBSan 在 **5/9 点**抓到实打实的 `signed integer overflow`；`gift1 → 2147483012`（应 `2144708006`）|
| **状态表元素** | **可以 `int`（规范选择，为内存）** | 表内每个值都由「和 ≤ W」的递归产生 ⇒ 取值 ≤ W ≤ INT_MAX ⇒ 收窄不截断（9/9 逐字节相同）|

★ **且第二处的安全性是【有条件的】**：
```
构造反例 W = 3,000,000,000（超规格，> INT_MAX）
  int 表 → 2100000024
  ll 表/独立实现 → 3000000000
⇒ 【真的截断】
⇒ 条件「W <= INT_MAX」由题面保证 ⇒ 在题面范围内安全
```

### 纪律

> 问「要不要用 `ll`」时，**要指明是哪一处**：
> - **参与算术的中间量** ⇒ 看**最坏情况的中间值**（可能远超最终答案）
> - **存储结构里的值** ⇒ 看**该结构的取值上界**（常可由算法不变量收紧）

**判据表**：

| 位置 | 判断依据 |
|---|---|
| `a + b <= c` 之类的**先算后判** | 看 `a + b` 的**最坏值**（本题：$W + G_i$ 可达 $2\times$INT_MAX）|
| 存进表/数组的**值** | 看**算法不变量**（本题：表内值 ≤ W ≤ INT_MAX）|
| 计数器/下标 | 看规模（`n`、`m`）|

★ 这与 `T34`（上界要区分题面声明与真实可达）配合：
**「哪一处的上界」也要分清。**

### 附带：`T38`（空间是承重维度）的**最强实例**

worker 合成**合法最坏输入**（48 件、`W = INT_MAX`、前半 $2^{24}$ 子集全部合法）：

|---|---|---|

## T51. 我写的 spj 也有 bug —— DP 用错了量（`k ± |a-b|` 而非 `k + a / k + b`）

### 现象（批次二十，`3218`）

want: 45 4 7 11 12 13 16 17 18 20 22 26 30 ...
spj : 两队规模差为 10（45 vs 55），但【最小可达规模差为 80】⇒ 未达到「尽可能接近」
```

★ **荒谬**：`n = 100` 时「最小规模差 80」意味着 $k = 10$ 或 $k = 90$ ——

### 根因

```python
# 我的错误写法
diffs.append(abs(cnt[0] - cnt[1]))          # d = |a - b|
for d in diffs:
    for k in reach_set:
        nxt.add(k + d); nxt.add(k - d)      # ★ 错！k ± d 不是块的贡献
```
**正确**：每个连通块把**其中一个色类整体**分给队1 ⇒ 队1 的贡献是 $a$ **或** $b$：
```python
comps.append((cnt[0], cnt[1]))              # 存 (a, b)
for a, b in comps:
    for k in reach_set:
        nxt.add(k + a); nxt.add(k + b)      # ★ 正确
```

⇒ 修好后闸门 **56/56 通过**。

### 为什么自测没抓到

我的自测用例（`demo`）**只有一个连通块** ⇒ 单个块时 $k \pm |a-b|$ 与 $k+a/k+b$
**恰好等价**（差一个常数偏移）⇒ **单块样例无法暴露多块的累积错误**。

⇒ 与 `T47`（worker 的验证器有 bug）是**同一类**，但这次是**我自己**的。

### 纪律

> **spj / 验证器 / 暴力程序的测试用例，必须覆盖「多块 / 多分支」的情形。**
>
> 单元素、单块、单层的用例**几乎必然通过**，因为退化情形下错误公式往往等价。

**检查方法**：
1. 构造**至少 2 个连通块**的输入（本题：两组互不相识的独立团）
2. 构造**块大小不等**的输入（$a \ne b$）
3. 用**已知最优值**的输入反推（如「两队规模差必为 0」的完全图）

★ 更一般的判据（`T35` 的延伸）：

| 判据 | 能抓 | 抓不到 |

x[7,389]y[426,496] + x[42,391]y[16,185] + x[94,374]y[296,359] + x[427,484]y[11,388]
= 26740 + 58981 + 17640 + 21489 = 【124850】
```
逐点验证：50 点全覆盖、每点恰在 1 个矩形内、每矩形恰为其点集外接盒、
6 对矩形全部**严格**分离（最近一对间隔 35）。

**（ii）异源算法族**：候选矩形集合覆盖（177626 个候选）；
代价 < 124850 时**枚举为空** ⇒ 下确界。

**（iii）全叶子枚举**：合法值 = `124850, 128726, ..., 138895, 139108, ...`
⇒ 124850 最小，**139108 只是第 18 个**。

### ★★★ 最有力旁证：**两个同点集的点自相矛盾**

```
jxfg4.in 与 jxfg5.in 是【同一组 50 点】（逐字节同体，仅首行 `50 3` / `50 4`）
该点集最优：k=1→231345 · k=2→190942 · k=3→156041 · k=4→124850
⇒ jxfg4.out = 156041 ✅ 正确 ｜ jxfg5.out = 139108 ❌ 与之矛盾
```
★ 且 `139108` 恰等于「y 连续段切分」的值，**但**同模型给 `jxfg6 = 2134 ≠ 2106`
⇒ **不存在任何模型能同时产出全部 7 个 `.out`** ⇒ **`.out` 集合内部不自洽**。

### 与 `T36` 的区别

| 编号 | `.out` 的问题 |
|---|---|
| `T36` | **非法**（违反题目约束，如 `1519` 的 spo13 有 3907 个厌恶对同选）|
| `T40` | **缺失**（整体不存在）|
| **`T56`** | **次优**（合法但不是最优）|

⇒ 三者都会让「与 `.out` 逐字节比对」判错**正确**的程序。

### 纪律

> 当程序与 `.out` 不一致，且**程序给出更优的解**时，
> **不要默认程序错** —— 要独立验证：
> 1. **构造显式证书**（只凭输入，不依赖任何程序输出）
> 2. **异源算法族**求下确界
> 3. **穷举全叶子**看 `.out` 的值排第几
> 4. ★★ **找同输入/同结构的不同点做交叉对照**（本题：`jxfg4` 与 `jxfg5` 同点集）

★ 第 4 条是本题**最强**的判据：**两个点共用同一组数据，但 `.out` 自相矛盾**
⇒ 不需要任何算法就能判定「至少有一个 `.out` 是错的」。

1. 在 `index.md` 里**如实记录数据缺陷**（含真最优值与三条互证）
2. 保持**正确**的实现（给出 124850）
3. 接受闸门 **6/7**（这是**闸门的适用性边界**，不是程序缺陷）

**换个 n 就会挂。**

### 与 `5072` 的对比（同一逻辑的两次应用）

| 题 | 现象 |
|---|---|
| `5072` | 平局点存在 2,901,234 个，**真实数据恰好避开全部** ⇒ 「数据运气，不是实现安全」|
| **`3065`** | 92/100 个 n 有多解，**真实数据的 n 恰好全命中同一 tie-breaker** ⇒ 同 |

### 纪律

> **「闸门通过」对多解题意味着什么，要看题面：**
> - 题面说「任意一个」⇒ 通过**只说明**「我们的解恰好与 `.out` 相同」，
>   **不说明**「别的合法解也会通过」⇒ **数据运气**
> - 此时**必须**评估：「如果 OJ 用别的合法解做 `.out`，我们会不会挂？」

>    —— 即使当前数据 10/10
> ```

★ 与 `T55`（判据盲区互补成洞）呼应：
**逐字节闸门对多解题【语义上】失效**，

## T64. 【更正 `T32`】全仓 `.out` 的 CRLF 是**平台级约定**，不是各题的数据缺陷

### 背景

`T32`（批次十八，`1519`）把「`.out` 是 CRLF」记为**数据缺陷第 17 类**，
此后又在 `1565`/`3065`/`3066` 等多题重复记录。

### 更正（批次二十二，`20030` 的 worker）

worker 对全仓 `.out` 做了**穷举扫描**：

```
.out 文件中：【2968 个是纯 CRLF，仅 1 个是纯 LF】
⇒ CRLF 是【全仓统一约定】（占 99.97%），不是各题的缺陷
⇒ check_bytes.py 未做行尾归一化 ⇒ 这 2968 道题的 ❌ 是【平台级噪声】
```

### 三层更正

| 原判断（T32） | 更正后 |
|---|---|
| 「1519/1565/3065/3066 的 `.out` 是 CRLF ⇒ 数据缺陷」 | 【全仓约定】，非缺陷 |
| 「`.in` 也是 CRLF ⇒ 缺陷加深」 | 同上，`.in` 同为 CRLF 是【配套约定】|
| 「check_bytes 对这些题会永远失败」 | ✅ 仍成立 —— 但应【归为平台级噪声】，不是「数据缺陷」 |

★ **真正有信息量的分层**：
1. **`.out` 与本仓绝大多数一致（CRLF）** ⇒ 平台约定，`check_bytes` 的 ❌ 是噪声
2. **`.out` 是 LF 而 `.in` 是 CRLF（混用）** ⇒ 这才是**异常**（如 `3519` 的 `jxfg0-4` vs `jxfg5/6`）
3. **`.out` 内容本身有问题**（`T36` 非法 / `T56` 次优）⇒ 这才是**实质缺陷**

### 纪律

> **判定「数据缺陷」之前，先建立【基线】。**
> 一行检查：
> ```bash
> # 全仓 .out 的行尾分布
> for f in $(find new_ROJ/problems -name '*.out' | head -3000); do
>   python3 -c "
> import sys
> b = open('$f','rb').read()
> crlf, lf = b.count(b'\r\n'), b.count(b'\n')
> print('CRLF' if crlf and crlf == lf else 'MIXED' if crlf else 'LF')"
> done | sort | uniq -c
> ```
> ⇒ 若某特征占 99%+ ⇒ 是【约定】，不是缺陷；
>   若是【少数派】⇒ 才可能是异常。
>
> ★ **任何「X 是缺陷」的结论，都要问一句：「这是少数派还是基线？」**

### 对 `T32` 相关记录的影响

- `1519`/`1565`/`3065`/`3066` 的「CRLF 数据缺陷」⇒ **降级为「平台约定」**
- 这些题的 `check_bytes` 失败 ⇒ **噪声**，不影响「程序正确」的结论
- ★ 真正的缺陷记录保留：`T36`（非法）、`T40`（缺失）、`T41`（语义不符）、
  `T56`（次优）、`T42`（顺序）、`T59`（格式元素）

## T65. 无数据题的**证据上限**：格式假设永远无法验证

### 现象（批次二十二，`8010`）

题面**完全未定义**输出格式。worker 的一手查证（全部无果）：

```
roj.ac.cn/api/problem/8010       → 只有 title/time/memory/tags/source
roj.ac.cn/api/problem/8010/markdown → 与本地 content.md 逐字节相同
上游 GitHub roj/8010             → 只有 content.md/config.json/data.json
roj.ac.cn 的「查看题解」链接      → 无公开内容
★ 仓库惯例也不能作依据：全仓 main.cpp 中 Yes=12 / YES=24 / yes=9
  ⇒ 【仓库内部没有统一的 yes/no 大小写约定】
```

⇒ 最终采用 `Yes/No` —— 但这是**假设**：
> 若官方数据用 `1/0` 或 `YES/NO`，逐字节比对会全错。
> ★ **本工作流无法排除该风险。**

### 与有数据题的本质区别

| | 有官方数据 | 无官方数据 |
|---|---|---|
| **算法正确性** | 与 `.out` 比对 ✅ | 跨源对拍 ✅（可替代）|
| **输出格式** | **从 `.out` 逐字节确认** ✅ | ⚠ **永远无法验证** |
| **题意细节**（如顺序/取等）| 官方真值可裁定（`V8`）| 穷举可裁定（部分可替代）|

⇒ **跨源对拍能替代「算法正确性」验证，但不能替代「格式」验证** ——
格式只存在于「官方判题器怎么读输出」这个环节，而它没有可观察的痕迹。

### 纪律

> 无数据题的 `index.md` 必须**显著标注**哪些内容是**假设**：
> - 输出格式（`Yes/No` vs `YES/NO` vs `1/0`）
> - 输入格式（题面未写时按最自然约定）
> - 空串等边界的处理
>
> ★ **假设必须在文档里可检索**（如加粗 + 「假设」字样），
> 而不是埋在正文里 —— 因为后续读者需要知道**哪些结论是可验证的、哪些不是**。

### 附带 1：`T63` 的再加强 —— API 可以**一手确认**「无数据」

```
https://roj.ac.cn/api/problem/<pid>
  → {"hasPublicData": false, "totalFiles": 0, "files": []}
+ 数据源 baseUrl 的 <pid>.tar.zst 实测 404
⇒ 「无数据」从【推断】升级为【官方一手确认】
⇒ 闸门跳过 = 「已确认无数据」，不是静默空转（T1 的判定要分层）
```

### 附带 2：**「题面保证」对不同实现的承重性不同**

```
8010 的题面保证「s1 各字符互异」：
  · 对【单值表类实现】（pos[c] 存一个位置）⇒ 承重（违反则错，8/13 例）

⇒ ref 实现要避免【依赖题面保证】的写法（更鲁棒的写法对验证更有利）

### 附带 3：样例的判别力（`V8` 的经典应用）

```
题面「子串」vs 样例「相对位置」矛盾 ⇒ 四个候选：

⇒ 一条例 + 逐字读题面末句 = 题意唯一确定
```

## T66. PDF 题面的**排版产物**：同一字符可能有多个码位

### 现象（批次二十三，`10012`）

从 PDF 提取的题面样例显示 **全角冒号** `00：00`，
而官方 `std.cpp` 用 `scanf("%d:%d")`（**半角**字面量）
⇒ 直接冲突：若数据是全角，`std.cpp` 解析会失败。

worker 用**三层独立证据**判定：

**（i）PDF 内部 ToUnicode CMap（字体级，决定性）**
```
ToUnicode 对象 47 (DengXian)   : <6F21> <6F22> <FF1A>   ← beginbfrange
ToUnicode 对象 77 (CambriaMath): <01E3> <003A>          ← beginbfchar
⇒ 码位 0x6F21 → U+FF1A「：」（真有全角字形）；0x01E3 → U+003A「:」
⇒ 【两者是不同的码位，不是提取错误】
```

**（ii）同一页两种冒号【按位置分工】**（用字体 advance 宽度判别，12pt）
| 位置 | 码位 | advance | 判定 |
|---|---|---|---|
| 样例块 `00：00` | `6F21` | 12.000 pt = **1.00 em** | 全角 |
| 格式行「形如 $hh:mm$」| `01E3` | 5.160 pt = **0.43 em** | **半角** |

**（iii）`problem.md` 字节级**：样例块 9 处 `\xef\xbc\x9a`（U+FF1A）；
格式行 2 处 `0x3A`（半角）。

**（iv）`std.cpp`**：`scanf("%d:%d")` 半角字面量；文件内非 ASCII 字节数 = **0**。

⇒ **数据用半角**；**题面样例块里的全角是 Word→PDF 排版产物**。

### 纪律

> **PDF 提取出的题面，其「标点符号」不能直接当作数据约定。**
> 必须用以下之一交叉确认：
> 1. **官方 `std.cpp` / 样例文件**（最强 —— D 组大多有 `std.cpp`）
> 2. **PDF 内部的 ToUnicode CMap**（看码位映射）
> 3. **字体 advance 宽度**（全角 ≈ 1.00 em、半角 ≈ 0.43 em）
> 4. **本地 `data/`**（若有）
>
> ★ 特别警惕：**中文排版里的标点**（冒号、逗号、括号、引号）
> 在 PDF 里常被替换为**全角形式**，而数据可能用半角。

### 附带：题面样例与 `std.cpp` 冲突时的处理

本题的**题面样例块用的是全角**，而 `std.cpp` 只认半角 ⇒ **`std.cpp` 在自己题面的样例上会失败**。

worker 的处理（**值得作为范式**）：
> 落盘实现选择**接受两种冒号**（只认数字，分隔符一律跳过）
> —— 即「**按题面语义 + 兼容 `std.cpp`**」，
> 而不是「按 `std.cpp` 的窄解析」。

★ 差异点清单（6 条）已记录在 `index.md`，
其中差异 2–4（全角/空格/无分隔符）**都不在题面给定范围内**。

### 附带 2：`V1` 的**双面结果**

```
D 变体（只认半角冒号）：
  半角输入 → 0 失败（【不承重】）
  全角输入 → 1437 失败
⇒ 【仅半角数据无法鉴别冒号处理】；加上全角才暴露它
```
⇒ 与 `T20`/`T55` 呼应：**判据的鉴别力取决于测试数据的覆盖面**。

### 附带 3：`std.cpp` 自身的两个缺陷

```
① 全角输入 → 输出 23:31（scanf 返回 1，m 未赋值 ⇒ 读到垃圾）
② 空输入   → 输出 14:43（m 未初始化 ⇒ 【UB】）
```
⇒ 与 `5012`（`p==1` 自溅丢失）、`5011`（平局段不精确）同类：
**官方 `std.cpp` 不是绝对正确的基准**。

## T72. **model 覆盖必须同时探明该 provider 的并发上限** —— 否则「修好一个、撞坏三个」

**1）换 provider 后，先用【小批】探明并发上限**（不要直接按老 provider 的批宽派）

**2）批宽记录表**（本仓）

## T73. **model ID 的 `cn:` 前缀不能省** —— 否则 `404 model_not_found`

> 已知不带 `cn:` 的：`s2a-gemini/gemini-3.1-pro`、`s2a-wb-my/global:gpt-5.5`
>
> ★ **无法从错误消息区分**「ID 写错」和「账号没这个模型」
>   ⇒ 看到 404 时，**第一反应应该是检查 ID 格式**（而不是换 provider）。

### 与 `T71`/`T72` 的合并：**五类错误消息 → 五种动作**

| 错误消息 | 第一反应 |

| `503 Service temporarily unavailable` | 等一下再试 |
| `Concurrency limit exceeded` | 降批宽 |
| `Upstream request failed` | 换 provider（重派时带上已得结论） |

★★ **教训**：`404` 与 `503` **看着都像「provider 不行」**，
   但前者是**我的输入错**、后者是**环境错** ——
   混淆的代价是**连续 5 次无效重派**（本轮实际发生）。
