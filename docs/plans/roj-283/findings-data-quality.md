# `new_ROJ` 素材源的数据质量缺陷

> 全部经过**独立验证**（自写实现跑真实数据 / 手算 / 构造反例）。
> 这些缺陷不影响本题解产出（已逐题如实记录在 `index.md`），
> 但会让任何「照题面写干净解法」的人 WA。**建议单独修数据。**

## 零、为什么重要

`data/*.out` 是由 `std.cpp` 生成的。**`std.cpp` 自己有 bug，`.out` 就是错的** ——
而我们的验收标准是「真实数据 10/10」，于是会出现：

> 正确的实现跑不过错误的数据。

**处理原则（写进任务卡了）**：

> **不要为了让 `.out` 通过而写错算法。**
> 用正确读入实现；若逻辑对但 `.out` 不符，在 `index.md` 写明
> 「`.out` 由带 bug 的 std 生成，本点数值可能是垃圾」，把**正确实现作为主解**。

1762 的子代理就是这么做的：它用 BFS 暴力 + 手算证明了原实现语义正确，
**拒绝迎合错误数据**，转而推动修数据。

## 一、A 类：`std.cpp` 自身有 bug（`.out` 被污染）

| 题号 | 缺陷 | 证据 | 状态 |
| --- | --- | --- | --- |
| **5004** | `std.cpp` 三处 `scanf` 格式符错：变量都是 `long long` 却用 `%d` 读（`%d%d` / `%d` / `%d%d%d`）。`%d` 只写低 4 字节，高 4 字节保留栈上旧值 → 执行到更新分支时 `x` 变巨大值 → `for(i=x;i<=y)` 整体不执行，**区间加被静默丢弃**；一旦跑过一条查询（`%lld` 写满 8 字节），高字节清零，后续更新又正常 | **坏点恰好是「首个操作是区间加」的那些**：10 个点共 1022 个查询，p1/4/5/6/7/9（首个操作是查询）0 处不符；p2(68/76)、p3(63/147)、p8(49/107)、p10(76/115) 共 256 处不符。代入「丢弃首条查询前的所有区间加」模型，**1022 个查询全部吻合（0 不符）** | ✅ **已修**（`new_ROJ` 提交 `f66790d`：改正格式符 + 重生成 10 个 `.out`；6 个好点一行未变） |
| **3058** | 压栈时**漏了�out栈内自底向上递减的守卫**，把大数压在小数上 → 该栈永远无法按升序弹出 → 程序死锁，输出的只是死锁前的残骸。**8 个数据点里坏了 5 个**（twostack2/3/6/7/8） | 特征：**入栈数恰为 n（全部压完）、出栈数远小于 n**：n=290 时入栈 290 / 出栈 **2**；n=813 时入栈 813 / 出栈 **6**。逐条模拟定位，每个坏点的**首次违规位置正好是分歧位置**，内容一律是「`a`：S1 顶 41 < 压入 42」这类破坏递减的压栈。另：输入是**多组数据**（首行 T），题面「输入格式」只写了「第一行是一个整数 n」，漏了 T | ✅ **已修**（`new_ROJ` 提交 `185dc38`：新增 `std.cpp` 作生成器 + 重生成 8 个 `.out`） |

## 四、通用纪律：做题前先验 `std.cpp`

```bash
cd /Users/rainboymac/mycode/RBOOK_series/new_ROJ/problems/<pid>
# 编译并跑一遍全部数据点，确认 std 自己是对的
g++-16 -O2 -std=c++17 std.cpp -o /tmp/std_<pid>

```

如果 `std` 自己都跑不过自己的 `.out` → **素材有问题**，不是你的解法有问题。

**注意**（macOS）：`/usr/bin/g++` 是 clang，**没有 `bits/stdc++.h`**，
必须用 `/opt/homebrew/bin/g++-16`（`compiler.py` 已自动探测）。

## 五、「真实数据 10/10」的语义边界

| 能声称 | 不能声称 |
| --- | --- |
| 与**随仓数据** `new_ROJ/problems/<pid>/data/` 一致 | 官方 AC |
| `main.cpp` 与 `main.py` 互相一致 | 评测机 AC |
| 通过了自写暴力/对拍 | 数据本身正确 |

`data/` 是随仓库数据，可能不等于线上评测点；且如上所述，**它自己可能是错的**。
报告里只声称「随仓数据一致」。
