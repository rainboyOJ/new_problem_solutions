# 问题报告：`oj-problem-analysis-writer` 的分层解布局经常不被触发

> 供 AI 分析用。以下每条结论都标注了验证方式和实测数据，未验证的推测会明确标为「推测」。

## 一、要解决的问题

仓库有 skill `oj-problem-analysis-writer`，其中定义了四种题解正文布局，优先级第一的是**子任务递进型**（即「分层解」）：

> 1. **子任务递进型**：真实约束形成层层推进，每层复用观察并移除新的瓶颈。

但实际观察是：**大量客观上应该写成分层解的题目，最后写成了别的布局，甚至根本没套布局。**

## 二、具体案例：P4447 分组

这道题的题面自带五档子任务：

| 测试点 | 数据限制 |
| --- | --- |
| 1~2 | $n\le 6$，$1\le a_i\le 100$ |
| 3~4 | $n\le 1000$，$a_i\le 10^5$ 且 $a_i$ 互不相同 |
| 5~6 | $n\le 10^5$，$a_i$ 互不相同 |
| 7~8 | $n\le 10^5$，$1\le a_i\le 10^5$ |
| 9~10 | $n\le 10^5$，$-10^9\le a_i\le 10^9$ |

**这是教科书级的子任务递进结构**：每档放宽一个条件（先放大 $n$、再允许重复、最后放开值域），每档对应一个不同的算法。

但仓库里原本的 `index.md` 是这样的（git 版本）：

```
### 题意
### 思路          ← 只讲了堆贪心一种解法
### Python 知识
### 代码          ← 只引用 brute.cpp 和 main.py
### 复杂度
### 总结
### 一图流解析
```

完全没有布局骨架（缺 `## 形式化题目`、缺 `## 暴力解法`、缺分层的 `## 正解`），只是把一种解法写成一篇随笔。

## 三、根本原因分析

### 原因 1：`fetch_problem.py` 只创建空占位符

运行 `python3 scripts/problem-analysis-tools/fetch_problem.py luogu <PID>` 会创建 6 个 workspace 文件，包括：

```
problem-analysis-workspace/02-observation-and-model.md
```

**但内容只有两行**（`scripts/problem-analysis-tools/template/workspace.md`）：

```markdown
# {{title}}

<!-- 由 oj-problem-analysis-writer 填写 -->
```

验证方式：`fetch_problem.py luogu P9999 --dry-run` 的输出确认了这些路径会创建，且模板文件内容是纯占位符。

**结论**：文件存在 ≠ 内容存在。目录看起来「规范」，但实质是空的。

### 原因 2：skill 不会被自动触发

`oj-problem-analysis-writer/SKILL.md` 的 frontmatter 是：

```yaml
description: >-
  Write Chinese OJ problem analysis content for this repository's ebook. Use
  this skill whenever the user asks to write a 题目解析, fill
  problems/<oj>/<problem_id>/index.md, ...
```

**触发机制**：靠 LLM 读到这段 description 后自行决定加载，没有任何代码调用它。

验证方式：`grep -rn "oj-problem-analysis-writer" scripts/ .githooks/ package.json` 只找到**注释和提示文案**（如 `new-problem.py:28` 的文档字符串、模板里的 HTML 注释），没有任何 `import` 或子进程调用。

**后果**：

| 用户行为 | 是否触发 skill |
| --- | --- |
| 明确说「写题解」「补 index.md」 | 大概率触发 |
| 只运行 `fetch_problem.py` 建框架 | **不会** |
| 让子 agent 做别的事（如「写 main.cpp」） | 可能不会，取决于 prompt 措辞 |

P4447 的旧文就是这种情况：文件建出来了，但写作时没走 skill 流程。

### 原因 3：布局判定是「软约束」，实测 98% 不执行

skill 第 4 步要求：

> 先判断解法关系，再在 `02-observation-and-model.md` 记录布局、依据、层次、代码对应关系和正式主解。

实测扫描全仓：

```
有 02-observation-and-model.md 的题目：1045 道
其中缺「文章结构判定」或「选定布局」段落：1024 道   ← 98%
```

也就是说，**即使文件被创建，几乎没人往里面写布局判定**。

### 原因 4：循环依赖——分层需要先有分层代码

这是最关键的一条。

skill 第 2 步要求：

> 读取 `problem.md`、现有 `index.md`、全部约束和子任务、**所有解法文件**（`main.*`、`brute.cpp` 及额外代码）……

但时间顺序上：

1. 刚 `fetch_problem` 完 → 只有空壳 `main.cpp` + `brute.cpp`
2. 此时执行者看不出「解法关系」，只能判成最简单的「直接正解型」
3. 于是不会去写 `main2.cpp`、`main3.cpp`
4. 于是分层永远不成立

P4447 旧目录实测只有：

```
brute.cpp  brute.py  gen.py  main.cpp  main.py
```

`main.cpp` 当时是「二分答案 + check()」，`main.py` 是「堆贪心」——这其实是**两个独立完整解法**，本该触发优先级第 2 的「并列多解法型」，但被当成「同一算法两种语言」处理了。

**注意这里还有第二层错误**：即使按旧素材判，也该是「并列多解法型」而不是「直接正解型」。说明执行者连「两个文件是否算两种解法」都没判断。

### 原因 5：即使判对布局，也可能漏写总览表

修改前的 skill 只说了布局优先级和骨架标题，**没有规定递进型必须放一张总结表**。所以即使选对了布局，也可能写成零散的分节，读者读完才知道哪层覆盖哪些点。

（这一条已在 2026-10-23 修复，见第六节。）

## 五、诊断结论

按重要性排序：

1. **skill 的约束全是描述性的，没有机械可查的交付物。** 1024/1045 的缺失率证明「要求」不管用。
2. **循环依赖**：布局判定要求读所有解法文件，但分层代码需要先有布局意识才会被写出来。
3. **触发不可控**：skill 靠 LLM 自主加载，用户只说「建框架」或「写 main.cpp」时不触发。
4. **占位符掩盖了缺失**：文件存在让人误以为流程走过了。

## 六、已做的修复（2026-10-23）

### 修复 1：skill 增加「递进型必须写一张分层表」

改 `oj-problem-analysis-writer/SKILL.md`，在布局判定后新增小节，规定：

- 表格固定五列：`层 / 做法 / 复杂度 / 覆盖 / 突破的瓶颈`
- 位置：正文开头，早于任何一层展开
- 每列要求：
  - **做法**要能对上代码，不写「优化一下」「二分」这类空标签
  - **复杂度**要逐层变好，否则该层不成立
  - **覆盖**写实际测试点区间，不写「部分分」
  - **突破的瓶颈**是重点，一句话说清上一层卡在哪、这一层靠什么绕过
- 表格后须说明哪几层是真正的思维跳跃、哪几层只是同一条路上的退化

同时改 `oj-problem-format-spec/references/layouts.md`，把该表写入布局骨架（递进型与并列多解法型都必须）。

示例（P4447 实际采用）：

| 层 | 做法 | 复杂度 | 覆盖 | 突破的瓶颈 |
| --- | --- | --- | --- | --- |
| 1 | 枚举分组编号 | $O(n^n)$ | 1~2 | —— |
| 2 | 排序 + 逐元素接最短链 | $O(n^2)$ | 3~4 | 从枚举变成确定性构造 |
| 3 | 扫描连续段 | $O(n\log n)$ | 3~6 | 利用互不相同，链数降为 1 |
| 4 | 桶 + 堆 | $O(n\log n)$ | 7~8 | 允许重复，需堆管理多条链 |
| 终 | 分块 + 双堆 | $O(n\log n)$ | 9~10 | 坐标压缩，容纳负数与 $10^9$ |

### 修复 2：P4447 补齐六个分层代码文件

```
brute.cpp     枚举分组编号                O(n^n)       1~2
main2.cpp     排序 + 逐元素接最短链       O(n^2)       3~4
main2-1.cpp   互不相同特化：链长 DP       O(n^2)       3~4
main3.cpp     扫描连续段                  O(n log n)   3~6
main4.cpp     值域桶 + 堆                 O(n log n)   7~8
main.cpp      分块 + 双堆（正式主解）     O(n log n)   9~10
```

`index.md` 改成子任务递进型，含上面那张表。

**这说明一件事**：分层解的前提是**先有分层代码**。只有 1 个 `main.cpp` 时，任何执行者都判不出分层。

## 七、待讨论：还需要什么

上面两个修复只解决了「判对布局后怎么写」，没有解决「如何保证判对」。以下是候选方案，需要权衡：

### 方案 A：加机械检查脚本

写 `scripts/check_analysis_layout.py`，规则例如：

- 若 `main*.cpp` 数量 ≥ 2，但 `index.md` 的 `## ` 二级标题数 < 3 → 报警
- 若 `index.md` 无 `## 形式化题目` → 报警
- 若 `problem-analysis-workspace/02-observation-and-model.md` 缺「文章结构判定」→ 报警
- 若判定为递进型/并列型，但缺总览表 → 报警

接入 `npm run verify:push` 或 `check-content.js`。

**优点**：可机械执行，不依赖 LLM 自觉。
**风险**：现有 7/16 的题目会立刻报警，需要先批量修或加白名单。

### 方案 B：把布局判定挪到「写代码之前」

在 skill 里加一条：**判定布局后，先列出需要哪些代码文件，再动手写代码**。打破循环依赖。

例如 P4447 在只有 `main.cpp` 时，就该先判定「这题有 5 档子任务，需要 5 个代码文件」，然后逐个实现。

**优点**：从根上解决循环依赖。
**风险**：需要改 skill 的步骤顺序，影响所有后续写作。

### 方案 C：`problem_status.py` 把缺失列为待办

已有 `scripts/problem-analysis-tools/problem_status.py`，可在其中增加检查项，让缺失在状态里可见。

**优点**：改动小，不改流程。
**风险**：仍然是「提示」，不强制。

### 方案 D：接受现状，只在 prompt 里强调

在 `scripts/navi/rbook-pi-prompt/write-solution.md` 里显式要求「先判布局、写 02、再写代码」。

**优点**：零成本。
**风险**：同样是软约束，历史证明不管用。
