# HTML 教学与掌握验收

## 从代码构造学习单元

每个关键单元围绕当前一个推理缺口组织，不按函数排列顺序机械切章节。默认顺序是“认识图中对象 → 看懂一次过程 → 预测后续动作或相似小例 → 图上解释原因 → 对应源码”。已掌握的内容可以直接用预测确认。

先让学生看懂针对卡点的可执行小过程，再解释关键观察与目标实现。已知知识用一句话连接；当前过程缺少必要前提时先简短补齐，完整推导与其他基础按需展开。用户明确要求从题意完整学习时才以整题顺序为主线。

## 首屏与信息呈现

- 打开即可看到核心图、足够小的教学例和单步按钮，不先经过课程介绍、目标列表、术语墙或答题页。只呈现读懂画面所需的对象标签、图例、任务和必要前提。
- 每步在图旁解释“谁做了什么、为什么”，文字与高亮同步。突出当前对象或路径、有效状态、变化前后的数值；不要同时展开历史日志、整套变量表、长证明与完整源码。
- 同一对象跨结构出现时，通过一致的编号、标签或颜色建立对应，点击时联动高亮。颜色不能成为唯一识别方式。图上要能区分谁提供贡献、谁收集贡献，以及更新和查询发生的时刻。
- 基础、推导、边界、复杂度和代码有清楚的展开入口，但不挤占默认主画面。短说明应足以理解当前动作，不能把关键条件藏进折叠区域。
- 不以字数少为唯一目标；删除不帮助当前判断的信息，保留对象含义、因果关系和必要条件。页面长短、关卡数和“看完”进度不能代替理解证据。

## 从直观过程接到实际实现

目标代码把多个对象的操作合并时，可先让一个对象独立走完过程，再展示重复工作如何被共享。只有这个过渡确实减少理解难度时才使用；不要为每题强造朴素算法。

例如双 Trie 计数可以先说明“已按相同差异核心分组”，用两棵树演示一个询问沿左路径激活规则、从右终点向上收集贡献、最后清除这些贡献。再增加共享路径的询问，过渡到左树 DFS 的进入、查询与退出。用另一分支说明为什么必须撤销，并保留“同节点先激活全部规则再回答询问”的实际顺序。

前一过程标为帮助理解的单询问做法，后一过程才是目标源码的执行方式。两者回答相同问题，但执行次序与效率可以不同。过渡时明确哪些对象、状态和结果保持对应；不要把两套执行轨迹混在一个没有说明的动画里。这只是教学示例，不要求其他题目使用双树或激活模型。

图上理解后再展示对应的短源码片段，完整源码按需展开。最终对应关系至少覆盖：

- 状态、节点、数组或变量在原题中代表什么；
- 每次更新和查询究竟统计什么；
- 关键判断条件由哪条数学或结构关系推出；
- 为何不漏、不重，以及循环、遍历或离线处理中保持的不变量；
- 边界与复杂度如何约束实现。

可用小规模简化代码铺垫，但明确其角色，最终必须接回用户指定文件。不要偷偷改成更容易展示的另一种算法。

## 可操作的图形

按概念选形式：字符串对齐与区间拖动、数组格子、DP 状态表、树图、路径、递归栈、事件队列或数值变化。SVG、HTML、CSS 或 canvas 均可，选择能让用户预测并观察状态变化的最小形式。

规则、样例与模型算出图形和数值，少量手工布局不等于可以手工伪造状态。原题样例标明来源，另造的小案例标为教学例或反例。显示关键中间状态，不只播放“最后答案正确”的动画。

预测与演示相互连接：选中对象、拖动区间、单步与回退要改变真正展示的状态。自动播放能够暂停；重置、切换案例或关卡后停止旧计时器。更新范围控件时保持其可连续拖动，不因重建 DOM 丢失拖动事件。

支持重试、回看与自由导航；用户可以先看演示再回题，不使用强制答对才能前进的锁关。需要保存学习进度时存本地，区分“看过”和“已作答通过”。

窄屏下图形可局部横向滚动并提供提示，尽量让当前对象可见，避免整页溢出。用文字或形状补充颜色语义，保证键盘操作、标签与可见焦点。避免为装饰增加复杂网络依赖。

## 源码可信度

单文件离线教程应内嵌需要的实际源码和数据，不依赖 `fetch('./main.cpp')` 在 `file://` 下成功。来源文件名、片段行号或源码摘要可以帮助后续维护者判断是否过时。

优先核对影响推理的中间状态：例如转移、父指针、DFS 区间、DP 单元或活跃集合。可以使用目标程序的临时副本输出追踪信息，不为调试改坏正式提交文件。

若目标代码或注释有错误，指出具体冲突，先验证，再在教程中区分正确含义与错误位置。修复目标文件是否属于任务范围，以用户授权为准，不为了让演示顺畅而无声改写目标。

## 三类掌握验收

### 1. 新例推演

选一个未完整演示过的合法小输入，让用户推演关键状态和输出。适度变化结构或边界，检验能否迁移规则，避免只是回忆演示中的答案。保留参考过程用于提交后的反馈。

### 2. 关键条件解释

选择真正控制正确性的变量、不等式、状态维度或更新顺序。让用户解释它的含义，并判断删掉、反转、改边界后会错在哪里。题目应对应本题，不使用“这个算法有什么优点”之类泛问。

对开放解释，提供对照要点或在用户作答后由 Agent 评阅。不能通过关键词出现次数或固定字符串一致就宣称理解正确。

### 3. 核心代码应用

让用户补全或修改短核心片段，例如边界条件、转移式、更新位置或遍历次序，并说明理由。语言与目标代码一致；不要求为通过教程重写整份程序。

答案验证能力必须真实：若只检查受限表达式或操作选择，说明检查范围；没有实际编译执行就不能显示“代码已评测通过”。语义等价的正确写法不应仅因与标准字符串不同就判错，无法自动判断时提供人工对照或等待用户交给 Agent 检查。

### 反馈与补救

每种错误关联到具体缺口与回看入口，例如“把 Trie 深度当成另一棵树的层数”“漏了状态的一维”“边界少一位”。解释为什么，并允许修改答案、回看或用另一个小例子重试。

制作时把验收任务和判定要点准备好。交付网页不代表用户已经通过验收。只有实际获得作答证据，才能报告哪些能力已验证、哪些尚需练习；不承诺仅凭生成一份 HTML 就让用户“彻底掌握”。

## 验证与交付

按变更运行适当检查，并在分析工作区记录：

- 题面样例与教学模型答案一致；有可靠基线时对关键模型做小数据核对。
- 首屏无需长距离滚动、阅读前置章节或答对题目即可操作核心图；首次陌生过程有演示，必要前提可见。
- 每步图形与短说明同步；可从图上辨认当前对象、有效状态和改变的数值。教学预测落在“下一步改变什么、为什么”这类具体问题上。
- 使用直观铺垫时，它与实际源码的区别标明，结果对应且过渡可解释；默认画面没有把简化过程冒充目标代码。
- 图中的关键状态、下标、计数含义与目标代码一致，重复元素与边界不被可视化悄悄改变。
- 作答、反馈、重试、播放、暂停、回退、重置、导航及关键选择控件实际工作；若支持进度恢复也测试刷新。
- 用可用浏览器检查桌面与窄屏、控制台和离线直接打开。无法执行浏览器检查时如实说明验证限制，不伪称已验证。
- 验收包含三种能力；开放解释和代码题的自动判定限制清楚，错误能定位到对应单元。
- 源码片段与文件一致；新增题解链接存在，Markdown 渲染与仓库相应内容检查通过。

交付只需说明 HTML 位置与打开方式、为当前用户调整的重点、实际验证和待完成的用户验收。无需发布网站或修改服务，除非用户另有要求。
