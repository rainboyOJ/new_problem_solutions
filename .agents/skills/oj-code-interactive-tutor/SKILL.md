# OJ 代码交互导师

目标是让用户理解**指定题目、指定解法、指定代码**的思考过程和实现，并能独立推演、解释和应用。产出适合当前用户的交互 HTML；完成网页与用户已经掌握是两个不同结果。

仅在用户明确调用时使用，如 `$oj-code-interactive-tutor`。调用策略由 `agents/openai.yaml` 的 `allow_implicit_invocation: false` 控制。

## 1. 读代码，确定教学对象

遵守仓库 `AGENTS.md`；编辑 `problems/**` 前阅读根目录 README 第 6 节和 CONTEXT.md。

- 读取题面、目标源码、样例、已有题解和分析记录，以实际代码核实状态、条件、计数对象、边界和复杂度。
- 用户指定了 `main2.cpp` 等文件，就围绕该文件教学。未指定且上下文没有歧义时，以当前题目主解为目标；只在确实有歧义时询问。
- 提取这份代码的最小前置知识及其依赖顺序。包含必要的算法、数据结构、数学关系和语言特性，不按题目标签罗列整份算法清单。
- 已有材料中的事实自行查阅；用户在会话中已说明的掌握程度直接沿用。不要让用户重复提供文件里能找到的信息。
- 题意、代码或现有解释相互冲突时先核实。无法确认代码正确时说明缺口，必要时先用样例或小数据验证，不把错误行为包装成正确算法。

## 2. 逐项 grill-me，诊断讲解粒度

在制作之前阅读 [前置知识访谈](references/interview.md)。这里内置 grill-me 的必要行为，不依赖用户额外安装全局技能。

**一次只问一个问题，等待回答再继续。** 每个问题只解决一个影响教学粒度的缺口；推荐合适的学习安排，不暗示用户应该声称自己更熟练。

采用用户确认的方式：

1. 先自评，区分没学过、听过、会模板、理解原理并能推演。
2. 对不确定或关系到关键转折的知识，必要时用一道小预测题确认；不用把访谈变成考试。
3. 已掌握部分简讲并接到本题；薄弱部分单独演示；完全缺失的必要基础补进 HTML，再回到本题。

访谈只覆盖目标代码需要的依赖。不要继续追问已经清楚的知识，也不为颜色、框架等常规实现选择延长访谈。

## 3. 汇总并确认教学路线

用一份简短路线将“用户基础 → 本题关键观察 → 状态或操作 → 源码 → 验收”接起来，标明哪些地方补基础、哪些地方细讲、哪些地方略讲。关卡数量按实际依赖决定，不固定为八关。

在首次访谈结束时请用户确认路线，再开始制作；此前可读取材料和整理分析。用户已经明确确认路线或要求直接按现有方案开始时，继续执行，不重复索要同一确认。后续只有实质改变学习目标或范围时才重新确认。

把目标文件及其版本、用户自评、预测题表现、教学路线记录在题目目录的 `problem-analysis-workspace/interactive-tutor-plan.md`。保留已有记录；不把个人学习画像写入公开题解的 frontmatter。

## 4. 制作针对该代码的交互教程

确认路线后阅读 [HTML 教学与验收](references/html-and-mastery.md)，落实完整流程。

- 默认制作本地可直接打开、可离线使用的单文件 HTML，脚本、样式、图形和需要的源码片段内嵌。用户已有页面或其他明确要求时按其约束执行。
- 每个关键单元采用“先预测 → 操作演示 → 因果解释 → 对应代码”，可以重试、暂停、回退和回看，不强制锁住后续单元。
- 用小案例与针对性反例展示真实的状态和转移。图形、变量值和计数由模型计算；模型的教学行为须与目标代码对应。
- 讲清观察为何成立、每个状态或变量代表什么、条件为何必要、边界与正确性，以及复杂度为什么满足题目约束。避免只逐行翻译代码。
- 把缺失基础补到足够理解本题的程度，随即返回本题使用它；若缺口过大，先与用户缩小第一阶段的范围，不擅自扩成完整算法课程。
- 定位源码的关键函数、变量和判断条件，内嵌真实片段并说明来源。适当记录行号和源码摘要，避免展示另一套算法却声称在解释用户代码。

题目目录已有教程时优先扩展或修订，不覆盖其他解法的教程。新文件可命名 `code-lesson.html`，或按目标解法选用有区分度的名字。

## 5. 验证教程，并安排掌握验收

先验证图形、示例和程序过程，再检验用户是否能应用。教程必须提供三类验收：

- **新例推演**：独立处理一个没有完整演示过的小例子，写出关键中间状态或结果。
- **条件解释**：解释关键变量、循环不变量或判断条件，以及删掉、改错后会出现什么反例。
- **核心代码应用**：补全、修改或组织一小段关键代码，并解释理由。

答错时指出具体缺口，链接到对应基础或推导单元，再提供适当的重试。不能只用“答案错误”结束反馈，也不能因为看完动画就标记为已掌握。

浏览器操作、模型核对与验收题的具体检查方式见教学 reference。记录实际运行的检查，不把未执行的代码编译、判题或用户验收写成已通过。

## 6. 仓库整合与交付

- 最终 HTML 放在对应题目目录；生成器、设计说明和验证记录放在 `problem-analysis-workspace/`。只在复用或可靠更新确有价值时编写生成器，不为每题强制创建同一批脚本。
- 需要在 `index.md` 加教程入口时，使用 [rbook-markdown](../rbook-markdown/SKILL.md) 和 [题解格式规范](../oj-problem-format-spec/SKILL.md)，使用相对链接，并按仓库要求刷新 `updated`。不为增加入口重写原题解。
- 如需独立样例素材，使用 [oj-sample-visualizer](../oj-sample-visualizer/SKILL.md)；只需 HTML 内动态 SVG 时可直接实现。正式题解写作交给 [oj-problem-analysis-writer](../oj-problem-analysis-writer/SKILL.md)，不是本技能的默认产物。
- 如用户另外要求修改目标 C++，遵循 [oj-cpp-style](../oj-cpp-style/SKILL.md)。教学本身不要求改写提交代码。
- 交付 HTML 链接、打开方式、个性化重点和实际检查结果。生成教程后报告“教程已完成，等待学习与验收”；只有收到用户的验收作答后，才根据表现判断其掌握情况。

调用示例：`$oj-code-interactive-tutor 帮我学懂当前题目的 main.cpp，先询问我的前置知识，再制作交互教程。`
