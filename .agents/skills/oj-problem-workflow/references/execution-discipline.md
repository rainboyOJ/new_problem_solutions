# 执行纪律：少返工、少空等

本文件约束**怎么做**，不改变阶段划分与产物标准。目标是把时间花在推理和实现上，而不是等待和重做。每条都来自实际耗时记录，不是理论建议。

## 1. 新算法先在临时目录验证，再写正式文件

正式主解文件不要当草稿用。已验证的实际代价：某题 `main.cpp` 在正式目录里被反复重写 4 次，中途还写出过不可编译的残留代码，问题只有在整篇重读时才暴露。

- 新算法先落在 `/tmp/<题目>/` 下的独立文件，编译、对拍、边界测试通过后再一次性写入 `main.cpp` / `main.py`。
- 正式文件每次覆盖都必须是完整可编译状态；不把半成品留在题目目录里，避免后续步骤读到中间态。
- 迭代方向没定下来之前，不修改 `index.md` 里的复杂度或算法描述。

## 2. 一次只改一个变量

同时改两个独立的东西，失败时分不清是谁的错。实际案例：某题同时新写算法和重写 `gen.py`，生成器有 `w_i > n` 的越界 bug，触发 Python 版 `IndexError`，排查一轮才发现是生成器而非解法。

- 先固定生成器（并用它与已通过的旧实现交叉验证），再换算法。
- 数据、写手和实现三者不同时动。改动范围超出当前阶段时，先记录，按 workflow 的返工表回退到对应阶段单独处理。

## 3. 关键结论先机械验证，再写进正文

题解里"恰好两个端点等价于共线"这类判据，写完证明不等于写对了。机械验证很便宜，返工很贵：

- 小规模穷举优先：用 Prüfer 序列枚举 $n \leqslant 7$ 的全部带标号树，枚举 $|S| = 2..4$ 的全部取值，几秒钟就能跑上百万组合。
- 验证对象是**要写进正文的判据本身**，不是代码碰巧通过。判据被穷举否掉，说明推导错了，回退到规划。
- 实际收益：某题用 1,597,551 个组合验证两个核心判据，0 处不符，直接避免了审稿阶段的返工。
- 注意前提边界：`dirs = 0` 只在 $|S| = 1$ 出现，验证时必须把 $|S| \leqslant 1$ 排除，否则会得到假失败。

## 4. 复杂度用实测定阶，不靠直觉或字面

内层循环的个数不等于复杂度。实际案例：暴力解的检查层写作「$n$ 种颜色各 $O(n)$」，字面上像 $O(n^4)$，但各颜色节点数之和恒为 $n$，实际是 $O(n^3)$；`grep` 和直觉都判错，靠计时倍率（$n$ 翻倍时 6.4 / 9.8 / 9.3 倍）才定位。

- 写复杂度之前，至少让 $n$ 取 3 个规模实测一次，看倍率落在 $2^k$ 的哪一档。
- 结构上先问「这个内层循环的**总**迭代次数是多少」，不要只看嵌套层数。
- 受数组上界限制的范围（如 `MAXN = 35`）要和渐近复杂度分开写，不能用复杂度解释为什么只适合小数据。

## 5. 验证分级，够用就停

不是每道题都要跑满全规模。按需升级，避免在无关环节超额消耗：

| 层级 | 什么时候必须做 |
| --- | --- |
| 样例 | 所有题，无条件 |
| 小规模对拍（≥ 300 组） | 有可信 `brute.cpp` 且算法非平凡 |
| 边界专项 | 存在退化结构（链、菊花、$n=1$、无解） |
| 全规模判题 | 题目卡时限、卡内存，或算法复杂度贴着限制 |

- 小规模对拍通过后，只有**结论依赖大规模**（性能、栈深度、内存）时才上 $n$ 上限的判题。
- 已通过的层级不重复跑；只有对应代码变了才重跑受影响的那一层。
- 时间限制紧的题，对拍规模由 `--timeout` 控制，不靠减少组数硬扛。

## 6. 恢复任务先定位真实进度，不重跑

已有 `main.cpp` 且能过样例时，先测它当前的真实表现，再决定动不动它。实际案例：某题原解 2.6s / 137MB、限制 3s / 500MB，结论是「能过但余量小」，这直接决定了是重写还是只改正文。

- 复用前先给出它现在的量化状态（样例、对拍、时间、内存），而不是只看文件是否存在。
- 旧的完成标记、空的 workspace 记录、未核验的通过声明都不是证据。
- 优化已有题先用 reviewer 定位要改的部分，不做无目标重写。
