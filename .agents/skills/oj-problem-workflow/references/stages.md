# 单题阶段的输入、产物与完成依据

只读取当前需要的阶段。这里规定交接条件，算法规划字段以 planner 的 [`handoff.md`](../../oj-solution-planner/references/handoff.md) 为准，格式与评测规则引用各自 skill，不复制命令体系。

## 1. 材料

输入是题号、原题 URL、题目目录或用户提供的题面。核对 OJ 与题号后，读取已有 `problem.md`、样例、解法和过程记录；先确认已有工作和用户目标，避免覆盖。

材料缺失时用仓库现有入口，例如：

```bash
python3 scripts/problem-analysis-tools/fetch_problem.py <oj> <problem_id>
```

已有材料完整时不重复抓取，不默认加覆盖参数。ROJ 题面读取用已安装的 `roj`；用户要求基于 rbook 文章或模板时用 `rbook-http`；只有需要读取洛谷题解时才用 `luogu-solution-reader`。不要为了“准备充分”读取与任务无关的来源。

完成依据：目标、输入输出、约束、样例和来源已核实，或缺失情况已明确且不影响当前工作。官方子任务与分析特例分开记录。影响算法选择的未知条件没有解决前，不把猜测写成事实。

## 2. 解法规划

输入为核实的题面及已有材料。读取 planner，建立或复核候选算法、适用范围、关系、关键证明、复杂度和实现验证计划，记录到 `01` 至 `05` 对应文件。已有可靠分析复用，不为显示流程而重新探索。

完成依据：选中的方案具体可执行，关键结论有论证，部分分与全范围解的界限明确，代码与测试需求可安排。没有代码不妨碍规划；有多份代码不自动证明有多种算法。

恢复任务时先量化已有解的当前状态（能否过样例、对拍结果、$n$ 上限下的时间与内存），再决定重写还是局部修。只看文件是否存在不算定位进度。

布局此时是建议，由 writer 在写作阶段确认。简单题可以直接正解，子任务可以分叉或合并，不按测试点数量制造实现。仅思路任务在这里交付，不自动改文章或代码。

## 3. 实现

输入为选中算法及代码计划。由当前 agent 按实际语言风格实现；复用已有有效源码，明确每份文件对应的算法、范围和用途。正式主解用 `main.<ext>`，其他实现命名清楚；共享代码或省略独立实现时记录理由。

需要教学暴力时参考 writer 的 [`brute-force.md`](../../oj-problem-analysis-writer/references/brute-force.md)，运行方式仍以 judge skill 为准。小数据基线要可靠，输入输出与比较对象一致。

完成依据：所需源码完整，状态、数据结构、范围和复杂度与规划一致，必要的编译或语法检查通过。没有运行行为验证时，只能说实现完成，不能说已通过测试。

Python 学习模式在此检索和使用相关笔记，收集知识映射与模仿清单供 writer 使用。仅 Python 任务不自动创建 C++；已有其他语言材料保留。缺失笔记时可以使用通用语言知识，但不编造引用。

## 4. 验证

读取 `oj-judge-and-stress`，按真实题目限制和方案范围运行样例、适用边界及必要对拍。官方测试数据可用时优先利用；需要下载 USACO 数据时可参考仓库的 `fetch_usaco_testdata.py`，将数据交给同一 judge 工具。运行工具及结果判读只维护在 judge skill。

各独立方案分别验证；部分分程序只测自身约束，跨实现对拍使用共同适用范围。对拍计划应有可靠基线和适当规模；不适用时说明替代验证。用户明确禁止运行某类测试时遵从并记录，不擅自执行。

在 `04` 或实际验证报告中记录源文件、命令、限制、数据来源与范围、结果和失败情况。样例通过、随机通过、性能证据和正确性证明分别表述；不从样例通过推断全范围通过。

完成依据：任务要求的验证已实际执行且没有未解决失败，证据对应当前实现。Python 教学变体若 TLE/MLE，如实记录；可提交目标不能因此视为满足。设施故障、缺答案或无法计量资源属于缺失证据，不是算法通过。

## 5. 写作与教学补充

将规划、实现、验证和当前任务范围交给 writer，明确当前已在 workflow 的写作阶段。writer 核对输入、确定布局、生成 `06-final-index-draft.md` 并写回 `index.md`，按 format 与 rbook-markdown 组织。它不重新启动总流程，也不自行重跑已经完成的规划与验证。

发现算法缺口时，记录问题并由协调者转回相应阶段。缺必需代码时先完成实现；不把不存在的路径写成有效引用，也不把占位注释当作完成内容。

根据实际教学目标按需路由：

- 图示帮助解释样例、状态或算法时使用 `oj-sample-visualizer`，可提前到规划阶段；制作后核对图、代码和题意一致。
- 某个关键观察难以自然理解时，使用可用的 `rainboy-brain` 深入说明，不让它重写整套流程。
- 需要新增或修复前置、相似、推荐关系时使用 `oj-problem-relation-writer`，不为填字段编造关系。
- Python 学习文章在所选布局中加入知识映射与模仿内容，不用语言教学的固定旧骨架替换算法布局。来源只引用真正读取且适合公开的资料；本地笔记绝对路径可留在过程记录和交付报告中。

完成依据：正文与选定算法、实际代码、复杂度和验证状态一致，所需资源与引用可用，元数据按规范复核。旧文章内容有效时保留，不顺手改写无关部分。

## 6. 审查、返修与交付

完整题解任务使用 reviewer 审查产物，调用它要求的确定性检查。reviewer 默认输出问题清单；协调者按用户已授权的完整交付范围将必须修问题交回对应阶段，不需要为常规返修重复请求许可。用户仅要求审稿时保持只读并报告问题。

审查不阻塞主链路。正文结构定型就启动 reviewer，不要等整篇措辞修完。等待期间继续做不受审查结论影响的工作：跑剩余验证、补过程记录、检查元数据与渲染。reviewer 运行时间可达数十分钟，空等是纯损失。

独立审查不是每个任务都必须。满足下列全部条件时，可以自检代替，并在报告里明说未做独立审查：结构检查与 `check_problem.py` / `check:content` 全绿、实现已对拍、正文判据已机械验证、本次只做局部修订。完整重写、算法新推导或用户明确要求审稿时必须真跑 reviewer。

同一 agent 按 reviewer 自查不能称为“独立审查”。批量主 agent 的独立验收仍由批量协议负责，本 workflow 不创建额外 agent。

确定性结构与关系检查按实际适用范围执行。现有 `check_problem.py` 会跳过 `legacy` 的布局检查，且没有完整检查总览表和过程记录；不能把退出码为零当作全部质量要求已满足。新写或明确重写的文章仍需核对共同结构、所选布局及实质内容。

局部检查后，完整单题任务按仓库要求运行 `npm run check:content`；批量 worker 将全库检查留给主 agent 在写手停止修改后统一执行。原有无关问题单独报告，不擅自修其他题，也不声称全库通过。只有用户要求 push 前检查或需要诊断相关失败时，才进入 `project-pre-push-check`。

检查会读取已提交产物或工作区内容，本地被忽略的 `workflow-status.md` 和规划笔记不作为共享 CI 的必需输入。修改题目文件时按 format 更新 `updated`，保留原 `date`。

完成依据：用户要求的产物齐全，审查中的必须修问题已解决，适用检查有真实结果；未验证、受阻或失败项明确保留。仅做局部任务不必补齐整题历史缺口，报告本次范围及发现的相关限制即可。
