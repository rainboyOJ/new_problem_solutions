# OJ 单题工作流

负责判断当前阶段、加载专项 skill、核对阶段产物和安排返工，直到用户要求的交付完成。算法、代码风格、评测命令和文章格式分别由对应 skill 维护，不在此复制一套规则。

## 入口与调用约定

先读仓库 `AGENTS.md`、README 第 6 节和 `problems/CONTEXT.md`。确认题目目录、任务范围、目标语言和已有授权；已明确的信息不重复询问。完整题解默认包括必要规划、实现、验证、正文与审查，不自动包含提交、推送、发布或其他题目的修改。

需要用户决策的问题**一次问全**（一次调用列出所有待定项，含推荐项），不拆成多轮串行等待。用户说“重写”“优化”这类方向性要求时，默认按“保留有效材料 + 定点增量修改”执行，只在真正的分歧（如两种结构不同的布局）上才问。

“调用 skill”表示当前执行 agent 读取其 `SKILL.md` 并执行本阶段要求，不代表启动另一个 agent 或调用某个不存在的命令。按阶段加载，已读且未变化的规则复用，不一次加载全部 references。

采用以下单向协调关系：

- 用户或入口适配 → 本 workflow → 当前阶段的专项 skill → 产物与问题返回本 workflow。
- 已进入 workflow 时，writer、planner、风格与验证阶段不反向重新启动 workflow；发现缺口，报告给当前协调阶段处理。
- 用户直接点名 writer 且要求完整做题时，writer 可一次性交接到本入口；本入口之后进入 writer 时只执行写作阶段。
- `local-python-learn-oj` 负责 Python 学习适配后进入本入口；本入口不再反向调用该适配入口。批量 worker 在自己的题目范围内执行本入口，批次派发与进程管理仍归批量 skill。

## 先确定终点与当前进度

按用户实际请求选择终点，不能因为存在后续 skill 就自动增加工作：

| 请求 | 执行范围 |
| --- | --- |
| 完整完成题目、代码与题解、补完目录 | 材料 → 规划 → 实现 → 验证 → 写作 → 审查交付 |
| 只分析思路、子任务或解法关系 | 使用 planner，交付规划即止 |
| 只写或修复代码 | 必要算法分析 → 实现 → 适用验证，不新增文章 |
| 根据可靠材料写文章 | 复核输入 → writer → 文章检查；发现算法或实现缺口按授权处理 |
| 只审稿、只改格式或一个局部段落 | 使用 reviewer、format 或相应专项 skill，不重跑完整流程 |

检查已有材料的实质内容，从最早未满足依赖的阶段接续。已有可靠规划和代码复用；空文件、旧的完成标记、未核验结论不能作为完成证据。优化旧题时先用 reviewer 定位需要改的部分，避免无目标重写。

多阶段或恢复任务在本地 `problem-analysis-workspace/workflow-status.md` 简记任务终点、语言、当前阶段、完成证据路径、未完成项及下一步；已有合适记录可复用。简单局部任务可只在当前上下文记录，不为每次修改创建状态文件。状态文件保持本地忽略，不进入文章或共享 CI。

阶段状态可用“未开始／进行中／完成／不适用／受阻”。“不适用”写理由，“完成”关联实际产物；恢复时核对文件和证据，不能只信状态。阶段切换不需要逐次让用户批准。

## 阶段路由

首次执行完整任务或恢复缺口时，读取 [`references/stages.md`](references/stages.md) 中对应阶段的输入、产物与完成依据。

| 阶段 | 使用规则 | 核心产物 |
| --- | --- | --- |
| 1. 材料 | 仓库题面获取工具；ROJ 来源按已安装的 `roj` skill | 核实的题面、完整约束、样例与来源 |
| 2. 规划 | [`oj-solution-planner`](../oj-solution-planner/SKILL.md) | 候选算法、关系、证明、复杂度、代码与测试计划 |
| 3. 实现 | 先按 [阶段 3](references/stages.md) 取 rbook 代码模板（本地 `RBOOK2_CODE_PATH` 优先，缺失时走 `rbook-http`）；再按 [`oj-cpp-style`](../oj-cpp-style/SKILL.md) 写，Python 按下文路由 | 与计划一致的源码、代码对应记录、模板来源或跳过理由 |
| 4. 验证 | [`oj-judge-and-stress`](../oj-judge-and-stress/SKILL.md) | 实际命令、适用范围、结果和边界证据 |
| 5. 写作 | [`oj-problem-analysis-writer`](../oj-problem-analysis-writer/SKILL.md)、[`oj-problem-format-spec`](../oj-problem-format-spec/SKILL.md)、[`rbook-markdown`](../rbook-markdown/SKILL.md) | 草稿与正式 `index.md` |
| 按需教学补充 | [`oj-sample-visualizer`](../oj-sample-visualizer/SKILL.md)、[`oj-problem-relation-writer`](../oj-problem-relation-writer/SKILL.md)，必要时已安装的 `rainboy-brain` | 服务于当前任务的图示、关系或关键解释 |
| 按需：挂载 rbook 文章 | [`oj-show-at-rbook`](../oj-show-at-rbook/SKILL.md)，用户同意后才执行 | `showAtRbook` 已更新、id 已校验 |
| 6. 审查交付 | [`oj-problem-analysis-reviewer`](../oj-problem-analysis-reviewer/SKILL.md)、适用仓库检查 | 已解决问题、检查证据与明确交付状态 |

教学补充可在规划或写作时开展，不必等正文全部写完。先评估必要性，再加载专项 skill；没有教学价值的图示和无依据的关系不机械生成。

### 语言与学习目标

用户语言要求优先；未指定时结合当前任务、已有主解和仓库约定选择，不因发现某个语言 skill 就改语言。已有多语言实现按实际算法关系核对。

- C++ 按 `oj-cpp-style` 实现。
- 用户要 Python/Pythonic 学习时，使用已安装的 `python-oj-learn` 检索笔记、完成语言表达与教学；复用 planner 的算法结论，必要调整反馈给规划阶段。其一般解题流程不重复已经完成的阶段，评测和正式文章采用本仓库的 judge、writer 与 format 规则。
- 用户明确要 Python 教学短解法时，再读取 [`oj-python-style`](../oj-python-style/SKILL.md)。展开式教学代码不强制压缩；旧资料中的 `python-oj-short` 指这个现有 skill。
- 教学短变体允许的 TLE/MLE 不等于正式主解通过。如果任务要求可提交程序，必须另有满足要求的实现，或明确报告目标尚未完成。
- Python 提交按题目时限的 **3 倍**评测（内存沿用题目上限），细则见 [`oj-judge-and-stress`](../oj-judge-and-stress/SKILL.md)。同阶复杂度仍不可放宽。

## 执行纪律

新算法先在临时目录验证再写正式文件、一次只改一个变量、关键结论先穷举验证、复杂度用实测定阶、验证分级、恢复任务先量化原解再动手。这些规则和实际耗时案例见 [`references/execution-discipline.md`](references/execution-discipline.md)，实现与验证阶段开工前读一次。

不要在等待外部结果时空转：子代理审查、外部抓取、用户确认尚未回来时，先做不受它影响的工作（生成数据、写不依赖该结论的章节、跑与它无关的验证）。需要用户决策的问题一次问全，不拆成多轮串行等待。

## 返工与继续

| 发现的问题 | 返回位置 | 需要重新核对 |
| --- | --- | --- |
| 题意、约束或样例来源矛盾 | 材料阶段 | 所有依赖被修正事实的结论 |
| 反例推翻算法、证明不成立、复杂度超限 | planner | 相关代码、测试计划、布局与正文 |
| 算法正确但实现有误 | 实现阶段 | 失败用例及受影响的原有验证 |
| 测试环境故障、无答案文件、资源计量无效 | 验证阶段 | 修复设施或补证据，不能改报 AC |
| 正文与已核验实现不符、推导跳步 | writer；必要时 planner | 对应章节、复杂度与代码引用 |
| 图示、关系、路径或元数据错误 | 对应专项阶段 | 受影响资源及文章检查 |

修正后只重跑受影响的验证与审查；已经有效的结果保留。证据要能对应当前代码，不能拿修改前的通过记录替代修改后的检查。只有格式或措辞变化时，不重复整套算法测试。

遇到外部材料或运行环境阻碍时，先完成不依赖它的授权工作，记录实际尝试与剩余缺口；不能将受阻项自动标为不适用。缺少决定性信息才询问用户，不以常规阶段交接为由停下。

## 完成与报告

以最初确认的任务终点验收。完整题解要求：选中算法的依据明确、必需实现与验证已完成、正文和资源一致、审查中的必须修问题已解决、适用检查完成。无法执行的必需项单独报告，不能称为完整通过。

最终简洁报告题目目录、主解与布局、实际文件、实际验证、未完成项。区别规划完成、代码完成、测试通过和文章完成；本地结果不能写成官方 AC。用户授权过的后续动作按其范围执行，不额外加入提交或发布流程。

报告结束后询问用户是否要更新 `showAtRbook`（把题解挂到 rbook 书的对应文章下）。用户同意才进入 [`oj-show-at-rbook`](../oj-show-at-rbook/SKILL.md)，不自动执行；用户没要求时不要自己写入这个字段。该 skill 只维护 `showAtRbook`，`pre` / `common` / `recommend` 仍归 `oj-problem-relation-writer`。
