# OJ 题目解析审稿

这个 skill 专门审查已有题目解析是否能让读者学会这道题。

默认读者会相关算法，但不会本题的解题思路。审查目标是读者能否低负担地复现思路发现过程。

**写作规则不在本文件里重复。** 本文件只写审稿动作、定级和报告格式；判定标准一律回溯下表，避免 writer 与 reviewer 各维护一份而漂移。

| 要审的东西 | 规则出处 |
| --- | --- |
| 读者基础、句子与段落、标点、讲解路线、篇幅（先主线、再按需展开）、证明按需展开、充要条件分方向 | [reader-and-explanation.md](../oj-problem-analysis-writer/references/reader-and-explanation.md) |
| 文字去模板化与自然度 | [humanizer-zh](../humanizer-zh/SKILL.md) |
| 章节骨架、布局与总览表、形式化题目、代码嵌入、图表说明 | [oj-problem-format-spec](../../oj-problem-format-spec/SKILL.md) 与其 `references/layouts.md` |
| 图示规模与放置 | [visualization.md](../oj-problem-analysis-writer/references/visualization.md)、`docs/problem-visualization.md` |

默认只审稿并输出报告；只有用户明确要求“修复”“改写”“应用建议”“直接改”时，才编辑 `index.md`。用户明确指定其他读者基础时，以用户要求为准。

## 边界

本 skill 负责：

- 审查已有 `problems/<oj>/<problem_id>/index.md` 的讲解质量。
- 判断题解是否存在跳步、只贴代码、样例解释不足、图表说明不足等问题。
- 对照 `main.cpp` / `brute.cpp` 检查文字和代码是否能互相对应。
- 检查 `description` 是否与 `06-distill.md` 定稿逐字一致，以及 `tags`、`pre` / `common` / `recommend` 的表达是否有明显质量问题。
- 调用已有检查工具提供基础信号。
- 在用户明确要求修复时，修改 `index.md` 并尽量保持原文风格。

本 skill 不负责：

- 从零写一篇题解。
- 发明新的算法解法。
- 维护题目关系字段的候选生成。
- 渲染关系图或样例可视化。
- 默认修改 `main.cpp` 或 `brute.cpp`。

从零完成代码与题解使用 `oj-problem-workflow`；已有可靠材料的正文写作使用 `oj-problem-analysis-writer`。
在 workflow 中审查时输出问题清单，由协调者按既有授权安排返修；本 skill 不重新启动总流程。
格式骨架使用 `oj-problem-format-spec`。
样例可视化使用 `oj-sample-visualizer`。
题目关系和推荐练习使用 `oj-problem-relation-writer`。

## 读取顺序

审稿时优先读取：

1. `problems/<oj>/<problem_id>/index.md`
2. `problems/<oj>/<problem_id>/main.cpp`
3. `problems/<oj>/<problem_id>/brute.cpp`
4. `problems/<oj>/<problem_id>/problem.md`
5. `problems/<oj>/<problem_id>/problem-analysis-workspace/*.md`
6. `.agents/skills/oj-problem-format-spec/SKILL.md`
7. [读者与讲解规范](../oj-problem-analysis-writer/references/reader-and-explanation.md)（评价正文前必读；仅核对必要材料，不因引用此文件启动 writer 流程）
8. [humanizer-zh](../humanizer-zh/SKILL.md)（文字去油与去模板化检查标准）

如果只是审稿，不要修改文件。

如果用户要求修复，修改前必须读取 `oj-problem-format-spec`，并保留已有有价值的用户内容。

## 工具检查

审稿时先运行已有确定性工具：

```bash
python3 scripts/problem-analysis-tools/check_problem.py problems/<oj>/<problem_id>
python3 scripts/problem-analysis-tools/check_relations.py problems/<oj>/<problem_id>
```

如果以后存在下面的质量检查脚本，也要运行：

```bash
python3 scripts/problem-analysis-tools/check_analysis_quality.py problems/<oj>/<problem_id>
```

工具报告是审稿输入，不是最终结论。不要机械复述工具输出，要结合题解内容判断是否真的影响读者理解。

## 审稿维度

按“读者能否学会”组织审稿，而不是只按文件结构罗列。每节只列判定信号，标准按开头表格回溯。

### 学习目标

- 读者能否明白要计算什么，是否必须依赖输入输出格式细节才能理解。
- 篇幅是否用在本题的观察与选择上，而不是重讲读者已掌握的基础算法。

常见问题：

- 形式化题目保留了故事背景或无关信息。
- 有真实操作序列却不写中文动作；或没有过程、只有一次性选择，却把同一件事拆成“动作 + 式子”写两遍。
- 没有解释约束为什么影响算法选择。

### 推导链条

- 讲解路线是否贴合真正的难点：建模路线交代题目到模型的对应与合法性，骨架路线补齐每个关键操作的动机。
- 朴素想法、特例、失败尝试是否确实推出下一步。
- 是否解释关键观察从哪里来，而不是直接给结论。

常见问题：

- “显然可以 DP”但没有定义状态来源；“贪心即可”但没有交换、反证或不变式；“建图跑最短路”但没有节点和边的含义。
- 正确性证明完整，却没交代为什么会想到这个模型。

### 阅读负担与篇幅

- 每个 `### 思路` 的主线能否在 6 句内跑通（当前困难 → 关键观察 → 做法 → 为什么成立）。读者必须回翻记号、连续读完长证明才能接上，按**必须修**。
- 主线之外新增的每段能否说出它消掉哪个具体阅读障碍；说不出且删掉不影响复现关键转折，按**建议修**删减，不以“补充说明”为由保留。
- 新定义是否先交代用途，符号是否在需要时出现；是否频繁换例子或提前使用未解释的结论。
- 是否重复铺陈同一结论，或把常识性操作讲得很长、真正的选择理由一笔带过。
- 是否用“显然”“自然想到”“很简单”等措辞掩盖推理缺口。

### 公式与直觉

- 4 行以上无中文说理的密集公式链、坐标化投影、冗长代数放缩，按**必须修**。
- 能用结构性质或一组具体数值说清却写成符号推导，按**建议修**改为数值或文字。
- 只有公式、读者必须先猜到用途才能继续读，按**必须修**；关键公式只定义符号、公式后没说它在讲什么，按**建议修**。
- 反向也要看：把读者已能看懂的每行化简逐行翻译成中文，同样按**建议修**处理（重复解释挤占主线）。
- 容易产生“局部贪心”等错误直觉的题目，是否给了干净的极小反例；把结论讲对却让读者自己踩坑，按**建议修**。

### 直觉与证明

- 需要展开的证明是否每项推进一步、依据可追溯；箭头是否混淆推出与等价。
- 一句话能写清或前文已证的结论被重证一遍并挤占主线，按**建议修**。
- 充要结论：方向标反、只证一半就宣称等价，按**必须修**；未分两段、用裸箭头标签、平凡等价未说明依据，按**建议修**。
- 关键动机缺失、必须依赖未解释定义才能继续、决定正确性的证明缺口，按**必须修**。
- 允许结论先在正文使用、证明后置；检查使用处是否说明了并指向真实存在的证明，不因证明在选读就要求搬回正文。
- 例子、图示和未经证明的猜想是否被冒充为一般论证。

### 状态和模型

按题型重点检查：

- DP：状态定义、转移来源、初始化、遍历顺序、答案位置。
- 图论：节点含义、边含义、方向/权重、遍历或松弛逻辑。
- 贪心：选择标准、为什么局部最优能推出全局最优。
- 搜索：状态、扩展方式、剪枝条件、正确性风险。
- 数据结构：维护的信息、操作含义、复杂度来源。

### 代码对应

检查：

- 正文中的变量名和 `main.cpp` 是否能对应。
- 核心循环是否在正文中解释。
- 边界处理是否只藏在代码里。
- `brute.cpp` 是否说明了朴素思路或对拍用途。

不要做逐行代码讲解。重点是“思路和实现之间是否接得上”。

### 样例和可视化

- 样例中的关键数据是否被解释。
- 图/表是否有图前一句、图后 1–3 句；只有一处观察时可并入图前那一句，不因句数少判错。表格是否说明行、列与单元格含义。
- 正文讲解的图论定理、决定解法的结构结论是否配了展示关键关系的图解；缺失或图未展示关键关系，按**必须修**。多个推理步骤可复用同图。
- 其他只能锦上添花的图示缺失只算**建议修**，不能把“有样例树图”当成所有结构结论已获图解。

### 元数据

检查：

- `description` 是否与 `problem-analysis-workspace/06-distill.md` 里定稿的那一行**逐字一致**。不一致列为必须修，不用自行改写：回到浓缩阶段重跑，再由 writer 同步 `index.md`。
- `06-distill.md` 缺失或其中没有一行定稿时，不能当成已通过；列出为必须修。
- 动作链本身是否合规：2～4 项、用 ` + ` 连接、每项是“对象或条件 + 动作”而不是“贪心 + DP + 图论”这类泛标签、没有把普通累加称为前缀和或把 last 数组一概称为去重。
- `difficulty` 是否缺失、是否为标准枚举、是否和题解中的算法复杂度与知识点明显不匹配。
- Luogu 题目的 `difficulty` 是否与官方 `difficulty` 字段一致（id→枚举映射见 `oj-problem-format-spec`）；凭印象猜测的难度视为质量问题。
- `tags` 是否和题解内容一致。
- `pre` / `common` / `recommend` 的 `reason` 是否具体。
- `recommend.reason` 是否说明推荐关系，而不是只有“类似题”。

关系字段的具体维护仍由 `oj-problem-relation-writer` 负责。

## 报告格式

默认输出中文审稿报告，按严重程度排序：

```text
必须修
- [推导链条] ## 思路 直接给出结论，没有解释为什么可以使用这个模型。
- [标点] 第 18 行正文误用了英文半角逗号与句号。按共享规范改为中文全角标点“，”与“。”。
- [证明方向] 第 48 行充要结论只写了 `**充分性（$\Leftarrow$）**`, 裸箭头无法判定指哪一侧. 改为写明中文方向, 如 `**充分性（等式成立 $\Rightarrow$ 点在路径上）**`.

建议修
- [篇幅] 第 76 行整段在重复已确定的结论, 删掉后读者仍能接上; 保留一条即可.
- [公式解释] 第 76 行的编号公式 (1) 后文直接引用, 却没有一句中文说它在讲什么. 补「左边是家放在某点时的耗时, 右边是取直径端点时的上限」.
- [样例和可视化] 第 42 行 DP 表后缺少说明，读者不知道当前格从哪里来。

可选优化
- [元数据] tags 可以再补一个结构类标签。

已通过
- frontmatter 字段完整。
- main.cpp 引用存在。
```

规则：

- 每条问题要指出位置或章节，并说明为什么影响读者理解。
- 能给改法时给具体改法，不写泛泛建议。
- 定级按实际阅读障碍：读者会被卡住或学到错结论的按必须修；能读懂但读得累、或有更短写法的按建议修。不因段落较长、出现公式或句数偏多就直接判必须修。
- 自然语言范围内出现英文半角句读，按必须修；起跑式报幕与生造翻译词，按建议修。
- 修改建议优先重排概念依赖、合并重复解释、复用例子、后置技术细节；只有缺失关键理由时才补内容，避免审稿越修越长。
- 如果没有明显问题，明确说“未发现必须修的问题”，并说明剩余风险。

## 修复模式

只有用户明确要求修复时才编辑。

修复原则：

- 优先小改，不整篇重写。
- 保留用户原有表达中有价值的部分。
- 拆句、拆段或改为证明列表时保留原意、条件和推理方向。标点修改只作用于本次范围内的自然语言，保留技术语法与原文引用。
- 不改变 `@include-code(./main.cpp, cpp)` 和 `@include-code(./brute.cpp, cpp)` 的规范位置，除非原文明显错误。
- 不编造题面或算法事实；不确定时写入审稿报告，不写进正式正文。
- 修改后运行 `check_problem.py`；如果存在 `check_analysis_quality.py`，也运行它。

修复完成后说明：

- 改了哪些章节。
- 哪些问题已解决。
- 哪些问题仍需人工确认。
