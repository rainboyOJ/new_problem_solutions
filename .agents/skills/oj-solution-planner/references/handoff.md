# 与实现、验证和写作交接

规划沿用 `problem-analysis-workspace/`，不另建一套平行计划。保留已有有效笔记，简单题允许合并文件，交付时说明实际位置。工作区保持本地忽略，不作为共享 CI 的必需输入。

## 材料归属

| 文件 | 规划阶段提供 | 后续补充 |
| --- | --- | --- |
| `01-problem-understanding.md` | 题意、来源、完整约束和官方子任务 | 有冲突时核实题面 |
| `02-observation-and-model.md` | 候选解法、关系、取舍、布局建议 | writer 确认正式布局；实现后复核 |
| `03-solution-derivation.md` | 选中方案的步骤或伪代码、关键推导 | 实现差异与路线调整 |
| `04-correctness-and-edge-cases.md` | 证明、边界、未解决义务、测试计划 | 验证执行者记录实际命令与结果 |
| `05-complexity-and-implementation.md` | 时间空间复杂度、参数、代码文件计划 | 实际变量、数据结构和文件对应 |
| `06-final-index-draft.md` | 本阶段不生成 | writer 生成文章草稿 |

文件名是现有工作流的约定，文件存在不意味着内容完成。规划中的文件路径可以标为“拟新增”；只有真正存在且可用的源码才可被正式文章引用。

## `02` 的最小内容

先记录观察与候选，再填写 `文章结构判定`。以下为填写提示；可以简写，但不能把空字段或备选值当作完成记录。

```markdown
## 候选解法与关系

- 真实约束与子任务：注明来源；分析特例单独标注
- 候选解法：名称、核心观察、适用范围、时间空间复杂度
- 关系：优化、推广、特例、替代或同一算法的不同实现
- 教学取舍：哪些独立展开、哪些合并或省略，以及原因
- 实现计划：拟复用或新增文件、共享实现的理由
- 证据与缺口：各方案的论证、实现和测试状态

## 文章结构判定

- 判定状态：规划建议 / 写作已确认 / 实现后已复核
- 建议布局：四种布局之一及依据
- 选定布局：writer 确认后填写；仅规划时注明尚未进入写作
- 正式主解：拟采用的算法和文件；尚未确定时说明缺口
- 验证后调整：实际调整与依据；尚未实现或测试则如实注明
```

已有 `02` 使用旧版字段时保留有效内容，补齐缺失语义即可，不为字段改名重写全部记录。合并文件中保留 `## 文章结构判定`，方便后续找到选择依据。

## 状态分别记录

对每个选中方案分别记录以下事实，不用一个笼统的“已完成”代替：

- **算法描述**：是否具体到可实现的步骤。
- **正确性论证**：关键结论是否有证明，未解决义务是什么。
- **实现状态**：尚未实现、已有实现待核对或已核对，并注明实际路径。
- **测试状态**：未运行或真实命令、范围和结果，失败时保留失败事实。

“写作已确认”只说明文章组织已确定，“实现后已复核”说明实现与路线已核对，均不自动代表测试通过。只有规划的任务可以在没有代码时交付；完整题解任务仍应继续完成其要求的实现和验证。

## workflow 与 writer 如何消费

1. 检查题面来源、选中算法的适用范围、正确性理由、复杂度及关系是否足以写作；已有可靠规划直接复用，只补缺口。
2. 根据规划建议和教学取舍确定正文布局，更新 `选定布局`；表格与章节形式读取格式 skill，不复制新的格式规则。
3. workflow 按任务范围安排实现与验证，执行 agent 使用相应风格和评测 skill，记录实际结果。writer 不重跑已完成的阶段；风格改变不能悄悄改变算法。
4. 若代码不符、发现反例或关键证明缺失，将缺口返回当前 workflow，由协调者回到 planner 或实现阶段修正，再继续写作。不重新启动总流程，也不能仅改措辞掩盖问题。
5. 以核验后的路线组织正文；只保留帮助读者理解的推导、证明与边界，不复制整个探索记录，也不假装最终解法是在真实比赛中逐步发现的。

格式工具只能检查结构和引用，不能证明路线合理。报告中区分规划完成、代码实现、测试通过和文章完成。
