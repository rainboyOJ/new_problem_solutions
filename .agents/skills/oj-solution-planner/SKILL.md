# OJ 解题路线规划

以正在比赛的选手视角分析题目：先找到当前能证明正确、实现可靠的方案，再研究扩大适用范围的办法。有明显子任务结构时，优先从这些可见线索推进；不要直接拿最终算法替代分析，也不要为凑层数制造中间方案。

产出的是可核验的解法路线与论证摘要，不是完整文章，也不是模拟真实比赛经历的思考日记。路线可以是链、分支、独立替代方案，或一个直接解法。

## 职责与任务范围

- 本 skill 决定候选算法、适用条件、推进关系、证明义务、复杂度、实现计划和布局建议。
- [`oj-problem-workflow`](../oj-problem-workflow/SKILL.md) 协调整体阶段；[`oj-problem-analysis-writer`](../oj-problem-analysis-writer/SKILL.md) 消费规划材料，组织正式题解；[`oj-problem-format-spec`](../oj-problem-format-spec/SKILL.md) 规定章节和引用形式。
- 实现由执行任务的 agent 完成，按语言读取 [`oj-cpp-style`](../oj-cpp-style/SKILL.md) 或 [`oj-python-style`](../oj-python-style/SKILL.md)。风格规则不代替算法选择与正确性论证。
- 实际样例、对拍和性能验证使用 [`oj-judge-and-stress`](../oj-judge-and-stress/SKILL.md)。规划测试不等于已经运行测试。
- `rainboy-brain` 若可用，可用于深入解释某个观察如何发现或为何成立；本 skill 不依赖它才能完成路线规划，也不复制其教学文案规则。

用户只问思路时，在回答中交付规划，不自动修改代码或 `index.md`。用户要求仓库内完整题解时，由 workflow 安排后续阶段；本阶段把规划写入既有 workspace 并返回协调者。已在 workflow 中时不重新进入总入口；规划完成不是整个任务完成。skill 分工不要求启动多个 agent。

## 先建立题目事实

先读题面、完整约束、样例和官方子任务，再核对已有笔记、代码与文章。已有材料用于复用和校验，不限制候选解法的范围。若只有目录，先查本地材料；缺失且无法取得的决定性条件明确列出，不凭文件名猜测题意。

新题尚无方案时，先做约束与直接做法分析，再用已有完整实现校验。已有解法的补写或整理任务可以直接复用可靠结论，但应标明来源，不编造“从未见过答案”的发现经历。

区分以下内容：

- **题目事实**：原题明确给出的规则、约束、测试点或分值。
- **分析特例**：为理解问题主动简化的条件，不冒充官方子任务。
- **算法结论**：有证明支持的适用范围、行为和复杂度。
- **实现与测试事实**：实际代码做什么、跑过什么数据及结果。

## 规划流程

### 1. 拆分约束，判断是否存在分层线索

检查规模、值域、可变参数、重复性、单调性、图结构、操作类型等条件。对每个有用的限制追问：它是否减少选择、状态、依赖或存储？它是否允许更简单的正确算法？

题面分了五档不意味着要写五个算法。比较各档约束的包含关系；“树结构”和“小值域”可能是两个互不包含的分支，不能仅按测试点编号连成一条优化链。

没有官方子任务时，也可以分析有依据的小规模或特殊情形，但明确标为分析特例，不编造得分。

### 2. 建立可靠起点

给出最自然的正确做法，具体到能执行的步骤；它可能是枚举、模拟、直接计数、简单 DP 或公式。说明为什么覆盖全部合法方案，估算时间与空间，指出适用约束。

按点拿分要求每个选中的方案在声明范围内可靠，不把未经证明的启发式当作部分分保证。已知官方分值时才能估算得分，重复覆盖的子任务不能重复计分；只有复杂度估计时写“预计适用”，不能声称实测通过。

直接做法已覆盖全范围且没有独立教学层时，就保留直接解法；不要人为降低效率来制造暴力。如果用户给出比赛时间预算，再结合实现成本和出错风险选择优先方案，不虚构剩余比赛时间。

### 3. 从当前瓶颈提出下一步

每次保留有用的推进时回答：

1. 当前方法具体卡在哪里：重复操作、状态数量、搜索分支、内存，还是某个假设即将失效？
2. 保留哪个模型或观察，新观察从题面或已证结论的哪里来？
3. 新算法具体怎样执行，为什么仍然正确？
4. 相比前层，改善了什么，新的适用范围和复杂度是什么？

有效推进包括消除重复计算、压缩状态、确定构造顺序、改进查询维护方式、取消值域或结构假设。复杂度不要求严格下降：取消特殊条件后，即使同阶或有所增加，只要在扩大后的范围内可行，也可能是有效推广；同时报告代价。

区分概念突破与实现优化。仅换语言、改变量名或等价改写容器通常不是新解法；确实改变性能或适用范围的数据结构替换可以保留，但不包装成新的算法思想。

没有自然承接关系时，将新方案标为独立替代或分支，不补造“由上一层必然推出”的故事。若最终模型已经清楚，不必继续枚举无关方案。

### 4. 论证并安排验证

每个拟采用方案都要有关键正确性理由、边界、时间与空间复杂度及参数定义；DP 说明状态充分性和转移，贪心说明选择为何安全，图模型说明对应关系。未证明的候选可以保留，但明确缺口，不交给 writer 作为确定结论。

测试计划按各方案适用范围设计：小数据与可靠基线比较，特殊假设的边界单独覆盖，优化版本补性能边界。对拍只检查共同适用范围；不能要求部分分实现通过满范围数据，也不能从小数据一致推断全范围正确。

代码发现的新限制、反例或资源问题要反馈到规划，修正结论后再写文章。测试不能代替证明。

### 5. 整理解法关系与教学取舍

给候选解法一个简短标识或名称，按需要记录以下关系，无需对所有候选两两比较：

- **优化**：沿用模型，减少时间或空间消耗。
- **推广**：复用观察，取消限制性假设，说明可能增加的代价。
- **特例**：依赖额外条件，可以帮助发现规律，但未必是通向正解的独立一层。
- **替代**：独立完整算法，适合比较取舍。
- **同一算法的不同实现**：原则上合并，同一行可以关联多份代码。

先确定哪些层值得展开，再规划必需文件；没有代码也能先做判断。多个 `main*.cpp` 不是多算法证明，`main.cpp` 与 `main.py` 也可能属于不同算法。共享实现或只需解释退化情形时注明理由，不按子任务数生成文件。

存在分支时选出有依据的教学主线，其余特例作为明确分支或补充；如果没有主线，就报告实际关系，不为了套布局强行连接。

### 6. 给出布局建议并交接

满足教学条件时，建议优先考虑：

1. **子任务递进型**：真实约束支持有价值的推进主线，能说清复用观察和解除的瓶颈或假设。
2. **并列多解法型**：至少两个值得独立讲解的完整替代算法。
3. **暴力到正解型**：朴素方法清楚暴露最终解法消除的瓶颈。
4. **直接正解型**：没有值得独立展开的其他层。

可以建议“递进主线＋特例补充”，但不要新增未经格式规范支持的布局名。writer 根据关系选择正式结构，记录删并取舍，不能修改算法事实来迁就标题。

## 交付与停止条件

写 workspace 或交给 writer 前，读取 [`references/handoff.md`](references/handoff.md)，按其中约定记录材料和状态。一般问答可直接简洁回答，不强制建立目录或填完整模板。

规划可交接的条件是：选中方案具体可执行、适用约束明确、关键结论有论证、复杂度可核算、关系及取舍有依据、实现验证工作可安排。仍有缺口则交付已可靠得到的部分和具体未完成项，继续处理授权范围内可解决的问题，不把猜想写成正解。

概念性自查：

- 多档约束被同一算法覆盖时，能否合并而不是生成重复代码？
- 两层同阶但后一层取消假设时，能否识别有效推广？
- 两个子任务互不包含时，是否保留分支而不是虚构线性递进？
- 同语言不同算法、跨语言同算法，是否都按核心模型正确归类？
- 简单直接题、仅思路请求、仅格式任务，是否保持合理工作范围？

这些是判定边界，不是要求每篇输出逐项复述的检查表。
