# RBook Markdown 写作规范

这份规范只记录仓库中已有、可由实现或文档验证的规则。它不替代算法题解的
内容写作，也不把个人审美偏好伪装成项目硬性要求。

## 通用正文

### 结构和可读性

- 每个段落只表达一个意图；长推导拆成短段落和三级标题。
- 标题层级按 `##` -> `###` 递进，不跳级，不用一级标题制造页面题名。
- 标题要描述读者将得到的内容，例如“状态定义”“边界情况”，不要使用空泛的
  “一些想法”。标题会生成锚点，改名会影响 TOC 和外部链接。
- 代码、命令、路径、变量名和语法关键字使用反引号；多行程序使用带语言标签的
  围栏或 `@include-code`。
- 需要读者观察的表格、图和代码前后都写解释。可视化是教学内容，不是装饰；
  遵守 `docs/problem-visualization.md` 的规模和说明要求。
- 资源路径优先使用相对于当前 Markdown 文件的 `./...` 或 `../...`，并检查文件
  是否确实存在。

### 代码块

- 语言标签写真实语言或项目支持的别名，例如 `cpp`、`python`、`javascript`、
  `haskell`、`text`、`mermaid`、`dot`。
- 输入输出样例用 `text`、`input` 或 `output`，避免被当成可执行语言高亮。
- 题解中可运行的正式代码优先引用同目录源码，不要复制一份容易过期的代码。
- 当前最终围栏 renderer 尚未启用 code tabs 的 Tab UI；需要展示多个实现时使用
  独立的带语言代码块或普通标题，不要依赖 `[group:tab]` 产生交互。
- 代码旁的解释说明“这段代码对应哪一步推导”，不要只贴完整程序而不建立对应关系。

### 链接、图片和外部资源

- 链接文字应说明目标内容；裸 URL 仅在确实需要展示地址时使用。
- 本地图片必须有描述性 alt 文本。图片只解释结构或过程时，在前后文字中说明
  读者应观察的关系。
- 远程图片、iframe、gallery 和外部脚本可能失效；同时提供正文解释或普通链接
  降级，不要让外部资源成为唯一信息来源。
- 不要通过 raw HTML、`style` 容器或脚本绕过正常 Markdown 结构来修复排版问题。

### 公式与符号

- 行内公式使用 `$...$`，独立推导使用 `$$...$$` 或 `\begin{...}` 环境。
- 公式中的变量、集合和关系保持符号一致；代码变量放在反引号中，不混用两种
  标记表达同一语义。
- KaTeX 不支持的命令不会抛错而可能显示错误文本；写完复杂公式后进行实际渲染
  检查，并准备文字或代码解释。

## 按文件类型写作

### 正式题解 `problems/**/index.md`

同时读取并遵守 `.agents/skills/oj-problem-format-spec/SKILL.md`。关键边界如下：

- frontmatter、字段顺序、`[[TOC]]`、固定章节和 `@include-code` 以该 skill 为准。
- 题解正文只使用规范允许的标题层级；不要在本 skill 中重新发明 frontmatter
  或章节模板。
- 单解法题通常在 `## 代码` 引用 `main.<ext>`；算法题的暴力代码和多解法布局
  遵守题解格式 skill 的要求。
- `## 形式化题目` 去除故事背景，表达数学结构；不要把输入输出格式重新抄一遍
  作为形式化题目。
- DP、树、图、网格、搜索和复杂模拟题先评估可视化价值。每个图/表前说明目的，
  后说明读法；图示规则详见 `docs/problem-visualization.md`。
- 题解的解释重点是“为什么这样建模、转移或贪心”，不是把代码逐行翻译成中文。

### 原题面 `problem.md`

`problem.md` 是抓题产生的题面归档。保留题面语义和必要公式/样例，不补题解
frontmatter，不添加 `@include-code`，不把归档改造成正式文章。

### 题单 `problem-sets/*.md`

- 使用任务列表表示完成状态，使用 `[[problem: oj,id]]` 或 `[[oj/id]]` 链接仓库题目。
- 条目文字保持短小，必要的题目背景放在链接后的普通句子中。
- 题单不套正式题解的 `## 形式化题目`、`## 思路` 等章节模板。

### 项目文档和 README

- 先说明命令/流程的目标，再给最小可运行示例。
- 命令、环境变量和路径使用代码格式；说明当前目录或前置依赖。
- 示例应与当前代码一致；如果是兼容旧行为，明确标注历史或迁移状态。
- 不为了展示扩展而堆叠 admonition、emoji、图和容器。

## 提示框与可视化的选择

按信息作用选形式：

| 目的 | 首选 |
| --- | --- |
| 一条重要提醒或边界 | `!!! warning` / `!!! note` |
| 证明、定义、引理 | `!!! theorem` / `!!! definition` / `!!! proof` |
| 需要折叠的长补充 | `::: fold` |
| 变量或状态的精确数值 | Markdown 表格 |
| 流程、状态转移、局部树 | Mermaid |
| 样例图、DAG、无向图 | Graphviz `dot` |
| 普通树、二叉树、线段树图片 | `tree_draw.py` 生成的 SVG |

不要用提示框替代正常段落；不要用 Mermaid 绘制十几层完整搜索树；不要把一个
可以用三行表格说明的状态变化做成依赖外部脚本的大图。

## 修改与审查清单

提交 Markdown 前逐项检查：

- 文件类型判断正确，题解文件已同时遵守 `oj-problem-format-spec`。
- Frontmatter 的 YAML 可解析，正文没有把 frontmatter 内容重复写成标题。
- 标题层级连续，`[[TOC]]` 位置正确（正式题解需要时）。
- 每个自定义块有匹配的结束标记；列表、引用和代码块的缩进正确。
- `@include-code` / `@include_md` 路径从当前文件解析，引用文件存在。
- 图片 alt、公式分隔符、代码语言标签和题目 ID 格式正确。
- Mermaid/Graphviz 的图前图后说明存在，规模没有超过教学目的。
- 没有把旧版插件、未注册语法或未经验证的 HTML 当成当前能力。
- 对自定义语法运行了聚焦渲染或相关测试；如果没有运行，明确说明剩余风险。
