# OJ 题目解析写作

将可核验的算法材料组织成读者能够理解的正式正文。完整任务的阶段协调由 [`oj-problem-workflow`](../oj-problem-workflow/SKILL.md) 负责；算法探索由 [`oj-solution-planner`](../oj-solution-planner/SKILL.md) 负责；格式与 Markdown 分别以 `oj-problem-format-spec`、`rbook-markdown` 为准。

默认读者会相关算法，但缺少本题的解题思路。入口负责核对材料、选择讲解风格和协调写作；通用内容标准在 [读者与讲解规范](references/reader-and-explanation.md)，风格专属要求按下面的路由加载。

## 入口与范围

- 已由 workflow 进入写作阶段时，只消费交接材料并执行本 skill；发现缺口返回当前协调阶段，不重新启动 workflow。
- 用户直接点名本 skill 且要求从题目到代码、验证和文章的完整任务时，一次性交接给 workflow。它后续再次进入本 skill 时只执行写作，不形成循环。
- 用户只要求按现有材料写正文或局部修订时，保持该范围；可以核对必要算法事实，不能自动扩展为多份代码、全题迁移或整套测试。

## 写作顺序

1. 确认目标目录、读者基础与正文范围，读取题面、已有 `index.md`、实际源码和过程记录。有代码必须读，不能只看文件名、算法标签或规划摘要。题面定义问题，代码用于核对实际算法，二者冲突时查明缺口。
2. 按 planner 的交接状态核对算法描述、证明、复杂度、实现与验证证据。没有代码但已有可靠、完整的解法推导时，可在纯写作范围内继续，并说明判断依据；材料不足以确定算法时指出具体缺口，在 workflow 内交回协调者，独立任务向用户询问，不猜测、不自动新增实现。
3. 按下节为每个独立解法选择主风格，再读取所选 prompt。读取共享讲解规范、格式 skill 和当前场景需要的 references；分别确认讲解风格与文章布局，在 `02` 的 `文章结构判定` 中简短记录依据。
4. 每个独立解法先按共享规范写一个 `info` admonition：标题一句话概括，框内让掌握相关知识的选手约 30 秒读懂做法与关键理由。随后按选定风格展开思路，按共享规范安排证明、边界、复杂度和图示，按格式规范引用实际代码。需要新实现或实际测试时交回 workflow 对应阶段；仅写文章的任务报告缺口，保持范围。
5. 形成 `07-final-index-draft.md`，读取 [`humanizer-zh`](../humanizer-zh/SKILL.md) 润色后写回 `index.md`，保留有效 frontmatter 和有价值的用户正文。局部修订只更新相关内容。`description` 原样采用 `06-distill.md` 的定稿行，不改写；缺失或不符时报告并交回浓缩阶段，不自行编造。
6. 按 [写作完成核对](references/writing-completion.md) 检查并报告。完整任务由 workflow 接续审查与最终交付；单独写作任务交付本次范围内的结果。

## 讲解风格路由

**每个独立解法选一种主风格。** 同一算法的 C++、Python 等实现共用一次选择；多个独立解法可以采用不同风格。风格决定一个解法怎么讲，四种文章布局决定各解法之间如何组织，两者分别判断。

1. **用户指定优先。** 用户指定全文或某解法的风格时按其范围执行，在该风格内调整讲法；确实无法满足要求才说明冲突。不因自动判断不同而覆盖用户选择。
2. **未指定时定位理解障碍。** 结合题面、实际代码与可靠推导，判断读者从条件走到当前算法时最先会卡在哪里。代码中的算法名称、语言、行数和函数数量都不能直接决定风格。
3. **按下表选择并加载。** 无须逐次询问确认，只读取当前解法的主风格 prompt；其他独立解法选了另一种风格时，才加载另一份。

| 理解障碍 | 主风格 | 选择后读取 |
| --- | --- | --- |
| 不知道为什么要这样表示、定义状态或转化问题；直接给算法会依赖尚未解释的模型 | 逐步建模 | [stepwise-modeling.md](styles/stepwise-modeling.md) |
| 操作本身容易理解，难点在各步骤怎样配合；先看全貌更容易理解 | 骨架展开 | [skeleton-expansion.md](styles/skeleton-expansion.md) |
| 已理解做法和对象，但不相信支撑算法的关键结论成立 | 关键结论论证 | [key-claim-argument.md](styles/key-claim-argument.md) |

逐步建模不限于背包、最短路等标准模型，也包括自定义状态、等价转化和支撑表示的关键性质。使用最短路不自动意味着逐步建模，自创 DP 状态也不排除逐步建模。

多种风格都适合时，优先解决最先阻碍理解的地方：不知道为何定义这些状态或转化对象，就先建模；已理解表示与做法，但怀疑某个关键命题，就围绕该结论论证；单步已易懂，困难在整体配合，就先给骨架。用户已指定时仍遵守用户选择。

证明的长短和“是否需要证明”不能决定风格。例如“只保留这些 DP 状态不会漏解”：读者尚不知道状态为何这样设计时，论证服务于逐步建模；读者已理解状态和转移，主要怀疑删去其他状态是否安全时，采用关键结论论证。不能把所有推导都归入逐步建模，也不能把所有贪心都归入关键结论论证。

允许局部借用另一种讲法，不因此加载另一份完整 prompt。例如模型建立后可编号概括执行步骤；骨架中的一个步骤也可局部解释状态来源。只有一个判据或一行结论时不硬凑步骤，按理解障碍选择：难在结论为何成立时采用关键结论论证；用户指定其他风格时可用段落概括，不强行改选。

在 `02` 的 `文章结构判定` 中，对每个独立解法记录：对应代码或推导材料、主风格、用户指定或自动选择、一句具体依据。示例：“解法一｜main.cpp、main.py｜逐步建模｜自动｜读者首先需要理解区间选择如何转成图上的路径。”纯写作任务缺代码时明确写“依据已核验推导，尚无实现”。局部结合只在影响组织时补一句，不另造记录文件。

### 新增风格的门槛

目前维护上述三种风格。反例、样例推演和图解是可供各风格使用的讲解手段；暴力到正解、多解对比由文章布局负责，不另立同级风格。以后遇到三种都讲得别扭的真实题目，先判断能否局部调整；只有确实需要改变整段讲解的组织顺序时，才考虑新增 prompt，不因增加一种表达技巧就扩充分类。

## 消费规划与确定布局

候选算法、递进判定、取舍和状态记录以 [`planner`](../oj-solution-planner/SKILL.md) 及其 [`handoff.md`](../oj-solution-planner/references/handoff.md) 为准。本 skill 将规划建议转成正式文章结构，不再维护另一套算法探索规则。

读取 `02` 至 `05` 的实际内容，核对选中方案是否具备适用约束、可执行算法、关键证明、复杂度与代码对应。文件存在或脚本通过不能代替这些内容。完整题解任务尚无实现时，交回协调者安排必要实现；仅写文章且可靠推导足够时，可继续写作并如实记录缺口。关键结论未成立时不能称作正解。

按真实关系选择四种布局之一，章节骨架见 [`layouts.md`](../oj-problem-format-spec/references/layouts.md)：

- 子任务递进型呈现有依据的推进主线；存在特例分支时标明其依赖关系，不强行串联。
- 并列多解法型呈现独立完整解法及取舍。
- 暴力到正解型突出朴素方法与被消除的瓶颈。
- 直接正解型省去没有独立教学价值的重复层。

在 `02` 的 `文章结构判定` 中确认最终选择，记录与规划建议不同的取舍。选中布局必须与算法关系一致；算法、文件、语言和子任务数量不能相互代替。正文布局和表格规范集中维护在格式 skill。

### 总览与正文

选定 **子任务递进型** 或 **并列多解法型** 时，在正文 `## 解法路线` / `## 解法总览` 下、各解法展开前放一张总览表。具体列和写法统一见 [`layouts.md`](../oj-problem-format-spec/references/layouts.md#总览表)，不要把两种关系都写成“突破上一层瓶颈”。后一个解法只是前一个的另一种记账方式时，按 `layouts.md` 的“记账方式例外”合成一节，不强制总览表。

- 递进型解释复用了什么、推进了什么；同阶复杂度也可以因取消值域或结构限制而形成有效递进。
- 并列型解释核心观察、适用场景和实现取舍，不虚构先后优化关系。
- 区分“本节针对的子任务”和“算法实际适用范围”。测试点编号只在来源明确时补充；复杂度分析支持的范围与实际测试结果分别记录。

完整题解正文必须有 `[[TOC]]`、`## 形式化题目`、所选布局和 `## 总结`；每个正式解法拥有自己的 `### 思路`、`### 代码`、`### 复杂度`（递进层可用 `### 复杂度与瓶颈`）。正式主解在对应代码小节使用 `@include-code(./main.<ext>, <lang>)`。完整布局骨架见 [`oj-problem-format-spec/references/layouts.md`](../oj-problem-format-spec/references/layouts.md)。

## 场景路由

只读取当前任务需要的专项资料：

| 场景 | 读取 | 关键产物 |
| --- | --- | --- |
| 完整任务尚未进入写作阶段 | [`oj-problem-workflow`](../oj-problem-workflow/SKILL.md) | 一次性交接，由其协调后续阶段 |
| 组织正文、重写思路或安排证明 | [`reader-and-explanation.md`](references/reader-and-explanation.md) | 读者基础、简洁句段、标点、证明按需展开与充要条件的分方向证明；风格要求按上节加载 |
| 所有题解的写作阶段 | [`process-documents.md`](references/process-documents.md) | 过程文档与最终草稿 |
| 需要解释正式暴力层 | [`brute-force.md`](references/brute-force.md) | 基线的教学用途与瓶颈说明 |
| 正文需要说明验证依据 | [`verification.md`](references/verification.md) | 核对验证记录；运行请求交回验证阶段 |
| DP、图、树、网格、搜索、复杂模拟图示 | [`visualization.md`](references/visualization.md) | `viz_render.py`、图表或 `final-visualization.md` |
| 用户目标是 Haskell/Rust/Python 等语言或语法学习 | [`language-learning.md`](references/language-learning.md) | 语言教学文章，不强制暴力 |

格式细节必须读取 `../oj-problem-format-spec/references/frontmatter.md` 和 `layouts.md`；用户明确要求修正旧文章时，额外读取 `migration.md`。旧文章默认不迁移、不批量改写，旧文内容审查交给 `oj-problem-analysis-reviewer`。

## 过程文档与正文要求

`problem-analysis-workspace/` 不存在时创建；核心信息必须记录题意、关键观察/模型、布局判定、解法推导、正确性和边界、复杂度及实现对应关系。复杂题可拆分为专项文件，简单直解题可合并记录；`duipai-report.md`、`final-visualization.md` 和 `viz_render.py` 只在实际使用时生成。具体章节和草稿约束见 `process-documents.md`。

`## 形式化题目` 去除故事背景，只保留数学结构：用树、点、边、权值、颜色、路径点集这类抽象对象，不搬题面的城镇 / 宗教 / 评级等故事词（题面词汇只留一句桥接说明）；有真实操作序列时每条写成“中文动作 + 形式化式子”两层，只有一次性选择加一个目标时写清对象、可选范围与目标即可（见 `layouts.md`）。正文简洁但要解释“为什么这样想到”，不能把过程文档原样倾倒进文章，也不能在 Markdown 中粘贴完整代码。

## 写作完成与交付

完成后读取 [写作完成核对](references/writing-completion.md)，核对正文、代码引用、资源、元数据和验证证据；按任务范围执行文章检查。写作完成不代表整题测试或最终审查已通过。

不编造题目标题、来源、约束、接受状态、测试结果或关系；不覆盖用户过程笔记，不把 `brute.cpp` 伪装成正解，不为语言学习或纯直解题强行制造暴力层。简短报告正文与草稿路径、布局、各解法主风格及选择依据、引用资源、元数据变更和材料缺口。

## 与 C++ 教学代码衔接

读者定位遵循 `AGENTS.md`「代码的读者与可读性」。正文中的状态、下标和转移要能对应 C++ 实现；完整证明留在题解，代码注释保留关键理由。存在真实的暴力优化链时解释瓶颈与改进，不为直解题编造优化过程。Python 保留其独立的语言技巧定位。
