# 写作完成核对

写回正文后读取本文件。按 [共享讲解规范](reader-and-explanation.md) 和每个解法已选的风格 prompt 检查语言、主线、动机、证明与图解；风格选择规则见 [writer 入口](../SKILL.md#讲解风格路由)。不要把一种风格的开头要求套到另一种风格上。

- 检查每个独立解法的首个内容块是否为 `info` admonition，标题是否一句话概括；熟悉全部相关知识的选手只读该框，能否约 30 秒理解关键做法与理由。详见共享规范的“解析开头的精华概括”。
- 检查简洁句段、中文全角标点、语言自然度、关键转折的来由及新增段落的教学用途。
- 本次撰写或重写了总结与体会时，按 [`oj-summary-insights`](../../oj-summary-insights/SKILL.md) 的“完成核对”检查可迁移性及适用边界；不因局部修改其他章节而扩展重写旧总结。
- 检查证明依据、公式的中文解释、充要条件的两个方向，以及容易误判的局部贪心反例。具体标准只在共享规范维护。
- 布局判定已复核且有实质依据；代码数量、语言数量和子任务数量不能代替解法关系分析。选直接正解型时说明为何其他候选不值得独立展开。
- 新写或本次明确重写的正文满足共同结构、所选布局和各解法小节要求；递进型/并列型的总览表与正文、代码、适用约束一致。空模板、空标题、缺实现的占位注释不算完整交付。
- frontmatter 的 `difficulty`、`tags` 已根据题目和代码复核；`description` 必须原样采用 `problem-analysis-workspace/06-distill.md` 里定稿的那一行，不改写、不重写、不润色（它由 workflow 的浓缩阶段产出）。若发现它与正文或代码不符，在报告里指出并交回协调者重跑浓缩，不自行修正。关系字段只评估是否需要交给 `oj-problem-relation-writer`，不凭记忆编造外部链接。
- 根据规划决定是否独立展示暴力；只有存在、可靠且在任务范围内的基线才引用。跳过重复暴力层时说明教学取舍和实际验证方式，不为填文章骨架新增算法。
- DP 正文在对应思路中有小规模 DP/状态转移表；图论定理与关键结构结论有对应图解，其他非平凡图示按 `visualization.md` 评估。图解支持当前推理，不以配图数量作为质量指标。
- 正确性、边界、复杂度和代码实现互相一致；未运行对拍或样例时如实记录，不声称通过。
- 运行 `timeout 120 python3 scripts/problem-analysis-tools/check_problem.py <题目目录>` 及适用文章检查，确认主解文件存在、引用路径正确、无占位内容和虚构题面信息。现有检查器会跳过未识别的 `legacy` 布局，也未完整检查总览表和过程记录；脚本通过后仍要逐项核对上述结构与内容要求，不能把 `legacy` 当作本次新写或重写文章的豁免。
- `problem-analysis-workspace/` 保持本地忽略。本地交付核对过程记录；共享 CI 或干净检出环境的发布检查只依赖已提交的正文和代码，不要求被忽略的工作区存在。

仅写思路或局部正文且没有实现时，只检查本次范围；报告代码与验证缺口，不将其声称为完整题解交付。完整题解的代码引用与验证要求不变。
