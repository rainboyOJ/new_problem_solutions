# 读者与讲解规范

本文件是 writer 与 reviewer 共用的内容标准. writer 在组织正文前读取, reviewer 在评价正文前读取. 两者使用同一份规则. 章节、元数据和渲染语法仍由格式与 Markdown skill 负责.

## 读者与目标

默认读者已经学会相关基础算法, 但不会从本题条件出发找到解法. 文章要让他**复现思路的发现过程**, 并且易读、易懂、阅读负担低. 用户明确指定其他基础或学习目标时, 以用户要求为准.

把篇幅用在本题的观察、选择和建模上. 可以简短提醒必要的算法性质, 不重讲整套 DFS、背包或最短路教程. 与当前难点无关的语法细节不展开. 算法正确、代码齐全, 不代表文章已经达到教学目标.

## 语气、句子与段落

默认用简洁陈述式. 用熟悉的词讲具体动作, 可以用"我们", 但不闲聊. 少用"先别急"、"想一想"等语气词. 问题确实有助于指出当前困难时可以提问, 不把推导机械改成问答.

**按逻辑拆句, 不设字数上限.** 一句只承载一个主要判断或动作. 必要的短条件句可以保留. 出现连续嵌套的条件、多个因果转折或多次指代回跳时, 拆成几个完整句子. 拆句后保留必要前提和理由, 不靠删逻辑来求短.

下面这句把条件、性质和结论串在一起, 可以拆开:

```text
因为数组有序, 所以当中间元素小于目标值时, 它左边的元素也都小于目标值, 因此可以排除左半段.
```

改成:

```text
中间元素比目标值小. 数组有序, 它左边的元素也都更小. 所以可以排除左半段.
```

同一个关键点组成一个短段落. 换观察、操作或证明目标时再分段. 不规定每段句数, 不机械地一句一段, 也不把普通讲解全部拆成列表.

优先用具体数据和操作解释. 比喻确实降低理解难度时才用, 不为已掌握基础算法的读者重讲"小朋友法". 历史文章中的逗号长句、重复措辞、笔误和未完成草稿不作为模仿目标.

不用"显然"、"自然想到"、"不难发现"替代关键理由. 不以"很简单"、"只需套模板"评价读者的困难. 不堆叠"本质"、"核心"、"优雅"等评价词, 直接说哪个条件允许了哪个动作.

**语言去模板化与自然表达（引用 `humanizer-zh`）:**
正文撰写与润色遵循本仓库的 `humanizer-zh` skill（见 `.agents/skills/humanizer-zh/`）：
- **拒绝起跑式报幕句（§4）**：不写“三者的关系值得先交代清楚”、“四项需求凑齐了”、“接下来让我们深入分析”等舞台报幕腔，直接陈述技术事实与逻辑联系。
- **拒绝翻译腔与生造词（§10、§12）**：用最地道平实的中文算法词汇，不生造“设计重量”、“原语”等生硬大词，直接说“实现代价”、“核心难点”、“支持两种基础操作”。
- **拒绝假对比与虚假深度（§1、§3）**：不玩文字游戏，不写脱离事实的修饰。
- **杜绝散装切片复读（§7）**：拆句服务于理解，不把连贯分析硬切成散碎独白；避免出现连续以同主语开头的短散段，善用自然衔接或有序列表。
- **严格保留算法事实（最高优先级）**：去模板化与润色只优化语言自然度，严禁删改、弱化或篡改任何数学证明、复杂度、边界与算法确定性。

## 标点与排版规范

新写或改写的正文、标题、图注和表格说明中的自然语言，**统一使用中文全角标点**。这是硬规则，不是建议。杜绝机械使用英文半角句读（如英文逗号 `,`、半角句号 `.`、半角冒号 `:`、直引号 `"` 等机器生成痕迹）。局部修改只处理本次范围，不因此批量迁移旧文章。

中文常用标点规范：
- 句读与符号统一使用：逗号 `，`、句号 `。`、冒号 `：`、分号 `；`、叹号 `！`、问号 `？`。
- 引号使用全角中文双引号 `“` `”` 与单引号 `‘` `’`，严禁在正文中使用西文直引号 `"` `'`。
- 括号在纯中文上下文中使用全角括号 `（` `）`；若括号内包含大量公式、代码或纯英文时，允许使用半角括号 `(` `)`。
- 保留中文专用标点顿号 `、`、书名号 `《》`、破折号 `——`、省略号 `……`。

中西文混排与排版规则：
- 全角标点自带合适字距，中文标点与中文字符之间不加半角空格。
- 中文文字与英文单词、数学公式 `$ ... $` 之间，建议留一个半角空格以提高可读性；中文全角标点与相邻的公式/英文之间无需加空格。
- **技术区域严格保护**：行内代码 `` `...` ``、代码块、LaTeX 公式 `$ ... $` 内部、YAML frontmatter、Markdown 语法标签、URL、文件路径及参数等，严格保持其原始代码/西文语法与半角符号，不做无差别替换。

正例：

```text
检查边界、复杂度和具体实现。这部分可以参考《算法导论》。
记住计算结果（避免重复计算），下次查询时直接取出。
这里的“已处理”指本轮已经更新过的有效状态。
若 $A_i \geqslant 0$，则前缀和关于右端点单调不减；若存在负数，该性质不成立。
```

## 组织讲解的两条路线

"复现发现过程"是共同目标. 根据真正的难点选择讲解路线, 必要时局部结合. 讲解路线不替代格式 skill 的四种正文布局.

| 路线 | 适用情况 | 讲解重点 |
| --- | --- | --- |
| 逐步建模 | 难点是把题目转成背包、最短路等通用模型 | 从条件和直接做法的困难出发. 解释哪个观察提示了模型, 再对应状态、点边或决策. 核对转换前后的合法性与目标. |
| 骨架展开 | 没有贴切的通用模型, 或先看全貌更容易理解一串操作 | 先用几步给出算法骨架. 再补上每个选择的来源、直觉和正确性. 骨架中的术语当场解释. |

两条路线都要交代"为什么想到这一步". 仅验证给出的算法正确, 不算完成发现过程. 先给骨架也不能把未经解释的结论当成读者已知条件.

优先走通一条主线. 其他方案有独立教学价值时才展开, 不按代码文件数堆解法. 朴素做法、失败尝试和特例用于暴露下一步的需要. 不强制每篇从暴力开始, 不虚构灵光一现.

## 控制读者需要同时记住的信息

- **先有需要, 再有定义.** 先指出当前困难, 再引入所需对象. 先解释用途, 再给名称、符号和公式. 不在开头列出后文尚无用途的整套记号.
- **每段推进一个关键点.** 给出理由, 再承接下一步. 同时引入多个对象、转换视角或处理多个分支时拆段. 仅将长段落换行不算降低阅读负担.
- **沿用例子和记号.** 优先用同一个小例子贯穿推导. 图、文字、公式和代码中的名称能对应. 换例子时说明新例子要解决什么问题.
- **公式直接参与推理, 但严禁大批量公式堆叠.**
  - 题解不是纯数学论文, **严禁使用密集的解析几何式坐标化、复杂下标链或多层代数放缩来包装显然的图论/组合性质**.
  - 优先使用**物理直觉与结构性质**（如路径分解、折返次数、极值性质、鸽巢分半、反证法导出结构矛盾）来解释. 能用两句话说清的几何事实，绝不写成 5 行以上繁琐的不等式组.
  - 禁止连续出现多行没有中文解释的纯符号公式推导.
- **关键公式要有中文解释（公式前说符号, 公式后说含义与作用）.**
  任何出现的独立公式都必须服务于读者的理解, 严格遵守：**公式前交代符号物理意义, 公式后用一句大白话解释这个式子在说什么**.
  - **引入新符号的公式**: 公式前一句说清符号在题里是什么 (如「$h(u)$ 就是 $u$ 到直径两端中较近那一端的距离」).
  - **带编号或被后文引用的公式**: 公式后一句说清它在论证里承担什么, 不要只留一个编号让读者自己回头找用途.
  - **承载结论的公式**: 关键不等式、递推式、充要判据之类, 用一句中文说清「这个式子人话是什么意思」, 必要时按边拆开 (如「左边是家放 $C$ 时花的时间, 右边是取直径端点时最多能拿到的值」).

  写法: **公式前说符号, 公式后说作用.** 两边各一句即可, 公式后不重述符号. 每行化简式与读者已能看懂的变形不加解释, 不把同一含义写第二遍.
- **解释一次就够.** 不在直觉框、定理、证明、样例和总结中完整复述同一结论. 关键选择讲清理由, 常识性操作简述即可.

## 直觉与证明的安排

正文先给例子与直觉, 再给推动下一步所需的短理由. 部分证明可以放到后文、折叠块或选读中. 使用结论时说明证明后置, 并给出可定位的入口. 不能用"后面再证"代替真正的证明.

决定正确性的结论必须已经核验. 例子说明现象, 图示帮助理解, 二者不能代替一般论证. 不把未证明的猜想写成确定结论. 已知的标准算法性质可以明确引用, 不必重证整套基础理论.

### 默认采用列表证明流

证明优先使用 Markdown 无序列表, 也可在需要引用步骤编号时使用有序列表. **每项推进一个推理步骤.** 一句话能说明的结论直接写, 不为了格式强行创建列表.

- 列表前说明证明目标、必要前提和符号. 不为简短结论额外建立整套记号.
- 每项给出当前结论, 必要时补一句依据. 公式可以直接参与推理, 不再套一段重复解释.
- 用箭头表示关系. 数学推出用 `\Rightarrow`, 等价用 `\Leftrightarrow`; 文字步骤可用 `->`. 不能把单向推出写成等价, 也不能让一串箭头掩盖中间缺口.
- 前一项的结论可以供后项使用. 不能在列表中悄悄增加假设或更换变量含义.
- 长证明先按证明目标拆成几小段, 每段再用列表展开. 必要性、充分性和边界分别处理, 不用大量嵌套列表制造新的阅读负担.
- 已有简洁的逐行等式可以保留. 列表是默认表达方式, 不是把所有公式强制改成项目符号的理由.

### 充要条件必须分方向证明

证明一个充要条件 (`\iff`、`\Leftrightarrow`、"当且仅当"、"等价于") 时, 必须把两个方向分成两段独立写出, 并在每段标题里用中文写明方向. 不能只证一个方向就用等价符号收尾, 也不能把两个方向揉在同一段里靠读者自己拆.

- 两个方向的含义先交代清楚: 写成 $p \iff q$ 时, 把哪一侧当**目标命题**、哪一侧当**条件**先说定. 按本仓库约定, 充分性指"条件成立就足以断定目标", 必要性指"目标成立时条件必然成立".
- 标签直接写中文方向, 不要只写 `$\Leftarrow$` / `$\Rightarrow$`. 箭头含义取决于哪一侧写在左边, 单看符号读者无法判断指的是哪个方向. 合格写法如 `**充分性（等式成立 $\Rightarrow$ 点在路径上）**`、`**必要性（点在路径上 $\Rightarrow$ 等式成立）**`.
- 只证单向时不必假造成两段, 但必须说明只证了哪个方向、另一个方向为何不需要 (例如只需充分性即可支撑算法正确性), 不能默默留着等价符号让读者以为两边都证了.
- 平凡等价的例外: 确实显然成立的等价可以一句话带过, 但要说明为何显然 (例如由定义直接展开), 不能仅写"显然等价".
- 适用范围只限充要命题. 局部的公式化简变形不要求拆成两段.

下面是一个合格的充要证明骨架:

```text
**引理 X**: $A \iff B$.

*证明*: 把 $A$ 当目标命题, $B$ 当条件, 分两个方向.

**充分性（$B$ 成立 $\Rightarrow$ $A$ 成立）**: ...

**必要性（$A$ 成立 $\Rightarrow$ $B$ 成立）**: ...

两个方向合起来即得等价关系. $\square$
```

下面的 GCD 证明展示一行一步的形式. 设 $a=qb+r$, 其中 $a\geqslant b>0$, $0\leqslant r<b$. 任取正整数 $d$, 证明两组数的公因数相同.

- $d\mid a$ 且 $d\mid b$ $\Rightarrow d\mid(a-qb)$, 所以 $d\mid r$.
- $d\mid b$ 且 $d\mid r$ $\Rightarrow d\mid(qb+r)$, 所以 $d\mid a$.
- 两组数的公因数相同 $\Rightarrow$ 最大公约数相同.
- 因此 $\gcd(a,b)=\gcd(b,r)$.

前两项分别证明两个方向, 后两项收束结论. 不必再定义公因数集合或加上"合取引入"等标签. 简短来自省去重复包装, 不是省掉证明依据.

以下形式仍有问题:

- 把原来的长证明段落整段放进一个列表项.
- 只写"条件成立 -> 贪心正确 -> 得到答案", 没有说明关键选择为什么安全.
- 只证明一个方向, 就宣布两个条件等价.
- 充要命题只写 `**充分性（$\Leftarrow$）**` 这类裸符号标签, 让读者自己回忆箭头指向哪一侧.
- 把充分性与必要性两个方向合并成一段叙述, 只在段末补一句"反之同理".

例如, "核心连通, 所以自然想到逐轮剥叶"仍然跳过了删除顺序为何最优. 应先解释某个点不选会造成什么距离问题, 再说明这个条件如何引出剥叶. 增加项目符号不能补上这段推理.

## 图论结论的图解

正文讲解的图论定理, 以及决定解法的路径、连通性、割、树结构等关键结论, **必须有对应图解**, 使用 SVG、Mermaid 或 Graphviz. 只调用已知的标准图算法、不展开其定理时, 不要求重画整套教程.

图要展示关键结构, 如被删点分开的两侧、必须经过的路径、交换前后的边. 只画完整样例树而不对应结论, 不算完成图解.

图前说明看什么, 图后指出支持推理的路径或关系. 颜色、标记和长度要有明确含义. 列表证明中的多个步骤可以复用同图, 用标记对应各步. **不强制每个证明段落各生成一张图.** 素材制作与规模控制见 [visualization.md](visualization.md).

## writer 与 reviewer 的共同核对

沿正文主线检查关键转折: 当前困难是什么, 为什么选择这一步, 它解决了什么. 若读者必须反复回翻记号或连续阅读长证明才能接上, 先重排依赖, 不一律靠加长文章解决.

- 标点和排版按本文件规范检查（中文全角标点），技术语法与原文引用除外。
- 语言自然度与去模板化按 `humanizer-zh` 规范核对，重点排查报幕腔、翻译生造词与散装碎片句。
- 长难句指出具体的条件嵌套、因果链或指代负担, 给出保留原意的拆法. 不设字数阈值, 不因长公式或段落较长直接判错.
- 证明列表检查每步的依据、前提和结论. 项目符号、箭头或公式数量不是证明质量的依据.
- 简洁陈述和短段落服务于理解. 不机械删掉必要理由, 不强制所有句子独立成段或改成列表.

本规范依据用户对 `newRbook_ejs` 文章的风格确认整理. KMP 与二分文章提供了具体例子推动推导的样本, GCD 文章提供了逐行证明的样本. 用户确认将证明流优先写成列表, 并将极简句式作为强化目标. 历史文章的混合标点和长句不作为规则例外.
