# 逐步建模

仅在路由选择“逐步建模”后读取。通用语言、证明、公式与图示标准见 [共享讲解规范](../references/reader-and-explanation.md)；章节布局由格式 skill 管理。本 prompt 组织一个独立解法的讲解，不改变已核验算法。

## 写作任务

让读者从题目条件出发，理解为什么需要新的表示、状态或转化，并能自己走到代码中的做法。这里的模型既可以是标准算法模型，也可以是自定义状态、等价关系或支撑转化的结构性质。

## 展开方式

先按共享规范的“解析开头的精华概括”写 `info` 提示框。下面的逐步推导位于概括之后，沿概念依赖推进，不把各项机械变成固定标题：

1. 从当前对象与目标出发，指出直接处理时的具体困难。必要时用一个小例子暴露困难，不为形式强造暴力层。
2. 找出题目中允许推进的条件，说明它怎样导出关键观察。先让读者看见需要表示或保留什么，再引入对应对象和名称。
3. 建立题目与新表示的对应。例如状态保留哪些信息、点边分别表示什么、等价转化前后哪些选择仍合法。解释为什么这些信息足够，以及目标如何保留。
4. 从已建立的表示推出算法。状态有了再讲转移，点边有了再说明图算法为何适用；模型成立后可以编号概括执行步骤。
5. 在对应转折处给出必要短理由，较长证明按共享规范安排。最后接上实现中的关键变量、边界和复杂度。

概括之后的推导从“当前困难与下一步需要”开始，不再用陌生状态或最终结论把整套算法报一遍。公式和术语在需要时出现，可用同一个小例子贯穿观察与转化。上述推进已经足够简短时直接写成连贯段落，不另加重复的总览。

## 自查

- 每次引入表示、状态或转化之前，是否已经说明需要解决什么问题？
- 观察是否来自题目条件，还是仅因已知代码用了某算法而倒贴标签？
- 合法性、目标保持与状态信息充分性是否有依据？涉及充要命题时按共享规范分方向证明。
- 读者能否沿前文推出做法，而不必先接受尚未解释的结论？

缺少关键论证时报告材料缺口，不用补写一段“自然想到”掩盖，也不自行更换算法。
