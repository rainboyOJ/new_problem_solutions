# 关键结论论证

仅在路由选择“关键结论论证”后读取。通用语言、证明、公式与图示标准见 [共享讲解规范](../references/reader-and-explanation.md)；章节布局由格式 skill 管理。本 prompt 组织一个独立解法的讲解，不改变已核验算法。

## 写作任务

读者已经理解做法和涉及的对象，但不相信支撑算法的关键结论成立。围绕这个命题组织讲解，让他看懂结论从何而来、为什么可靠，以及它如何允许代码中的操作。证明长度、算法标签或“存在正确性证明”都不是选择本风格的理由。

## 展开方式

先按共享规范的“解析开头的精华概括”写 `info` 提示框：标题一句话概括，内容让熟悉相关知识的选手约 30 秒读懂做法和关键理由。其后按“关键结论 → 直觉 → 论证 → 算法落地”展开，概括已说清的内容直接承接，不再复述一遍。以下是推理顺序，不要求固定四个小节。

1. **明确关键结论。** 给出准确命题，交代适用条件、涉及对象及它解决的疑问。例如需要说明某次交换保持可行且目标不变差，不能仅写“按此顺序贪心最优”。只引入读懂当前命题必需的符号。
2. **解释直觉来源。** 从题目条件、一个小例子或结构关系出发，解释为什么值得比较这些对象、进行这种交换或保留这些状态。让读者知道证明的切入点从哪里来，不只公布结论后机械验算；例子支持理解，不冒充一般证明。
3. **完成关键论证。** 明确比较对象和需要保持的条件，按依赖推进。交换论证要解释可行性、目标变化，以及局部交换如何导向所需的全局结构；其他论证也要补齐局部结论到算法保证的连接。按实际命题采用合适证明，不强制所有题使用交换法。充要结论、边界与公式解释遵守共享规范。
4. **落实算法。** 说明已证结论具体允许怎样排序、删除、合并、选择或判定，再对应实现的关键操作。代码中的平局、边界和复杂度按需交代；不能在“证毕”处结束，让读者自行补出算法。

论证本身是这条路线的主线，不把关键证明全部塞进选读。无关技术细节可以后置，简单结论也可以几句话讲完，不为凑结构扩写。需要一个局部模型或几步操作时就地解释，不因此加载其他风格的完整 prompt。

## 自查

- 关键命题是否明确，有无隐藏前提或把单向推出说成等价？
- 是否解释了结论与证明切入点为何值得考虑，而不只是声称算法正确？
- 直觉是否有一般论证支撑，局部性质是否足以推出算法所需的全局保证？
- 证明之后是否接上实际操作，正文与已有代码的判据、顺序和边界是否一致？
- 如果真正卡点是“状态为什么这样定义”，是否应按入口规则优先逐步建模，而不是因为证明较长就选择本风格？用户明确指定时仍尊重指定。

关键结论尚未核验时报告材料缺口，不能由 writer 补造证明、弱化命题或悄悄换算法。
