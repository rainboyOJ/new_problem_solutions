# 骨架展开

仅在路由选择“骨架展开”后读取。通用语言、证明、公式与图示标准见 [共享讲解规范](../references/reader-and-explanation.md)；章节布局由格式 skill 管理。本 prompt 组织一个独立解法的讲解，不改变已核验算法。

## 写作任务

先让读者看清各个操作如何配合，再解释每个关键选择的来源、直觉与正确性。骨架描述算法的概念步骤，不照抄函数顺序或逐行翻译代码。

## 展开方式

先按共享规范的“解析开头的精华概括”写 `info` 提示框。其后用“一句当前困难 → 编号步骤 → 一句成立理由”组织操作主线；概括已交代的困难和理由直接承接，不再重复写一遍：

- 编号列出 2～6 个可执行动作，每项一句，只写做什么。不给“想清楚 X”“证明正确性”这类空步，也不把证明塞进编号。
- 主线中的术语当场简短解释；若一步依赖尚未交代的表示，就在这里补足必要含义，后文再解释它的来源。
- 成立理由指出支撑算法的关键性质，不能只说“这样即可得到答案”。需要后置证明时给出可定位入口。

沿骨架顺序展开真正的卡点：为什么选这个动作、利用了哪个条件、给下一步提供什么，以及为什么不漏解或不破坏答案。常识性操作可以略过，不强制每个步骤各占一节。某一步确需局部建模时解释它的状态来源即可，不为此加载另一份风格 prompt。

主线采用共享规范的简短起点预算，必要依据不受机械句数限制。后置讲稿或速览附录尽量与编号同序，且不重复完整论证。

## 没有可排序步骤时

解法本质是一个判据、等价变形或一行结论时，用段落概括主线，不硬凑编号。在 `02` 的风格记录中说明拆不出步骤的原因；仍要解释结论的来源及必要理由。

## 自查

- 只读骨架能否理解算法实际做什么、步骤之间怎样衔接？
- 编号是否都是可执行动作，是否夹带未经解释的概念或空泛任务？
- 展开部分是否补齐关键选择的动机，而非仅证明一个已经公布的算法正确？
- 每段是否解决具体障碍，是否把同一骨架重新复述了一遍？
