# 正文布局与嵌入

## 共同结构

frontmatter 后固定写：

```markdown
[[TOC]]

## 形式化题目

<!-- 由题目解析 skill 填写 -->

<!-- 这里放一种正文布局 -->

## 总结
```

`## 形式化题目` 去掉故事背景，直接描述给定对象、约束关系和要求；不写输入输出格式或数据范围。正文不使用一级标题。非平凡题目可以在 `## 总结` 后追加 `## 图示解析`，具体图示由可视化 skill 决定。

这一节有三条硬规则：

- **用抽象对象，不用故事词。** 用树、图、点、边、权值、颜色、路径上的点集、序列下标这类数学对象；题面里的「城镇」「宗教」「金价」「评级」「信徒」「国王」等叙事词不搬进来，换成对应的抽象说法（城镇 → 点，道路 → 边，宗教 → 颜色，评级 / 金价 → 权值）。
- **题面词汇只做一次桥接。** 正文其他小节沿用题面称呼时，在这里用一句短注说明对应关系，例如：原题把颜色称为「宗教」、把权值称为「评级」，下文遇到时按这两个叫法理解，指的是同一组属性。桥接句只写一次，不在后面反复交代。
- **每条操作 / 约束写成「中文动作 + 形式化式子」两层。** 先一句中文说清这一步在做什么，再用 `$...$` 把目标精确化。只有式子，读者要自己翻译一遍；只有中文，目标的精确定义又可能含糊。

合格写法（操作列表）：

````text
1. `CC x c`：把点 $x$ 的颜色改成 $c$，即 $c_x \leftarrow c$；
2. `CW x w`：把点 $x$ 的权值改成 $w$，即 $w_x \leftarrow w$；
3. `QS x y`：在路径 $x \to y$ 上，把所有颜色等于 $c_x$ 的点的权值相加并输出，即求 $\sum_{v \in P(x, y),\ c_v = c_x} w_v$；
4. `QM x y`：在路径 $x \to y$ 上，取所有颜色等于 $c_x$ 的点的权值最大值并输出，即求 $\max\{\, w_v \mid v \in P(x, y),\ c_v = c_x \,\}$。
````

两种不合格的极端：只写 `CC x c`：令 $c_x \leftarrow c$（读者得自己把式子翻译成动作）；把题面描述整段搬进来（等于没有形式化）。

## 四种布局

直接正解型：没有独立教学层，直接方法就是最终方法。

```markdown
## 正解

### 思路

### 代码

@include-code(./main.cpp, cpp)

### 复杂度
```

暴力到正解型：朴素方法能暴露最终优化所消除的瓶颈。

```markdown
## 暴力解法

### 思路

### 代码

@include-code(./brute.cpp, cpp)

### 复杂度

### 瓶颈

## 正解

### 思路

### 代码

@include-code(./main.cpp, cpp)

### 复杂度
```

并列多解法型：至少两个独立且值得教学的完整解法，是替代关系而非连续优化。

```markdown
## 解法总览

说明各解法差异，并指出正式主解及其 `main.<ext>`。
紧接着放并列解法总览表（必须，见下）。

## 解法一：...
### 思路
### 代码
### 复杂度

## 解法二：...
### 思路
### 代码
### 复杂度

## 复杂度对比
```

子任务递进型：题面中的真实约束或子任务形成层层推进，主线各层复用前一层观察，并消除性能瓶颈或取消限制性假设；复杂度不要求严格下降。存在互不包含的子任务时，标为特例分支并说明与主线的关系，不按测试点顺序强行串联。

```markdown
## 解法路线

说明每层真实约束、上一层瓶颈或限制性假设、复用观察，并指出正式主解。
紧接着放分层表（必须，见下）。

## 暴力解法
### 适用范围
### 思路
### 代码
### 复杂度与瓶颈

## 子任务解法：实际约束
### 适用范围
### 思路
### 代码
### 复杂度与瓶颈

## 正解
### 关键观察
### 思路
### 代码
### 复杂度
```

### 总览表

递进型与并列多解法型必须在 `## 解法路线` / `## 解法总览` 下放总览表，位于各解法展开之前。表前说明比较目的，表后解释关键关系；两种布局使用不同的列。

递进型表头：

```markdown
| 层次 | 适用约束 | 做法 | 复杂度 | 相对前层的推进 |
| --- | --- | --- | --- | --- |
```

- **适用约束**写算法实际成立且复杂度允许的范围；可另加“对应子任务”列，注明题面中已核实的测试点编号。不要把本节针对的测试点写成算法全部覆盖范围，也不要虚构分数。
- **做法**写到能对上代码，不写“优化一下”“二分”这类只有标签没有动作的词；需要时另加代码列。
- **复杂度**写该层自己的时间复杂度，空间是瓶颈时也列出，定义值域等额外参数。同阶复杂度也可以通过取消限制性假设形成有效递进。
- **相对前层的推进**说明复用了什么观察，如何消除性能瓶颈或取消限制性假设；起点可标为“基线”。不能只写“范围更大”而不给出使算法仍然成立的原因。

表后点明关键思维跳跃与实现优化。例如两层都是 $O(n\log n)$，后一层通过改变存储方式支持更宽值域，仍可构成递进；应解释具体变化，不能仅凭复杂度相同就删除该层。

并列型表头：

```markdown
| 解法 | 核心观察 | 复杂度 | 适用场景 | 对应代码 |
| --- | --- | --- | --- | --- |
```

各行是独立完整解法；“适用场景”说明实现取舍或扩展需求，不虚构前后优化关系。表后说明如何选择及哪一个是正式主解。“对应代码”列写实际文件；同一算法的多语言实现归在同一行，跨语言但算法不同的实现分行。

布局选择优先级：子任务递进型、并列多解法型、暴力到正解型、直接正解型。先由 [`oj-solution-planner`](../../oj-solution-planner/SKILL.md) 提供候选解法和布局建议，再由 writer 依据核实的解法关系确定正文结构，验证后复核。子任务数、文件数和语言数均不能直接决定布局或层数；同一算法覆盖多档子任务时可以合并。不按模糊的“简单/困难”决定；标题不要编造“60 分/80 分”，使用实际约束。

每个正式解法都拥有自己的 `### 思路`、`### 代码`、`### 复杂度`（递进层可用 `### 复杂度与瓶颈`）。如果解法共享代码，必须在该解法的 `### 代码` 明确写“同解法一/见上文/不单独给出”及原因。正式主解至少出现一次 `@include-code(./main.<ext>, <lang>)`，普通 C++ 为 `@include-code(./main.cpp, cpp)`；暴力代码只能放在暴力层自己的 `### 代码`。

### 文件命名约定（不需要每次重新判断）

| 文件 | 用途 |
| --- | --- |
| `main.<ext>` | **正式主解**，题解推荐提交的那一份，必须被 `@include-code` 引用 |
| `main2.<ext>`、`main3.<ext>` | 与主解并列的其他完整解法，按正文解法顺序编号 |
| `brute.<ext>` | 小数据暴力，只用于对拍与讲解基线 |
| `gen.<ext>` | 对拍数据生成器，无输入、stdout 即数据 |

- 多解法题把**推荐提交**的那份定为 `main.<ext>`，即使它在正文里排在后面。旧主解降级为对照解法时改名为 `main2.<ext>`，不要占用 `main.<ext>` 后又把它当非主解讲。
- 同一算法的多语言实现共用同一个解法章节：`main.cpp` 与 `main.py` 并列为正式主解；对照解法的其它语言写 `main2.py` 等。
- 改名时同步修正文件头注释里写的文件名与 `@include-code` 路径，不要留下 “`// main.cpp：…`” 却放在 `main2.cpp` 里的情况。

## Markdown 细节

- 代码引用路径相对当前 Markdown 文件；不要在正文粘贴完整源代码。
- 草稿或仅搭建骨架时，缺少代码文件可保留 `### 代码`，用 `<!-- 缺少对应代码文件 -->` 占位；不要使用可见 TODO。完整题解交付时补齐代码或说明合理的复用/省略依据，不能把占位注释当作已完成。
- 行内公式使用 `$...$`，展示公式使用 `$$...$$`；不等式写 `\leqslant`、`\geqslant`，不要混用 `<=` 或 `>=`。

## 可视化辅助格式

允许的形式：Markdown 表格（DP、背包、网格、样例推演）、Mermaid（流程/状态/简单树）、ASCII 文本图（小型流程和递归分支）、Graphviz dot（图、DAG、拓扑关系）、`tree_draw.py` 生成的 SVG（树、二叉树、线段树）以及确有必要的图片。具体渲染扩展以 `rbook-markdown` 为准，题目专用素材由 `oj-sample-visualizer` 生成。

放置规则：样例图放在 `## 形式化题目` 的样例附近；算法本质图放在对应解法的 `### 思路` 或 `### 关键观察`；非平凡题目的总路线图放在 `## 总结` 后的 `## 图示解析`。除该二级标题外，图示小节使用三级标题，不添加一级标题。直接输入输出、极短模拟和纯语法学习可以省略，但应在过程记录说明理由。

每个图或表必须有教学目标，图前用一句话说明展示内容，图后用 2--5 句说明观察重点；表格解释行、列和单元格含义。Mermaid/Graphviz 节点 ID 尽量使用 ASCII，中文放在 label 或正文。普通题解通常最多 1--2 个可视化块，难题最多 3 个；超过 30 个节点、`10 x 10` DP 表或搜索树 3 层时只展示关键局部，避免装饰性图片。

本地 SVG 用标准相对路径引用，例如 `![线段树结构图](./segment-tree.svg)`；推荐文件名为 `tree.svg`、`binary-tree.svg` 或 `segment-tree.svg`。DP 题的最终文章必须在对应解法思路中有小规模状态/转移表，并在表格前后解释观察内容。
