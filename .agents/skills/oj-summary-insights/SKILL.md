# OJ 总结与体会

把一道题中值得带走的思考方法写成可迁移的经验。读者读完应知道：以后遇到什么结构，可以尝试怎样思考，以及为什么值得尝试。

## 范围与材料

- 由 writer 调用时，消费已核验的解法与正文，只提供总结部分，不重新启动整题流程。
- 单独调用时，阅读用户指定的题解、推导和必要的实现，确认经验的事实依据。材料不足时说明缺口，不为写体会发明性质或新算法。
- 用户只要求建议或草稿时直接返回文字；要求写入文件时仅修改指定部分。保留有价值的原文，不自动重写全文、修改代码、维护元数据或推荐其他题。
- 本 skill 负责总结的内容质量；写入 rbook 正文时沿用调用方已加载的格式与 Markdown 规范。单独修改 rbook 正文时读取 `rbook-markdown`，不另造章节体系。

## 提炼方法

先找解法中真正改变思路的一步：原先受什么阻碍，改换了什么表示、枚举方向、信息组织方式或证明目标，为什么这一步消除了阻碍。再去掉题目背景、专有变量和数值限制，保留决定这一步有效的结构条件。

优先选最有迁移价值的一条；确有独立启发时再增加，不按算法或实现数量逐项凑体会。几种实现共享同一个思想时，提炼共同原因。

每条经验应让读者理解以下关系，但不强制分成四个标题或四句话：

- **识别信号**：什么目标、关系或瓶颈出现时，可以考虑这一方法。用可识别的结构描述，避免“遇到难题时”这样的空话。
- **思维动作**：具体改变什么，例如把逐对象更新改为按共同特征汇总，或把验证结果改为反推必要条件。不能只写“逆向思维”“对偶”“降维”等标签。
- **有效原因**：哪种共享、等价、单调性或不变式使转换成立，省掉了什么重复工作，或缩小了什么需要考虑的范围。
- **适用边界**：保留真正影响正确性与代价的前提。尚未证明的推广写为“可优先尝试”“先检查是否满足”，不把本题的成功写成普遍保证。

抽象的是思考方法，不必推广本题的完整算法。通用经验可以不提具体数据结构；某种结构确为方法生效的必要条件时，应明确保留。复杂度结论必须有相应条件支持，不能把本题的数值或界直接推广。

## 写法与例子

用一段紧凑的中文说明“遇到……，可以先……，因为……；前提是……”。这是组织思路的提示，不是每条照填的句式模板。方法直接面向一般问题，本题最多补一句作为来源或例证，不让读者依赖本题记号才能读懂。

只有本题回顾的写法：

> 将逆置换的前缀编码存入哈希集合，再查询每个原排列的最长匹配。

可迁移的写法：

> 对一批各自求最佳匹配的对象，可以先考虑让答案的接收者主动查询，把候选一侧预处理为可检索的信息。这样有机会避免每个候选向大量接收者逐一更新。关键要检查：候选信息能否共享预处理，以及单次查询能否避免遍历全部候选；仅仅交换枚举方向不会自动降低复杂度。

不要把这个例子固化为所有题目的结论。其他题应从自己的关键转折提炼经验。例如，查询代价过高而候选贡献能按组聚合时，批量推送也可能更合适。

正文已讲清本题算法时，总结不再完整复述步骤。现有章节可以保留简短回顾，但体会的主体应是一般性方法，不强制另加一个同义的总结章节。

## 完成核对

- **去题目化**：删掉题号、故事、本题变量与专用名词后，这段话是否仍然成立、仍能指导其他题目？需要保留的结构条件不应随背景一起删掉。
- **可操作**：读者是否知道何时尝试、下一步具体做什么？换成任何题都能照用的口号不算体会。
- **有依据**：经验是否来自实际解法的关键转折，有效原因是否受正文支撑？不从单个成功例子推出“总是最优”。
- **有边界**：是否把有条件的策略写成“只要……就一定……”？是否漏掉会改变结论的查询代价、更新方式或结构限制？
- **不重复**：是否只是把正文算法换词重讲，或仅列数据结构名称？删去重复步骤，留下可迁移的判断。
- **语言克制**：删除对作者或读者的夸赞，以及“黄金法则”“彻底解决所有问题”等无依据的承诺。不为显得抽象而堆砌术语。

若材料只能支持很窄的经验，就如实写清适用范围，不强行升格为普遍法则。只请求总结时交付总结；请求审查时指出具体缺陷并给出改写建议，不扩大任务。
