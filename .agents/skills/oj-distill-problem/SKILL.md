# OJ 题目浓缩

把一道题的核心解法压成一行，让读者一眼看透解法的数学本质、突破瓶颈的关键转折以及落地的极简结构。

这一行是本仓库 `index.md` frontmatter 中 `description` 的正式来源。

## 读取与选解法

- 接受仓库题号、OJ 与题号、题目目录或题解路径，也可以使用当前对话明确指定的题目。先定位真实材料；裸题号有歧义时再询问，不猜测题目。
- 阅读适用的仓库指引、题面与约束、现有题解和对应代码，核实关键观察、统计对象、依赖顺序及适用条件。只读研究，不修改题目文件（被 workflow 阶段 5 调用时例外，只写 `06-distill.md`），不启动整题写作或关系推荐流程。
- 默认浓缩题解中的主解；用户指定某种解法时，只浓缩指定方案。不能把暴力、优化方案或不同正解的技巧拼成一条不存在的解法。
- 正文与代码有冲突时先辨明是否为正在修改的实现。不能把明显错误或尚未核实的方案包装成确定结论。材料不足、目标不明或关键冲突无法消解时，用一句简短说明或问题代替浓缩结果；不为满足格式编造结论。

## 提炼三要素范式（核心规则）

提炼出的每一项必须凝练有力，坚决杜绝流水账式长句，通常由 **2～4 个核心要素** 通过 ` + ` 连接而成：

1. **要素一：核心数学 / 算法模型**（直击题目本质）
   - 指明本题所属的高级数学思想或经典算法模型，使用具体明确的概念名称；
   - 例如：`鸽巢原理（抽屉原理）`、`极值对抗统一模型`、`正难则反`、`回文核极小化归约`、`闭区间记账二分`。
2. **要素二：关键性质推导 / 观察转化 / 下界证明**（突破瓶颈的逻辑枢纽）
   - 概括解法中最具洞察力的思维动作或必要性证明，说明如何把复杂约束化简；
   - 例如：`同战力互斥下界证明`、`后手反应函数代数化`、`3字符集周期为3锁定`、`81种合法前驱反向生成`、`块平均权值贪心`。
3. **要素三：落地数据结构 / 核心计算动作**（代码层面的极简实体）
   - 指明算法在代码实现时最终依托的数据结构或统计方式；
   - 例如：`桶计数`、`5个代表元ST表查询`、`6种全排列前缀和`、`状态频次哈希计数`、`延后代价贡献法`、`树上DFS全局回溯栈`。

### 表述规范

- **短语化优先**：采用名词性短语或紧凑的动宾结构，避免“因为……所以……”、“每轮……迫使……”等冗长的过程性长句；
- **保留关键机制**：算法名可以作为限定词，但不能只写空泛的大标签（严禁写“贪心 + DP + 图论”这类毫无信息量的标签拼凑）；
- **逻辑紧密对称**：按解题逻辑的先后递进次序排列各项，所有项必须严密服务于同一套主解；
- **概念边界准确**：如普通单调队列优化不能写成斜率优化，和哈希不能泛化为普通哈希。

## 输出格式

正常完成时只输出一行纯文本，各项用 ` + `（加号两侧各保留一个空格）连接。

- 格式示例：`鸽巢原理（抽屉原理） + 同战力互斥下界证明 + 桶计数`
- 不加标题、题号前缀、项目符号、代码围栏、加粗或结尾多余说明。
- 不附每项解释、证明、复杂度、代码或推荐题。
- 不输出多个版本让用户挑选。

## 两种调用模式

### 独立调用（用户直接要求浓缩）

按上面“输出格式”节执行：对话里只给那一行，不建文件、不改题目文件、不输出内部检查。

### 被 oj-problem-workflow 阶段 5 调用

除那一行之外，还要把结果写入 `problem-analysis-workspace/06-distill.md`，内容含：

- 浓缩对象：浓缩的是哪个文件、哪套算法（如 `main.cpp` 的主解）；
- 定稿行：那一行纯文本，单独成行；
- 选题依据：每项思维动作分别依据哪段代码或哪条结论；
- 排除项：若有其他解法、暴力或优化方案未被纳入，一句说明为什么。

这个文件是写作阶段 `description` 的唯一来源，也是审查阶段逐字比对的对象。
