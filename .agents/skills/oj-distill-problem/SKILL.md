# OJ 题目浓缩

把一道题的核心解法压成一行，让读者看出几个关键思维怎样组成这套解法。保留具体动作，而不是罗列宽泛的算法标签。

这一行是本仓库 `index.md` frontmatter 中 `description` 的正式来源。

## 读取与选解法

- 接受仓库题号、OJ 与题号、题目目录或题解路径，也可以使用当前对话明确指定的题目。先定位真实材料；裸题号有歧义时再询问，不猜测题目。
- 阅读适用的仓库指引、题面与约束、现有题解和对应代码，核实关键观察、统计对象、依赖顺序及适用条件。只读研究，不修改题目文件（被 workflow 阶段 5 调用时例外，只写 `06-distill.md`），不启动整题写作或关系推荐流程。
- 默认浓缩题解中的主解；用户指定某种解法时，只浓缩指定方案。不能把暴力、优化方案或不同正解的技巧拼成一条不存在的解法。
- 正文与代码有冲突时先辨明是否为正在修改的实现。不能把明显错误或尚未核实的方案包装成确定结论。材料不足、目标不明或关键冲突无法消解时，用一句简短说明或问题代替浓缩结果；不为满足格式编造结论。

## 提炼规则

1. 在内部找出解法的关键观察、模型转化和消除瓶颈的方法，选出有独立作用的思维动作。
2. 每项使用简短的“对象或条件 + 动作”表述，例如“最后出现位置跳过无效过程”“按位置统计贡献”“沿依赖拓扑累加”。具体到能区分本题思维，又不复述完整题意或代码。
3. 通常保留 2～4 项，按实际需要增减。只有一个核心思维就只写一项；不拆同义项、不凑数量、不把读入、排序容器或普通循环等附带实现列成独立思维。
4. 按解法的逻辑关系排列各项。每个加号连接的内容必须属于同一套解法；组合后应保留决定性的转折，不因追求短小而漏掉真正难想到的一步。
5. 算法名可以作为限定词，但不能只写“贪心 + DP + 图论”等泛标签。也不要把普通累加称为前缀和、把使用 last 数组一概称为去重，或把有序扫描说成实际执行了拓扑排序。
6. 保持概念边界准确。例如树上统计经过某点的起点数，与一般 DAG 上累加路径数并不天然等价；浓缩时不能抹掉影响正确性的差别。

## 输出

正常完成时只输出一行纯文本，各项用 ` + ` 连接。

- 不加标题、题号前缀、项目符号、代码围栏、加粗或结尾说明。
- 不附每项解释、证明、复杂度、代码或推荐题。
- 不输出多个版本让用户挑选。

交付前在内部检查：每项都有材料依据，关键动作清楚，没有重复、遗漏决定性转折或混合不同解法。检查过程不输出。

## 两种调用模式

### 独立调用（用户直接要求浓缩）

按上面“输出”节执行：对话里只给那一行，不建文件、不改题目文件、不输出内部检查。

### 被 oj-problem-workflow 阶段 5 调用

除那一行之外，还要把结果写入 `problem-analysis-workspace/06-distill.md`，内容含：

- 浓缩对象：浓缩的是哪个文件、哪套算法（如 `main.cpp` 的主解）；
- 定稿行：那一行纯文本，单独成行；
- 选题依据：每项思维动作分别依据哪段代码或哪条结论；
- 排除项：若有其他解法、暴力或优化方案未被纳入，一句说明为什么。

这个文件是写作阶段 `description` 的唯一来源，也是审查阶段逐字比对的对象。主解在验证后发生变化时必须重跑本阶段，不能沿用旧句。

其余规则（只浓缩主解、不拼接不同解法、概念边界准确）两种模式一致。

## 粒度示例

P17830 的“跳转链 + 贡献累加”主解可浓缩为：

最后出现位置跳过无效过程 + 按位置统计贡献 + 沿依赖拓扑累加

这只是表述粒度示例，不是其他题目的固定结构；实际使用时仍需核实目标题及选定解法。
