description: 一键只读验收单道题目的代码、验证证据、题解正文和仓库格式，判断是否可发布
---
题目目录：优先用用户消息里给出的路径；消息里没给就用当前工作目录。

目标：对一道已经基本完成的题目做发布前总验收，串联代码审查、主动验证、题解审稿和格式检查，给出统一结论。

硬约束：只检查和报告，不修改仓库里的任何文件，不安装依赖，不生成正式题解或补写缺失代码。所有临时编译产物、测试输入、对拍报告和失败数据放在用 `mktemp -d` 创建的 `/tmp` 目录中。

验收顺序：

1. **材料完整性**：检查 `problem.md`、`index.md`、正式主解文件是否存在；记录 `brute.cpp`、`gen.py` 和过程文档是否存在。缺少后两者不一定直接判失败，但会降低验证置信度。
2. **代码审查**：按 `scripts/navi/rbook-pi-prompt/review-code.md` 的维度核对 IO、边界、溢出、复杂度、递归深度和未定义行为。
3. **运行验证**：按 `scripts/navi/rbook-pi-prompt/verify-solution.md` 运行样例、确定性边界、随机对拍和适用的压力测试。必须把 `ptool` 的 `--report` 与 `--failed-dir` 指向 `/tmp`。
4. **题解审稿**：完整遵循 `.agents/skills/oj-problem-analysis-reviewer/SKILL.md`，核对题意、推导、证明、复杂度、代码对应、教学质量和元数据。
5. **仓库检查**：运行适用于单题的确定性检查，例如：

   ```bash
   python3 scripts/problem-analysis-tools/check_problem.py <题目目录>
   python3 scripts/problem-analysis-tools/check_relations.py <题目目录>
   ```

   这是单题验收，不用 `npm run verify:push` 的全仓库成功替代上述检查。

判定规则：

- **不可发布**：样例或对拍失败、存在确定代码错误、题意/算法/证明/复杂度有实质错误、主解或引用缺失、单题检查失败。
- **有条件可发布**：没有已知错误，但缺少可信暴力、生成器、对拍或关键来源，证据不足。
- **可发布**：所有必需材料与确定性检查通过，正文和代码一致，且未发现阻塞问题。仍要说明测试只能证明覆盖范围内未发现问题。

输出：

- 总结论：可发布 / 有条件可发布 / 不可发布
- 验收表：材料、代码静态审查、样例、边界、对拍、压力、题解质量、格式与元数据逐项写“通过 / 失败 / 未验证”及证据
- 阻塞问题：按严重程度给出文件位置、复现输入或检查输出、原因和修复方向
- 非阻塞风险：证据不足但值得关注的项目
- 下一步：明确建议使用 `generate-data.md`、`create-brute.md`、`find-bug.md`、`write-solution.md` 或人工确认中的哪一个，不要在本次验收中直接修复
