## 形式化题目

给定一个字符串 $s$（可能包含空格），对其中每个字符 $c$ 做映射：

$$
f(c) =
\begin{cases}
\text{对应的大写字母} & \text{若 } c \in [\texttt{a}, \texttt{z}] \\
c & \text{其他情况}
\end{cases}
$$

求把所有字符按 $f$ 替换后得到的字符串。

样例：输入 `helloworld123Ha`，输出 `HELLOWORLD123HA`。逐类看字符的变化：

| 字符类别 | 样例中的字符 | 输出中的对应部分 | 变化 |
| --- | --- | --- | --- |
| 小写字母 | `helloworld` | `HELLOWORLD` | 每个换成大写 |
| 数字 | `123` | `123` | 原样保留 |
| 大写字母 | `H` | `H` | 原样保留 |

三行覆盖了全部情况：**只有小写字母会变，且变换只取决于字符自己**——第 $i$ 个字符的输出与它两侧的字符无关，所以整题就是一次独立的逐字符映射。

## 正解

### 思路

最朴素的写法直接来自逐字符扫描的思路：整行读入后手写一个 `for` 循环，逐字符判断
`'a' <= c <= 'z'` 就把 ASCII 码减 32（同字母大小写在 ASCII 表里正好相差 32），
否则原样收进结果串。

这个朴素做法**没有可消除的瓶颈**：每个字符只被检查一次，复杂度 $O(n)$ 已是下界，
上下文无关的映射也没有"分块、预处理"可省的空间；题目要求的全部计算就是这一层循环。
所以本题不写暴力层——再写一个"朴素版"只会得到与正解逐字符等价的代码，
没有可讲的推进关系，直接给出最终写法。

真正的收获在表达方式上：Python 把"整类字符变换"沉淀成了标准库方法。
`str.upper()` 的语义与题面逐字对应——**把小写字母换成大写，其余字符不动**，
内部在 C 层走一次翻译表扫描，一句话等价于上面整段"循环 + 判断 + 拼接"，
还顺带避免了手写循环里 `chr(ord(c) - 32)` 这种容易拼错的细节。

读入方式是本题唯一的坑：题面明确"可能包含空格"，真实数据中 problem4/6/9/10
都含空格（problem6 还有连续两个空格）。`input()` 恰好满足要求——它只去掉
行末换行，**行内空格原样保留**；而 `split()` 会把空格当分隔符丢掉，输出必然错。

样例的执行过程只有两步：

| 步骤 | 代码 | 结果 |
| --- | --- | --- |
| 整行读入（丢行末换行，留行内空格） | `line = input()` | `helloworld123Ha` |
| 小写 → 大写，其余不动，输出 | `print(line.upper())` | `HELLOWORLD123HA` |

两步里没有任何条件分支需要自己写：`input()` 负责“整行、保留空格”，`upper()` 独立完成全部字符映射，最后 `print` 补上行末换行。也就是说，读者只需记住“读入用哪个函数、变换用哪个方法”，算法本身退居幕后。

### 复杂度

- 时间复杂度：$O(n)$，$n$ 为字符串长度（$\leqslant 100$）：读入、映射、输出各扫一遍。
- 空间复杂度：$O(n)$，保存原串与 `upper()` 返回的新串。

## 总结

- 题目本质是一次与上下文无关的逐字符映射，$O(n)$ 即下界，没有更优解，因此采用直接正解。
- Python 里"整类字符变换"优先找标准库：`line.upper()` 替代手写循环 + `chr(ord(c) - 32)`。
- 输入含空格时用 `input()` 整行读，不要用 `split()`——空格是内容，不是分隔符。
- 本题无状态、无边界特判：非字母和已有大写字母天然原样保留。
