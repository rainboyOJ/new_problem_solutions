## 形式化题目

给定一个 $3\times n$ 的棋盘，每个格子可以填 X 或 O。格子被染色：

- 格子是 X，且它位于**连续三个 X** 排成的一线里（同行、同列或两条对角线）→ 染红；
- 格子是 O，且它位于**连续三个 O** 排成的一线里 → 染蓝；
- 否则染黑。

每个格子有权值 $a_{i,j}$（可以为负），分数 $=$ 所有红格权值之和 $-$ 所有蓝格权值之和。求染色方案的最大分数，$n\leqslant 10^3$。

## 思路

**一句话本质**：三连判定只看相邻 3 列，所以把每列压成 3bit 图案 + 3bit "已计入"标记，做 3 列滑窗的窄带状压 DP，让每个格子的权值在它滑出窗口时恰好结算一次。

**问题？** 直接枚举棋盘染色有多少种方案？

每种方案 $2^{3n}$ 种，$n=1000$ 时完全不可行，但它是"按题意直接判定、绝不会错"的基准。先看这个暴力，它把 $3n$ 个格子拉平成一条 01 选择序列，生成完整棋盘后在叶子统一判定每个格子是否位于三连里：

@include-code(./brute.cpp, cpp)

**问题？** 一个格子是红/蓝/黑，到底由哪些格子决定？

"连续三个相同"的线只有 4 类：横（同行相邻 3 列）、纵（同列相邻 3 行）、对角线 ↘ 和 ↗（各跨相邻 3 列）。所以判定格子 $(r,c)$ 只需要看它自己、同列上下两格、左右两列同行格和两条对角线的斜邻格——也就是以它为中心、半径 2 的邻域。

**问题？** 从"每个格子看邻居"出发，从左往右扫描时状态要记多少列？

格子 $(r,c)$ 的横/斜三连可以跨到 $c+2$ 列，看起来要记未来两列的信息，非常臃肿。这里换个角度：**把"决定颜色"推迟到"所有相关三连都可见"时再做**。包含列 $c$ 的横/斜三连，最右边只到列 $c+2$；因此当窗口恰好覆盖 $[c, c+1, c+2]$ 三列时，列 $c$ 中每个格子是否红/蓝已经**完全确定**，可以一次性结算整列（纵向三连在列内，也在这时判定）。这就是关键卡点①：三连判定只需要相邻 3 列的信息，列状态只要 3bit。状态充分性：更早的列已全部结算完毕，不再影响未来任何判定，所以只需记录最近两列。

注意 $n \leqslant 2$ 需要特判：列数不足 3 时（$n \leqslant 2$）不存在横向/对角线三连，只有纵向三连，代码用 `solve_small` 单独处理；$n=1$ 时主流程状态里"旧列"不存在，必须特判，否则收尾访问越界。

**问题？** 一个格子可能同时属于多个三连（例如全 X 时一个格子横、纵、两条对角线全是三连），贡献怎么保证只算一次？

每个三连被"发现"时如果都去加权，同一个格子会被重复计权。解决方法是给每列额外维护 3bit `colored` 标记：格子第一次被判定为红/蓝时打上标记并计入权值，之后再被其它三连命中时直接跳过。这就是关键卡点②。有了标记，权值结算就只发生在"该格子所在的列滑出窗口左端"这一次。

**问题？** 状态具体记什么？

处理到第 $i$ 列（尚未放置）时，状态记录最近两列——列 $i-2$（窗口左列 $A$）与列 $i-1$（中列 $B$）的图案（3bit）+ colored 标记（3bit），共 12bit；下一轮放置列 $i$（新列 $C$）形成 3 列窗口，并让列 $i-2$ 滑出结算。状态数 $2^{12}=4096$。转移时枚举新列图案(8 种),在 3 列窗口里判定 4 类三连:

- **纵向**：旧列整列图案为 000 或 111；
- **横向**：三列同一行图案相同；
- **对角线 ↘**：格 $(0,旧)(1,中)(2,新)$ 相同；
- **对角线 ↗**：格 $(2,旧)(1,中)(0,新)$ 相同。

旧列格子命中 → 结算权值（红 $+$、蓝 $-$）；中列、新列格子命中 → 只打 colored 标记，等它们成为旧列时再结算。

**问题？** 一个 $3\times 3$ 窗口里有 8 条直线，为什么只判定 6 条？

$3\times 3$ 内长度为 3 的直线共 8 条：3 横、3 竖、2 对角。但窗口 $(A,B,C)$ 这一轮**只判定"最左格落在 A 列"的直线**：

- 3 条横向、2 条对角线的最左格都在 A 列 → 全部收录；
- 3 条纵向里只有 A 列整列落在窗口内 → 收录 1 条；B 列、C 列的纵向三连要各自等它们变成窗口左列 A 时才判定（下一轮、下下轮）。

展开就是下面这 6 条：

```text
1 条纵向： (0,A)(1,A)(2,A)
3 条横向： (0,A)(0,B)(0,C)   (1,A)(1,B)(1,C)   (2,A)(2,B)(2,C)
2 条对角： (0,A)(1,B)(2,C)   (2,A)(1,B)(0,C)
```

所以判定的是 $1+3+2=6$ 条而不是 8 条。这样安排的意义在于：**每条三连在整个 DP 中恰好被检查一次**，正好对应“每条三连都在它最左列滑到窗口左端时结算”，也解释了为什么结算函数只需要处理旧列 A 的账。代码里把这 6 条三连直接写成常量表 `T[6][3]`：`T[t][k]` 是第 $t$ 条三连的第 $k$ 个格子，用结构体 `offset{row, col}` 记录“第几行 + 哪一列（0=A, 1=B, 2=C）”，`gain()` 用一个循环统一判定，不必为每类三连单独写代码。

**问题？** 这 12bit 状态是“想”出来的一大坨吗？脑容量不够怎么办？

不是。它只是几个小积木的乘积：**2 列 ×（每列 3bit 图案 + 3bit 标记）× 3 行 = 12bit**。真正撑爆脑子的不是位数，而是“**当场给格子定色**”的直觉；把目标换成“让下一列能算对”，状态就是被逼出来的，不用靠记忆堆。

**问题？** 为什么“当场定色”一定会失败？

一条三连跨 3 列，一个格子会被好几个窗口反复命中。在窗口 $(c-1,c,c+1)$ 就给 $(r,c)$ 加权，等窗口 $(c,c+1,c+2)$ 再次命中它时会重复加；当场不加，等它滑出窗口又补不回来。**早定色会重复、晚补又来不及——只能推迟结算。**

**问题？** 推迟之后，为什么还要多一个“已计入”标记？

因为**过去的信息会丢**：窗口 $(c-1,c,c+1)$ 判定过 $(r,c)$ 染色，但当时列 $c$ 还没滑出、不能结算；等列 $c$ 滑出时，那三列早已不在状态里，无法重新判断。要么当场记下这 3bit，要么把状态撑成 5 列——选前者，`mark` 位就出现了。

所以状态不用“设计”，用它的唯一职责反推就行：**状态 = 为了让下一列能算对、不得不记住的最小信息**。下一列要判三连 → 留最近两列的图案；更早窗口的结论会丢 → 留最近两列的标记。12bit 是推导结果，不是要背的清单。

### 状态转移方程

先把记号固定下来。用 $p_c \in \{0,\dots,7\}$ 表示列 $c$ 的图案，第 $r$ 位为 $1$ 表示格子 $(r,c)$ 画 X；用 $m_c \in \{0,\dots,7\}$ 表示列 $c$ 的"已计入"标记，第 $r$ 位为 $1$ 表示格子 $(r,c)$ 已被判定为红/蓝、但权值还没结算。状态

$$
s = (p_A,\ m_A,\ p_B,\ m_B)
$$

打包了"窗口左列 $A$"和"中列 $B$"的全部信息，共 $12$ bit。

$dp[s]$ 的含义是：**最近两列恰为状态 $s$ 时，左侧所有列都已结算完毕的最大分数**。它只统计"已落账"的部分，$A,B$ 中被标记的格子权值仍然挂账。

从 $s$ 再放一列 $C$（图案 $p_C$），列 $A$ 滑出窗口、当场结清，转入新状态 $s' = (p_B,\ m_B',\ p_C,\ m_C')$，转移方程是

$$
dp'[\,s'\,] = \max_{p_C \in \{0,\dots,7\}} \Big\{\ dp[s] + \mathrm{settle}(A)\ \Big\}
$$

其中 $\mathrm{settle}(A)$ 是列 $A$ 这一轮结算掉的总权值：列 $A$ 中凡是**位于三连里**的格子，红格 $+a_{r,A}$、蓝格 $-a_{r,A}$，并且**每个格子只算一次**。红/蓝的符号用一个式子统一给出：$p_A[r]=1$（X）取 $+1$，$p_A[r]=0$（O）取 $-1$，即

$$
\mathrm{sgn}(r) = 2\,p_A[r] - 1 .
$$

$\mathrm{settle}(A)$ 覆盖三类格子：之前被更早的窗口判定为染色、记在 $m_A$ 里的格子；列 $A$ 自身的纵向三连（$p_A = 0$ 或 $7$）；窗口 $(A,B,C)$ 的横向、两条对角三连命中的 $A$ 格子。

同一轮里，被窗口三连命中的中列 $B$、新列 $C$ 格子**只打标记、不结算**：

$$
m_B' = m_B \cup H_B,\qquad m_C' = H_C,
$$

其中 $H_B, H_C$ 分别是本轮窗口的横/斜三连命中的 $B$、$C$ 的行集合。

初始状态是"列 0、1 图案任意、无任何标记"：

$$
dp\big[(p_0,\ 0,\ p_1,\ 0)\big] = 0,\qquad p_0, p_1 \in \{0,\dots,7\}.
$$

主循环结束后，状态停在最后两列 $(n-2, n-1)$，它们的账还没结，所以最终答案要在所有状态上再补结一次：

$$
\mathrm{answer} = \max_{s} \Big\{\ dp[s] + \mathrm{settle}(n-2) + \mathrm{settle}(n-1)\ \Big\},
$$

收尾时右侧没有第三列，$\mathrm{settle}$ 里只剩"纵向三连 $+$ 已有标记"两项。

**怎么读这个方程：**

1. $\max$ 是对新列图案 $p_C$ 取的：三列窗口里 $A,B$ 已由状态 $s$ 唯一确定，$p_C$ 是唯一的自由变量，要挑对答案最有利的一种。
2. 加号左边 $dp[s]$ 是**过去已固定**的分数，右边 $\mathrm{settle}(A)$ 是**刚滑出窗口的那一列**新贡献的分数；列 $A$ 的权值在此之前从未加过，所以不重不漏。
3. 方程里只出现最近两列，更早的列既不在状态里、也不在方程里——这就是"三连只跨 3 列"带来的**马尔可夫性**：列 $A$ 一旦结清，对未来再无影响。
4. 标记 $m$ 是方程能成立的关键：$\mathrm{settle}(A)$ 和 $m_B$ 的更新必须放在**同一次**转移里，否则 $(A,B,C)$ 这条三连下一轮就看不见了，中列 $B$ 中被它染色的格子会漏账。

### DP 转移表格

先看 12bit 状态在代码里的布局（低 6 位是窗口左端“旧列 $A$”，高 6 位是“中列 $B$”）：

| 位 | 0..2 | 3..5 | 6..8 | 9..11 |
| --- | --- | --- | --- | --- |
| 含义 | 旧列图案 | 旧列已计入 | 中列图案 | 中列已计入 |

下表把一次转移拆成 5 个逻辑步骤；代码里这 5 步由 `gain()` 一次完成——第 1 步是开头的落账循环，第 2~5 步是 6 条三连共用的那个循环。用样例 1（$n=3$，权值全为 1）演示一次完整转移：初始状态是列 0、列 1 全 X 且无标记($dp=0$),枚举新列 j=2 的图案为全 X:

| 转移步骤 | 判定的三连 | 动作 | 累计 gain |
| --- | --- | --- | --- |
| 初始状态 | 旧列 $A$=列0: 图案111 已计入000；中列 $B$=列1: 图案111 已计入000 | $dp=0$ | 0 |
| 1. 结算旧列已计入格子 | 列0 无标记 | 无 | +0 |
| 2. 纵向三连 | 列0 整列 XXX | 三格计入并结算 | +3，旧列已计入=111 |
| 3. 横向三连 | 三行都是 列0=列1=列2=X | 中列、新列打标记 | 中列已计入=111，新列已计入=111 |
| 4. 对角线 ↘ | (0,列0)(1,列1)(2,列2) 全 X | 打标记 | 标记已存在，跳过 |
| 5. 对角线 ↗ | (2,列0)(1,列1)(0,列2) 全 X | 打标记 | 标记已存在，跳过 |
| 新状态 | 旧列 $A$=列1(图案111,已计入111)，中列 $B$=列2(图案111,已计入111) | $ndp=0+3=3$ | 3 |

观察这张表：横向、两条对角线三连都命中了列 1、列 2 的格子，但因为 colored 标记，每个格子只被标记一次；而且列 0 的格子被纵向、横向、两条对角线四个三连同时命中，gain 却只加了 3 而不是 12——这正是"一格只计一次"的体现。

转移完成后，最后两列（列 $n-2$、$n-1$）永远不会成为窗口左端，需要单独收尾结算：把已计入的格子权值加上，再补判纵向三连。延续上面的状态（列1、列2 已计入均为 111）：

| 收尾结算 | 图案 | 已计入 | 结算 |
| --- | --- | --- | --- |
| 列 1（$n-2$） | 111 | 111 | +3 |
| 列 2（$n-1$） | 111 | 111 | +3 |
| 总计 | | | 9 |

看这张表：列 1、列 2 的格子权值在此刻结算，加上转移阶段结算的列 0 的 3，总分 9，与样例 1 一致。每个格子的权值在整个 DP 中恰好出现一次。

## 复杂度

状态数 $2^{12}=4096$，每个状态枚举 8 种新列图案，共 $n-2$ 轮主循环，收尾 $O(2^{12})$：

- 时间复杂度：$O(n \cdot 4096 \cdot 8)$，$n=1000$ 时约 $3.3\times 10^7$ 次操作；
- 空间复杂度:$O(4096)$,只需滚动两行 DP 数组。

## 另一种解法：五列窗口（不记账）

主解是“三列窗口 + 染色标记”：只拿到 3 列就急着结算左列，再用标记把更早窗口的信息补回来。这里换一个**更直白、但状态更大**的思路——**攒够信息再结算**。

### 思路

**信息覆盖**：一条三连最多跨 3 列，所以某一列的格子是否染色，只取决于它**左右各 2 列**。把这 5 列凑齐，正中间那一列的颜色就完全确定，可以一次性结算。于是不需要任何“已计入”标记。

滑动一下看（中间列逐列被确定）：

| 窗口 | 本步新确定 | 累计已确定 | 仍待定 | 状态里留的 4 列 |
| --- | --- | --- | --- | --- |
| [1][2][3][4][5] | [3] | $\le$ [3] | [4][5] | [2][3][4][5] |
| [2][3][4][5][6] | [4] | $\le$ [4] | [5][6] | [3][4][5][6] |
| [3][4][5][6][7] | [5] | $\le$ [5] | [6][7] | [4][5][6][7] |
| [4][5][6][7][8] | [6] | $\le$ [6] | [7][8] | [5][6][7][8] |

注意：**5 列窗口只确定正中间那一列**。[3]、[4] 并不是在窗口 [3..7] 这一步确定的，而是更早的窗口 [1..5]、[2..6] 已经结算过；到 [3..7] 这一步，累计已确定的是 $\le$ [5]，待定的是 [6][7]。

**要检查几条三连**：结算中间列时，只有"经过中间列"的三连才可能影响它的颜色，其余三连碰不到列 2，判了也白判。3 行 × 5 列里经过列 2 的直线恰好 16 条：横向 9 条（每行 3 条）、纵向 1 条（只有列 2 自己的竖线完整落在窗口内）、右下斜 3 条、右上斜 3 条。代码里用 `build_lines()` 生成这 16 条，用一张固定的线表代替"对每个格子反推它可能在哪些三连里"的坐标运算。

**为什么状态只存 4 列**：第 5 列正是“刚要加进来的那一列”。状态里存的是“已经拿到、但还没用于结算”的信息：

```text
4 列  →  加新列 = 5 列  →  结算中间列  →  丢掉最旧列  →  又是 4 列
```

每步恰好丢掉最旧一列，所以状态恒为 4 列，记 $f(\text{最近 4 列})$ 即可；棋盘外不存在的列用“虚拟列”补齐。

**和主解的对比**：

| | 何时结算 | 要不要额外记账 | 状态 |
| --- | --- | --- | --- |
| 主解（`main.cpp`） | 只有 3 列就结算左列 | 要（否则更早窗口的信息会丢） | 2 列 + 染色标记 = 12bit |
| 本解（`main2.cpp`） | 等到 5 列才结算中列 | 不要（信息齐了才动手） | 4 列图案 = $9^4$ |

一句话：**主解是“提前结算 + 记账补信息”，本解是“攒够信息再结算、不记账”。**

### `dp` 里到底存了什么

上面说"记 $f(\text{最近 4 列})$"，落到代码里就是字典 `dp`：

```python
dp: dict[tuple, int]      # 键 = 状态，值 = 分数
```

**key 是状态，回答"未来长什么样"。** 元组的每个元素是一列的 3bit 图案（`0..7`），棋盘外的虚拟列写 `None`；元组里存的是"以刚读入的那一列结尾的最后若干列"：

```python
key = ( ..., p[i-3], p[i-2], p[i-1], p[i] )
```

| 处理完 | key 的形状 | 例子 |
| --- | --- | --- |
| 列 0 | 3 元组 | `(None, None, 5)` |
| 列 1 | 4 元组 | `(None, None, 5, 3)` |
| 列 2 起 | 4 元组 | `(None, 5, 3, 7)` |

注意 key **永远不是 5 元组**——5 列只活在循环体的临时变量 `window` 里，结算完就把最左一列丢掉：

```python
window = state + (pattern,)   # 凑成 5 列，结算中间列
new_state = window[-4:]       # 存回 dp 的仍然只有 4 列
```

**value 是分数，回答"过去赚了多少"。** `dp[key] = v` 读作：*最后这几列的图案是 key 时，更左边那些已经结算完的列的得分总和，最大能到 v。*

**问题？** key 已经记了状态，为什么还要 value？直接存 key 不行吗？

因为**得分是累加的，而 key 只留了最后 4 列**，更左边的列已经被丢掉，它们的分数不可能从 key 反推。用样例 2（$n=4$）跑真实数据，倒数第二轮就出现同一个 key 对应多种历史分数的情况：

```text
key = (0, 0, 0, None)
    历史得分 = [83, 84, 85, 87, 88, 95]     ← 6 条不同路径抵达同一状态
    dp 只留   = 95
```

同一个 key，有的历史只赚 83 分，有的赚 95 分。key 看不出区别，差的那 12 分只能靠 value 记住。

**问题？** 那为什么可以只留最大值，把别的都扔掉？

因为转移增量只依赖 `key + 新列`：

```python
window = state + (pattern,)
gain = 0
if len(window) == 5:                                # 凑齐 5 列才轮到中间列结算
    gain = middle_score(window, next_col - 2, weight)
new_score = old_score + gain        # 过去唯一的作用就是这个加法
```

被丢掉的列再也不可能影响任何未来的 `gain`。所以到达同一 key 的两条历史面对的"未来"完全一样，未来能加的分也一样 $\Rightarrow$ 谁的过去分高谁永远赢 $\Rightarrow$ 低分那条可以安全删除。这就是无后效性，也正是下面这一行的依据：

```python
next_dp[new_state] = max(next_dp.get(new_state, NEG), new_score)
```

**如果 `dp` 只是"状态的集合"，这一行就不存在了——这一行就是 value 这个概念本身。**（`NEG` 只是 `max` 合并时表示"还没有值"的占位，不会被写进最终结果。）

**问题？** 那干脆"直接存每列的状态"、存下整条序列 $p_0,p_1,\dots,p_{n-1}$ 不行吗？

那就是不压缩、不合并，路径数是 $8^n$：$n=4$ 时 4096 条，$n=1000$ 时约 $10^{903}$ 条。DP 的全部价值就是把 $8^n$ 条压成不超过 $8^4=4096$ 个 key。压缩必然丢信息：**过去各列的图案可以丢（无后效性），但过去赚的分不能丢（它就是答案）**，于是浓缩成一个标量挂在 key 上。

所以 `dp` 的本质是一个**映射**：

$$
dp:\quad \text{状态} \;\longrightarrow\; \text{该状态下能达到的最大累计得分}
$$

它对应的"状态集"不是预先枚举好的，而是被 `max` 合并**动态长出来**的：多条路径撞上同一个 key 才产生一个状态，而"状态存在"这件事，就是它的 value 不是 `NEG`。`main2.cpp` 用 C++ 重写时，把这层意思换成了定长数组 `dp[9^4]`：

```cpp
for (int s = 0; s < SZ; s++) dp[s] = NEG;
if (dp[s] == NEG) continue;      // 等价于"这个 key 不在字典里"
```

数组是稠密预分配的，字典是稀疏懒生长的，两者概念完全一样：**key 管未来，value 管过去，缺一不可。**

## 总结

这道题的关键是把"格子颜色"的判定从局部视角换成窗口视角:横向/斜向三连跨相邻 3 列,所以当一列滑出 3 列窗口时,它的颜色已经确定。窄带状压 DP 的通用套路就是--**先找"未来只依赖过去哪段紧凑信息"(这里是相邻 2 列),再用 colored 标记解决"一个对象被多个结构重复命中"的计权问题**。这种“标记去重”的思想在网格类 DP 里很常用。

本题还演示了两种“有限记忆”策略：主解**提前结算 + 用标记补回已经丢失的信息**（状态更小），另一解**攒够 5 列信息再结算、完全不用标记**（状态更大但更直白）——它们都是“只保留够用的过去”这一思想的变体。
