## 形式化题目

给定 4 个值：字符 $c$、整数 $n$、单精度实数 $a$、双精度实数 $b$。
要求按同一顺序把它们用单个空格连接成一行输出，其中 $a$ 取输入文本在 IEEE-754
**binary32** 下的最近值，$b$ 取 **binary64** 下的最近值；两个浮点数都按定点格式
写出恰好 6 位小数（不足补 `0`，负号保留）。

样例：

```
a
12
2.3
3.2
```

```
a 12 2.300000 3.200000
```

样例逐位置对照表，展示"同一个 token 按不同类型读入"的含义：

| 位置 | token | C++ 类型 | 变量里真正持有的值 | 输出片段 |
| --- | --- | --- | --- | --- |
| 1 | `a` | `char` | 字符 `a` | `a` |
| 2 | `12` | `int` | 12 | `12` |
| 3 | `2.3` | `float`（binary32） | `2.299999952316284…` | `2.300000` |
| 4 | `3.2` | `double`（binary64） | `3.200000000000000…` | `3.200000` |

观察重点：样例里第 3、4 个数的输出完全一样，**看不出**它们的类型不同——
`2.299999952316284` 四舍五入到 6 位小数正好回到 `2.300000`。
类型差别被样例掩盖了，这正是本题最容易踩空的地方。

## 正解

### 思路

本题没有可优化的算法层：输入固定 4 个 token，任何正确写法都走同一条
"分词 → 按类型转换 → 定点输出"的链路。按直接正解型组织，真正要学的是
**每个 token 按它自己的类型解析**，尤其是第 3 个数的单精度。

**第一步：分词读入。** C++ 的 `cin >> ch >> a >> b >> c` 是"跳过任意空白、
按 token 读"，每个变量再用自己的类型解析文本。Python 侧的等价写法是
`sys.stdin.read().split()`：它按空白切分，所以题面写"四行"、数据写"一行"
切出来是同一组 4 个 token。

**第二步：第 3 个数要按单精度读（本题唯一考点）。** 参考解把第 3 个数存进
`float`，变量里是文本在 binary32 下的最近值；Python 的 `float` 只有 binary64，
直接写 `float(token)` 会多留几位精度。以真实数据 problem0 为例
（$13928.89 \in [2^{13}, 2^{14})$，故 binary32 的间距 $\mathrm{ulp} = 2^{13-23} = 2^{-10}
\approx 0.0009766$）：

| binary32 网格上的相邻点 | 距输入 `13928.89209389` |
| --- | --- |
| `13928.8916015625` | $0.0004923 > \mathrm{ulp}/2$ |
| **`13928.892578125`** | $\mathbf{0.0004842 < \mathrm{ulp}/2}$ → 最近 |
| `13928.8935546875` | $0.0014608 > \mathrm{ulp}/2$ |

所以 $a = 13928.892578125$，打印 6 位小数为 `13928.892578`；而按 binary64 读入后
打印是 `13928.892094` —— 差在输出的第 6 位小数上。原因是这里的
$\mathrm{ulp} \approx 10^{-3}$ 比打印精度 $10^{-6}$ 大了三个数量级：
单精度这步的舍入量已经超过打印精度，只要它跨过某个 6 位小数的分界，
输出就会跟着变。

反过来，只有当 $|x| < 16$ 时才有 $\mathrm{ulp}/2 < 5\times10^{-7}$：
舍入量被打印精度完全吞掉，压不压单精度得到的字符串一模一样——
样例的 `2.3`、`3.2` 正落在这种量级里，所以只看样例发现不了这个问题。

Python 里把 double 搬成 binary32 的两步往返就是：

```python
def to_float32(text: str) -> float:
    """按 C++ float 的精度读入：先解析成 double，再截回单精度的精确值。"""
    return struct.unpack("f", struct.pack("f", float(text)))[0]
```

`struct.pack("f", x)` 按 binary32 编码（这一步发生舍入），
`struct.unpack("f", bytes)` 再把 4 字节读回成 double；读回的值正是那个
binary32 实数的**精确值**，于是它和 C++ 里 `float` 变量持有的数完全相同。

**第三步：格式化输出。** `f"{to_float32(b):.6f}"` 就是 C 的 `printf("%.6f")`：
对持有值的精确二进制值做十进制四舍五入、取 6 位小数、不足补 `0`、保留负号，
一次做完。最后 `print(ch, int(a), ..., ...)` 的多参数形式默认 `sep=" "`
（间隔一个空格），与参考解 `cout << ch << " " << ...` 的输出格式一致。

排除的写法：

| 写法 | 为什么不行 |
| --- | --- |
| `float(b)` 直接格式化第 3 个数 | 精度是 binary64；真实数据 10 组全部输出错误 |
| `round(x, 6)` | 返回浮点数，`3.2` 打出 `3.2`，尾随 0 丢失 |
| 手工按字符串截 6 位小数 | 不做四舍五入，也没解决单精度取值 |
| 直接输出 token 原文 | 数字文本不等于它二进制表示对应的十进制串（如 `13928.89209389` ≠ `13928.892578`） |

与同源的 [[roj/1024]]、[[roj/1025]] 相比，本题多出的就是"第 3 个数必须按
单精度读"这一条：1025 的参考解本来就把数读进 `double`，1024 的参考解虽然读的是
`float`，但它只要 3 位小数、数值只有 $10^2$ 量级，binary32 的舍入量（$\leqslant 6\times10^{-5}$）
会被 $10^{-3}$ 的打印精度吞掉。本题同时踩中"参考解读 `float`"和"只要 6 位小数、
数值到 $10^5$"两点，单精度的痕迹才露了出来。

### 复杂度

- 时间复杂度：$O(1)$。4 个 token 各做一次常数时间解析，第 3 个多两次 `struct`
  编解码；与正解同阶（输入规模恒定，不存在随数据增长的循环）。
- 空间复杂度：$O(1)$。只保存 4 个 token 与一行输出；实测峰值 14.6MB，
  远低于 128MB 限制，单测例约 0.017s，远低于 1000ms。

## 总结

- 输入只有 4 个 token 时，`sys.stdin.read().split()` 就等于 `cin >>` 的空白分词，
  四行写法和一行数据同解；输出用 `print(ch, int(a), ...)` 的默认空格分隔。
- 本题的唯一考点是**类型化读入**：第 3 个数是单精度，Python 没有 binary32，
  要用 `struct.unpack("f", struct.pack("f", float(text)))[0]` 手工压回单精度；
  只按 double 读会让输出的第 6 位小数与参考解不同。
- 样例 `2.3` / `3.2` 掩盖了类型差别（binary32 的间距在这个量级小于 $10^{-6}$），
  所以"样例过了就不管单精度"是本题最典型的错法；真实数据量级在 $10^4\sim10^5$，
  binary32 间距达 $10^{-3}\sim10^{-2}$，差别必然外显。
- 定点输出统一交给 `:.6f`：舍入、补零、负号一次完成，不需要任何手写分支。
