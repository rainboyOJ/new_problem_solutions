## 形式化题目

有 $n$ 个人，编号 $1 \sim n$ 就是名字在输入中出现的先后顺序，每个人初始钱数为 $0$。
随后给出若干条送礼记录，每条记录由三元组描述：

$$
(\;g,\ m,\ c,\ r_1, r_2, \dots, r_c\;)
$$

含义是：$g$ 把 $m$ 元**平均分**给自己指定的 $c$ 个人 $r_1 \dots r_c$，
每人得到 $\left\lfloor m / c \right\rfloor$ 元，除不尽的余数 $m \bmod c$ 由 $g$ 自己留下。
若 $c = 0$，这条记录不产生任何钱的转移。所有人之间不存在先后依赖，
每条记录只是一次独立的加减记账。要求在全部记录执行完后，按编号顺序输出每个人的最终钱数。

输入样例（题面样例，人名为 `maomao` 等）：

```
5
maomao
laura
owen
vick
amr
maomao
200 3
laura
owen
vick
owen
500 1
maomao
amr
150 2
vick
owen
laura
0 2
amr
vick
vick
0 0
```

输出样例：

```
maomao 302
laura 66
owen -359
vick 141
amr -150
```

把每条记录执行完后的钱数快照列出来，就能看清规则：

| 已执行的记录 | money[maomao] | money[laura] | money[owen] | money[vick] | money[amr] |
| --- | --- | --- | --- | --- | --- |
| （初始） | $0$ | $0$ | $0$ | $0$ | $0$ |
| maomao：$200 \to 3$ 人 | $-198$ | $66$ | $66$ | $66$ | $0$ |
| owen：$500 \to$ maomao | $302$ | $66$ | $-434$ | $66$ | $0$ |
| amr：$150 \to$ vick、owen | $302$ | $66$ | $-359$ | $141$ | $-150$ |
| vick：$0 \to 0$ 人 | $302$ | $66$ | $-359$ | $141$ | $-150$ |

第一行是 200 元分给 3 人：每人 $200 \div 3 = 66$，余下 $2$ 元留在 maomao 手里，
所以 maomao 这一行的变化是 $-200 + 2 = -198$；最后一行 `0 0` 是空记录，表格不再变化。
注意 owen 中途是 $-434$，说明钱数可以为负，本题只看净额、不看"手上够不够"。

## 正解

### 思路

题面已经给出了全部规则，没有任何隐藏的优化点，所以解法就是**把规则直译成一遍扫描**。
真正需要设计的地方只有三处：怎么把名字换成下标、怎么处理未知条数的记录、怎么算均分与余数。

**第一处：名字 → 下标。** 记录里只出现名字，但记账只需要一个下标，
而且最后要按"读入名字的顺序"输出。于是先读完 $n$ 个名字存进 `names`，
再用字典推导式建一张反查表：

```python
index = {name: i for i, name in enumerate(names)}
```

`names` 负责输出顺序，`index` 负责 $O(1)$ 查人，两者共用同一套下标，
钱数数组 `money = [0] * n` 就只用长度 $n$ 的定长数组，不需要任何字符串状态。

**第二处：记录条数未知。** 输入只说"第 $n+2$ 行一直到文件末尾"，没有给出记录条数，
所以不能先数条数再循环。读入切成令牌流后，每条记录的第一个令牌必然是送钱人的名字，
于是直接写成

```python
for giver in data:
    ...
```

迭代器耗尽即文件结束，循环自然终止；`cnt` 只用来控制"这条记录还要再读几个名字"。
这样既不会多读一条，也不会漏掉最后一条。

**第三处：均分与余数。** 设钱数为 $m$、接收者个数为 $c$，则

$$
share = \left\lfloor \frac{m}{c} \right\rfloor, \qquad left = m - c \cdot share = m \bmod c
$$

这两件事在 Python 里由 `divmod(m, c)` 一次给出，正对应 `divmod` 返回的商和余数。
送钱人的净支出是"真正分出去的部分" $m - left$（等于 $c \cdot share$），
而不是 $m$：如果直接写 `money[g] -= m`，就还得再补一次 `money[g] += m % c`，
等价但多一步，也容易在 $c=0$ 时误做取模。余数自留这个细节在样例里就能看到：
$200$ 分给 $3$ 人，maomao 只亏 $198$ 而不是 $200$。

还有一处不能省：$c = 0$ 时 `divmod` 会抛 `ZeroDivisionError`，
所以用条件表达式把空记录挡住，令 $share = left = 0$：

```python
share, left = divmod(amount, cnt) if cnt else (0, 0)
```

它同时覆盖了样例中 `vick / 0 0`（$m=0,c=0$）和 $m>0, c=0$ 这两种情况，
两者按定义都不产生任何钱的转移。

**为什么不做别的优化。** 名字的线性查找（逐个比较字符串）同样正确，
两者都是"一遍线性模拟"，差别只在查找常数；$n \leqslant 20$ 时都远低于时限。
选字典不是为了"更快"，而是因为它把"人"这一概念压成了一个下标，
让状态退化成一条 `money` 数组——这正是本题的模型。
同理，本题不存在需要单独教学的朴素层，正文只给这一个正解。

### 复杂度

设 $L$ 为所有记录的接收者总数（除名字表之外的名字令牌个数）。

- 时间：$O(n + L)$。建表 $O(n)$，每条记录一次字典查找加 $cnt$ 次字典查找，
  输出 $O(n)$；所有记账都是常数时间的整数加减。
- 空间：$O(n)$。`names`、`index`、`money` 各占 $O(n)$；
  输入一次性读入内存，规模由数据文件决定。

## 总结

本题是入门级的模拟题，算法上只有一遍线性扫描，值得记住的是三个习惯：

- **名字只用一次的地方，就把名字换成下标。** 字典映射让状态变成定长数组，
  输出顺序也由这张表固定下来，不必再做二次查找或排序。
- **条数未知的输入用迭代器耗尽当结束条件。** `for giver in data:` 比手工判 EOF 更不容易出错，
  记录内部再用 $cnt$ 精确控制读几个名字。
- **整除与余数一起算。** `divmod` 一次给出人均份额和自留余数；
  除数为 $0$ 时要单独挡住，顺序是"先判除数、再除法"。

真实数据 $9$ 组、根目录 `in` 与题面样例均已逐组比对通过（另与数据仓 `std.cpp` 交叉核对，$10$ 组输出全部相同），
实测单组耗时约 $0.017$ s、峰值内存约 $14.6$ MB。
